## 项目深挖

### 事务一致性问题，如调用了风控扣款，之后票据这边出问题了，怎么办
**1. 还原真实的业务链路与代码结构**

> “坦白讲，由于这是一个有历史包袱的系统，早期的开发规范是直接在 Service 层加 `@Transactional`。 我们当时的真实业务链路是自带补偿逻辑的：
> 
> 1. 先通过 RPC 调用风控系统，**占用额度**。
>     
> 2. 额度占用成功后，继续往下走本地的票据落库、状态流转等核心业务。
>     
> 3. 如果本地业务逻辑抛出了异常（比如校验不通过、唯一键冲突），我们会在代码的 `catch` 块或者 `finally` 块里，再去发一次 RPC 调用风控系统的**释放额度（回冲）**接口。最后抛出异常，让 Spring 把本地事务回滚。
>     
> 
> 从正常流程来看，这套逻辑形成了一个闭环：成功了就一起成功，失败了就调接口把别人复原，自己再回滚。”

**2. 揭示“分布式陷阱”与大事务痛点（展现架构深度）**

> “但在真实的生产环境中，这种**‘在本地大事务里包裹正反两次 RPC 调用’**的做法，有着极其致命的隐患。
> 
> **隐患一：连接池被长时间霸占。** 占用额度和释放额度一来一回两次网络开销，这期间本地的数据库连接是死死捏在手里不放的。一旦风控系统响应变慢，我们的数据库连接池瞬间就会被打满。
> 
> **隐患二：同步补偿失败导致的‘单边账’（薛定谔的释放）。** 这是最致命的一点。假设本地业务失败了，代码走到了 `catch` 块去调用风控的‘释放额度’接口。此时**如果网络断了、或者风控系统瞬时宕机了，释放接口调用失败（抛出 Timeout 异常）**。 结果是什么？Spring 依然会把本地的数据库回滚（票据没落库），但风控那边的额度**永远被占用了**，而且我们的系统再也没有代码去触发第二次释放。这就是经典的‘单边账’。”

**3. 当时的务实兜底方案（怎么解决单边账）**

> “面对这种极端网络异常导致的释放失败，我们当时的兜底手段是**‘T+1 日终对账’ + ‘人工补偿’**。 因为额度被多占了属于长款，资金没有真跑掉。夜间的定时对账文件跑批时，会发现风控有一笔额度被占，但我们票据系统找不到对应的成功单据。这时就会生成异常预警，由业务运营在后台核实后，手工点击触发释放。在当时，这算是 ROI（投入产出比）最高的兜底做法。”

**4. 终极反杀：基于防御性编程的内部重构方案（只改自己，求稳为主）**

> “但随着单量的上涨，这种强耦合的同步补偿风险太大了。如果现在由我来主导重构，在**‘坚决不改动下游风控系统接口’**的前提下，我会利用**‘本地状态机 + 异步补偿’**来彻底解决这个问题：
> 
> 1. **切碎大事务，记录前置状态：** 先开一个极小的本地事务，插入一条票据记录，状态设为 `待占额度`，立刻 Commit。
>     
> 2. **无事务环境下的 RPC 占用：** 在事务外调用风控占用额度。如果成功，再开小事务把状态改为 `额度已占，业务处理中`。
>     
> 3. **核心业务处理与防断电机制：** 执行核心业务。如果失败，我们**不再做脆弱的同步 RPC 释放**，而是利用本地事务，将票据状态改为 `业务失败，待释放额度`。
>     
> 4. **后台 Job 异步兜底（核心精髓）：** 写一个后台定时补偿任务，专门扫描 `待释放额度`，以及卡在 `额度已占，业务处理中` 超过 10 分钟的异常单。由这个定时任务，在后台不断重试调用风控的释放接口。只要风控系统恢复，额度必定能被自动释放，彻底消灭单边账，也把人工对账的活儿全自动化了。”
>


### 事务+MQ 架构策略
**面试官：** 你们处理完本地业务后，是怎么发送 MQ 报文给票交所的？如果放在同一个事务里，不怕长事务或者发 MQ 失败导致本地脏回滚吗？

**你的满分话术：** “这就涉及到了我们系统内部对**‘可靠消息最终一致性’**的架构封装了。

在上层业务代码来看，我们是串行写的：先做本地业务 CRUD，然后直接调用一个封装好的 MQ 发送方法。看起来像在一个大事务里，但其实底层的平台封装做得很巧妙，采用了 **本地报文流水表 + AFTER_COMMIT 实时发送** 的模式。

1. **本地事务原子性：** 我们在 `@Transactional` 中，除了修改业务表，还会向同库的**‘报文流水表’**中插入一条状态为 `待发送` 的记录。这保证了业务状态和发信意图的本地原子性。
    
2. **剥离网络 I/O（实时解耦）：** 那个封装好的 MQ 发送方法，底层其实利用了 Spring 的 `TransactionSynchronizationManager`（事务同步管理器）。它拦截了发送动作，把它挂载到了 `AFTER_COMMIT` 阶段。只有当本地事务真正在底层 DB 落盘提交、释放了数据库连接后，才会立刻在事务外实时发起 MQ 网络调用。这完美规避了网络 I/O 拖死连接池，以及‘本地回滚但 MQ 已发出’的幽灵消息问题。
    
3. **极端异常的兜底：** 即使事务提交成功后，实时发送 MQ 时网络挂了，或者机器突然断电，也没关系。因为同库的‘报文流水表’里已经记下了这条 `待发送` 的消息。底层会有异步的补偿机制去扫描这张表进行补发。
    

这样一套封装，既实现了绝大多数正常情况下的**毫秒级实时发送（低延迟）**，又通过本地流水表保证了极端异常下的**100% 消息必达（高可靠）**，同时业务开发的同事也完全不需要去关心这些底层的分布式一致性问题。”






### 数独，回溯

回溯模板：
所有回溯问题，都可以抽象为一棵**N 叉树**：
- **树的深度（纵向）：** 决定了递归的层数（往往对应你要找的组合长度 `k`，或者字符串长度）。
- **树的宽度（横向）：** 决定了 `for` 循环的次数（当前层有多少个选项可以选）。
    
**万能模板：**

```java
// 全局变量定义：
// res 负责装所有的有效路径（最终答案）
List<List<Integer>> res = new ArrayList<>();
// path 负责记录当前正在探索的单一路径（像一个探路的小兵）
List<Integer> path = new ArrayList<>();

/**
 * 回溯算法万能模板（以组合问题为例）
 * 
 * @param nums       原始的数据集（候选池）
 * @param startIndex 控制下一层递归从哪里开始，防止出现重复的组合（如避免 [1,2] 和 [2,1] 算两次）
 *                   注：如果是“全排列”问题，不需要 startIndex，而是换成 boolean[] used 数组来记录谁被用过。
 */
public void backtrack(int[] nums, int startIndex) {
    
    // ==========================================
    // 1. 终点拦截 (Base Case) —— 对应 N 叉树的叶子节点
    // ==========================================
    // 比如：要求组合长度必须是 k，或者路径总和正好等于 target
    if (path.size() == k) {
        // 【天坑警报 / 面试必讲】：
        // 绝对不能直接 res.add(path)！
        // 因为 path 贯穿全局，始终是同一个内存引用。如果不做深拷贝，后续的回溯撤销操作会把 path 清空，
        // 导致最后 res 里面存的全是空列表。必须 new 一个新集合进行快照定格！
        res.add(new ArrayList<>(path)); 
        return; 
    }

    // ==========================================
    // 2. 遍历当前层的所有选项 —— 对应 N 叉树的横向宽度
    // ==========================================
    for (int i = startIndex; i < nums.length; i++) {
        
        // 【高阶加分项：剪枝 Pruning】
        // 如果当前选项不合法，或者发现就算把后面的元素全选上也凑不够 k 个了，直接跳过，停止无效搜索。
        if (不合法条件) continue; 

        // ==========================================
        // 3. 做选择 (Make Choice) —— 踏出当前这一步
        // ==========================================
        // 把当前元素加入路径，更新当前的追踪状态
        path.add(nums[i]);
        
        // ==========================================
        // 4. 递归下探 (Recurse) —— 对应 N 叉树的纵向深入
        // ==========================================
        // 进入下一层决策树。
        // 关键点：如果是组合问题，下一层只能从 i + 1 开始选（不能重复选自己）；
        // 如果是允许重复选取同一个元素的问题（如硬币找零），这里传 i。
        backtrack(nums, i + 1);
        
        // ==========================================
        // 5. 撤销选择 (Undo Choice) —— 回溯的核心灵魂：恢复现场
        // ==========================================
        // 刚才的递归函数弹栈了，说明包含 nums[i] 的所有可能性都已经探索完毕。
        // 现在必须把 nums[i] 从路径中踢出去，把位置腾出来，让 for 循环进入下一次循环，去尝试下一个兄弟节点！
        path.remove(path.size() - 1);
    }
}
```

```java
// 传入棋盘本身即可，棋盘就是我们的 path 和 res
public boolean solveSudoku(char[][] board) {
    // 遍历棋盘的每一个格子（相当于寻找需要做选择的位置）
    for (int i = 0; i < 9; i++) {
        for (int j = 0; j < 9; j++) {
            // 如果已经有数字，跳过
            if (board[i][j] != '.') continue;
            
            // 找到一个空格了！开始尝试 1-9（横向遍历宽度）
            for (char k = '1'; k <= '9'; k++) {
                // 1. 剪枝：校验当前行、列、3x3九宫格内是否合法
                if (isValid(board, i, j, k)) {
                    // 2. 做选择：填入数字
                    board[i][j] = k;
                    
                    // 3. 递归下探：基于现在的棋盘，继续去填下一个空格
                    // 【关键点】：如果下一层返回 true，说明整盘解出来了，一路向上返回 true！
                    if (solveSudoku(board)) {
                        return true; 
                    }
                    
                    // 4. 撤销选择（回溯核心）：如果下一层没解出来返回了 false，说明当前这个 k 填错了
                    // 恢复成空格，让 for 循环去试下一个数字
                    board[i][j] = '.';
                }
            }
            // 【终极剪枝】：1-9 都试过了，都不行。说明前面的格子填错了，直接返回 false，让前面的格子去回溯！
            return false; 
        }
    }
    // 【终止条件】：两个大 for 循环都跑完了，没有碰到 '.'，说明全填满了，触发终点拦截返回 true！
    return true; 
}
```
