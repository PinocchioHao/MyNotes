## 二、 面试官的核心连环问与你想知道的满分回答

面对面试官的层层递进，你需要掌握以下核心架构知识点，才能在脱离“老旧业务”时依然有话可说。

### 1. 消费端落库失败，如何保证消息不丢？（手动 ACK 机制）

当面试官切断了你的所有退路（没有防腐层、数据库瞬间挂掉），他想听到的唯一答案是 **MQ 的手动确认（Manual ACK）机制**。

**满分回答：**

> “只要我们是作为消费者，底层一定会关闭 MQ 的自动 ACK（Auto-Ack），改为**手动 ACK**。只有当我们的业务逻辑执行成功，并且**成功落入本地数据库**后，代码才会向 MQ Server 发送 ACK 确认。如果在落库瞬间数据库宕机导致抛出异常，此时不发送 ACK（或发送 NACK）。MQ 会认为这条消息未被成功消费，它会保留在队列中或者重新投递，这样就从物理机制上绝对保证了消息不丢。”
> 

### 2. 如何处理收到两条相同的消息？（幂等性设计）

面试官问重复消费，就是在考分布式系统中最核心的**幂等性（Idempotent）**。

**满分回答：**

> “网络重传必然会导致重复消费，所以消费者必须做**幂等性设计**。最常规的做法是基于数据库的唯一索引去重：
> 1. 上游发消息时，必须带上一个全局唯一的业务流水号（如 Ticket_ID）。
> 2. 我们消费时，在本地落一张**消费去重表（幂等表）**，以这个流水号作为主键或唯一索引。
> 3. 如果收到重复消息，第二次落表时会触发 `DuplicateKeyException` 冲突。我们捕获这个异常，直接向 MQ 返回 ACK（告诉 MQ 这条消息我处理过了，别再发了），但业务层面不做任何重复处理。”
>     

### 3. 死信队列（DLQ）到底什么时候用？

面试官在 `27:08` 纠正了你的说法，问你丢入死信的触发机制是什么。

**满分回答：**

> “死信队列不是用来处理重复消息的，它是处理异常消息的‘垃圾桶’。进入 DLQ 通常有三种场景：
> 
> 1. **主动拒绝**：消费端遇到无法解析的脏数据，主动调用 `NACK/Reject`，且设置不重新入队（`requeue=false`）。
>     
> 2. **重试超限**：消息处理失败触发重试，当重试次数（如 3 次或 5 次）达到上限后，MQ 自动将其路由到 DLQ。
>     
> 3. **消息过期（TTL）**：消息在队列里存活时间超过了设定的阈值还没被消费掉。”


### 4. 串行改并行与系统健壮性演进

面试官在最后一段指出：既然“风控”和“征信”没有强依赖，为什么要串行？遇到抖动为什么直接失败？这其实是一道非常好的**架构优化题**。

**满分回答：**

> “您指出的确实是我们老系统的一个痛点。既然风控和征信没有严格先后顺序，**优化方案应该将其改为并行调用**。我们可以利用 Java 的 `CompletableFuture` 或多线程池，同时发起两个 HTTP 请求，以最慢的那个接口时间为准，大幅降低整体 RT（响应时间）。
> 
> 针对网络偶尔抖动导致的失败，直接放弃确实不够健壮。更好的做法是在调用下游 RPC/HTTP 接口时，引入类似 **Resilience4j 或 Spring Retry** 这样的容错组件。对于 `TimeoutException` 这类瞬态异常，配置 2-3 次的指数退避重试；如果依然失败，再执行降级策略（打 Tag 落库），这样既不会‘得不偿失’，又提升了系统的自愈能力。”
> 

**给你的面试策略建议：** 如果在之后的面试中，再遇到基于老旧单体系统展开的提问，**不要过度为老系统“辩护”**。大胆承认老系统的历史局限性（“当时是这么设计的”可以作为背景介绍），然后迅速把话题引向“如果用现在的眼光来重构，我会怎么做”。这不仅能化解尴尬，还能向面试官展现你的成长和架构视野。

### 二、 核心问题拆解、面试官意图与知识点

#### 1. 异步任务的结果聚合（Fork-Join 模式）

- **提取问题**：风控和征信两个任务并行跑，如何确保两个结果都拿到了，主线程才继续往下走完成订单？
    
- **面试官意图**：考察 Java JUC 并发编程的实战能力，特别是线程协同机制。

#### 2. 分布式请求路由与负载均衡

# 星展银行 (DBS) 技术面试全景复盘 (附高分话术重构)

**面试官风格画像 (Wesley)：** 他是一位非常典型的外企 Tech Lead。他不关心你背了多少八股文理论，他习惯用连环追问的方式，把你逼到“系统出故障、网络断掉、数据库宕机”的极端角落（Edge Cases），看你如何利用架构思维自救。

## 模块一：系统架构与数据流 (System Architecture & Data Flow)

### Q1. 从系统设计上来讲，你是怎样设计这个核心系统的？ (10:47)

- **面试官意图：** 考察你的全局架构视野，看你能不能清晰地划分系统边界、上下游依赖。
    
- **高分回答策略：** “我们的商业汇票系统是一个标准的分布式架构。**对外**，我们通过内部的一个防腐层（Gateway）与国家票交所打交道，核心通信方式是基于 MQ 的异步报文；**对内**，我们作为核心交易枢纽，下游依赖行内的风控系统、征信系统，主要通过 HTTP/RPC 进行同步调用。系统内部采用经典的 Spring Boot 单体/微服务架构，按业务模块进行了严格的分层设计。”
    

### Q2. 交易的起始点在哪里？数据流是怎样的？ (12:43)

- **面试官意图：** 确认你是否真的懂业务的生命周期。
    
- **高分回答策略：** “双向触发机制。**第一类是我们行内主动发起**，比如企业客户来网点开票，我们落库组装报文，发给票交所；**第二类是票交所被动推送**，比如票据到期日的清算报文，我们收到后触发内部的打款和记账流程。”
    

### Q3. 防腐层是什么意思？它是如何工作的？ (14:12 / 15:27)

- **面试官意图：** 听到新名词，测试你是不是在乱用概念。
    
- **高分回答策略：** “防腐层（Anti-Corruption Layer）相当于一个网关和隔离带。票交所的报文格式非常复杂且有加解密要求。防腐层的作用就是把外部的报文统一转换成我们核心系统能直接理解的内部模型（明文 JSON/对象），这样外部接口的变更就不会污染到我们核心交易链路的代码。”
    

## 模块二：消息队列与极端一致性 (MQ & Consistency) - 核心丢分区

这是本次面试的最深水区，面试官在这里挖了至少 7 个连环坑。

### Q4. 给 MQ 发消息，怎么确定对方确实收到了？ (17:21)

- **面试官意图：** 考察 MQ 的可靠投递机制（Producer 端的 Confirm 机制）。
    
- **高分回答策略：** “我们依赖 MQ 底层的 ACK 机制。在代码层面，我们会开启生产者的 Confirm 模式。只有当 MQ Broker 成功将消息持久化到磁盘后，才会给应用端返回一个成功的 ACK；如果超时或者返回 NACK，我们的系统会捕获这个事件进行重试。”
    

### Q5. 什么时候需要补发/补收？怎么判断网络抖动？是手动还是自动？ (18:22 / 20:46)

- **面试官意图：** 考察系统的容错兜底机制。
    
- **高分回答策略：** “我们结合了**自动与手动**两套机制。
    
    1. **自动补偿（应对短时网络抖动）**：我们会有一个定时任务（Job），每隔 5 分钟去扫描『本地报文日志表』中状态为『发送中』但超过一定时间未收到回执的消息，自动触发重新投递。
        
    2. **手动补偿（应对业务异常）**：如果票交所因为业务原因（比如报文某些字段不合规）明确拒绝（Reject）了我们的交易，这就不是系统故障了，我们会将状态置为『人工干预』，由业务员在前端页面核对数据后，手动点击重发。”
        

### Q6. 如果刚收到消息，还没来得及落库，数据库就报错挂了，怎么补收？ (22:53 / 25:57)

- _你的原回答：可以通过防腐层再补发... (显得很被动)_
    
- **面试官意图：** 考察 MQ 消费者的 ACK 机制与本地事务的结合。
    
- **高分回答策略：** “这里我们利用了 MQ 的**手动 ACK 机制**。收到消息时，我们不会立刻告诉 MQ 我们消费成功了。我们会先开启数据库本地事务进行落库，如果落库失败（抛出异常），事务回滚，同时我们在 catch 块中向 MQ 拒绝消费（或直接不提交 ACK）。这样，这条消息就依然保留在 MQ 服务器上，MQ 会根据策略进行重新投递，绝对不会出现消息丢失的情况。”
    

### Q7. 如果上游重发了，你收到了两条一模一样的消息，怎么处理？ (26:48)

- **面试官意图：** 考察接口幂等性（Idempotency）。
    
- **高分回答策略：** “我们在消费端做了严格的**幂等性控制**。每条报文都有唯一的 `MessageID` 或业务流水号。我们在本地消息表会对这个字段建立『唯一索引』。第一条消息成功落库；第二条消息进来时会触发 `DuplicateKeyException` 异常。我们捕获这个异常，认为这是重复投递，直接向 MQ 返回消费成功（ACK）将其丢弃即可。”
    

### Q8. 什么时候消息会被发到死信队列 (DLQ)？ (26:55)

- **高分回答策略：** “当一条消息因为格式错误或者代码 bug 导致持续消费失败，并且触发了 MQ 的最大重试次数阈值（比如重试了 3 次依然抛出异常）时，为了不阻塞后续消息的消费，MQ 就会自动把这条消息路由到死信队列。开发人员会对死信队列进行监控并人工排查。”
    

## 模块三：并发控制与服务编排 (Concurrency & Robustness)

### Q9. 调下游风控系统，网络断了一分钟，怎么处理异常？会不会回滚整个 Transaction？ (27:43 / 28:36)

- **高分回答策略：** “调用外部风控系统属于 RPC 调用，**绝对不能将其包裹在数据库大事务中**。如果网络断了，我们的 HTTP Client 会触发超时异常。此时不会回滚整个业务链路，而是采用『降级』策略，比如在本地将这笔交易打上『待风控确认』的 Tag，放行主链路，后续再由定时任务或人工旁路补偿。”
    

### Q10. 风控和征信没有严格依赖关系，为什么一定要串行调用？怎样设计更健壮、提效？ (30:20 / 35:03)

- _你的原回答：封到 MQ 里边去... (面试官反驳：MQ 怎么拿最终结果验证？)_
    
- **面试官意图：** 高并发场景下的 IO 并行调用与结果聚合。他想听多线程。
    
- **高分回答策略：** “对于这种没有前后依赖的 IO 密集型调用，**串行是历史遗留问题，我会重构为并行调用**。具体的做法是不使用 MQ，而是直接使用 Java 8 的 **`CompletableFuture`**。 我可以向线程池提交两个异步任务，分别调用风控和征信。然后使用 `CompletableFuture.allOf(riskFuture, creditFuture).join()` 方法等待两者全部完成。这样，原本相加的耗时（比如 1s + 1s = 2s）就被优化成了最大耗时（约 1s），大大提升了系统吞吐量。”
    

### Q11. 如果让你用多线程，怎么保证两个线程结果都拿到后，主线程再往下走？ (36:19)

- **高分回答策略：** “在传统的并发包中，可以使用 **`CountDownLatch`**，初始化设为 2，两个线程执行完分别调用 `countDown()`，主线程调用 `await()` 阻塞等待。但在现代 Java 开发中，使用我刚才提到的 **`CompletableFuture.allOf()`** 是更优雅、支持链式调用的方案。”
    

## 模块四：基础架构与 CI/CD (Infrastructure & DevOps)

### Q12. 服务部署在哪？起了几个实例？请求是怎么轮询到的？有没有服务注册与发现？ (38:21 - 40:05)

- **高分回答策略：** “我们部署在内部私有云上，底层大概率是基于 K8s 或 Docker Swarm 的容器编排。系统是无状态的，起了三个实例。因为我们没有引入类似 Eureka 或 Nacos 这种微服务注册中心，流量主要是通过前端的 Load Balancer (比如 Nginx 或者 F5，或者 K8s 的 Service) 进行简单的轮询 (Round-Robin) 分发到这三个实例上。”
    

### Q13. 讲一下整个 CI/CD Pipeline，在哪里 Monitor？ (40:20)

### Q15. 表 (student_name, subject, score)，求每名学生所学各科成绩里面最高分数。写出完整的 SQL。 (44:20)

- _你的原回答：select max ... in ... where name ... group by (逻辑混乱，未完成)_
    
- **面试官意图：** 测试最基础的分组聚合 (GROUP BY + MAX) 的肌肉记忆。
    
- **标准正确写法 (务必背诵)：**
    
    ```
    SELECT 
        student_name, 
        MAX(score) AS highest_score
    FROM 
        student_scores 
    GROUP BY 
        student_name;
    ```
    
- **讲解话术：** “因为要求『每名学生』的最高分，所以必须以 `student_name` 作为聚合维度，使用 `GROUP BY student_name`。然后在 `SELECT` 中使用 `MAX(score)` 函数提取每组中的最大值即可。”
