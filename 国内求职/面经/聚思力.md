### 对大量存储过程的看法
> “我对 ERP 系统中存在大量存储过程这件事是非常理解的。因为早年为了处理复杂的供应链批处理和月底结账，减少网络 I/O，存储过程确实是最高效的方案。
> 
> 如果我入职，面对这些历史遗留的存储过程，我的处理原则是‘敬畏历史，稳妥演进’。具体会分三种情况来处理：
> 
> **第一：增量业务，坚决上提**。对于所有新接到的业务需求，只要不和老逻辑强耦合，我会在 Java 应用层（Spring Boot）用现代化的代码规范去实现，不再往存储过程里加新逻辑，控制住技术债务的源头。
> 
> **第二：存量老业务（能跑但不慢的），保持隔离**。对于那些几十上百个关联表、目前运行稳定且没有严重性能瓶颈的老存储过程，把它当成一个黑盒 API 去调用，不盲目为了‘代码整洁’去重构它，保证业务的绝对稳定。
> 
> **第三：核心性能瓶颈的重构（逐步拆解）。** 如果某个几千行的存储过程已经严重卡顿，必须优化或迁移到 Java 层，我绝对不会直接改代码，而是会严格走这几步重构流程：
> 
> 1. **先写测试：** 根据业务梳理出这个存储过程的入参和出参，在 Java 里写好厚厚的单元测试和数据比对脚本，兜住底线。
>     
> 2. **在 Java 层翻译逻辑：** 用 MyBatis 等现代框架把逻辑拆解到应用层。
>     
> 3. **双写/影子运行（Shadowing）：** 上线后，让老存储过程和新 Java 代码同时跑一段时间，每天在后台比对两边的计算结果是否 100% 一致。
>     
> 4. **无缝切换：** 等跑了一两个账期，数据完全无误后，再切断对老存储过程的调用。”

### 老旧 ERP 数据库还有哪些典型的“潜在问题”？（面试加分项）

除了多表 JOIN，如果你能主动指出以下三个 ERP 系统的通病及解决思路，面试官会立刻觉得你是一个“填过深坑”的老兵：

**1. 历史数据极度膨胀（大表问题）**

- **痛点：** ERP 系统用了十年，订单表里积压了上亿条数据，但实际上业务人员平时只看最近半年的订单。数据量过大导致任何 B+ 树索引的层级变深，增删改查全面变慢。
    
- **解决思路：冷热数据分离（数据归档）。** 定期（如按年）将一年前的已结案订单数据迁移到归档历史表（Archive Tables）中。业务库的活跃表始终保持在合理的量级。
    

**2. 大事务与死锁频发（长事务问题）**

- **痛点：** ERP 的一个核心业务动作（比如“订单发货”）可能需要同时更新库存、写财务流水、改订单状态、发通知。老系统喜欢把这一切塞进一个巨大的 `@Transactional` 甚至一个存储过程里。事务执行时间极长，长时间持有行锁，极易引发死锁（Deadlock）和数据库连接池耗尽。
    
- **解决思路：缩短事务边界。** 将非核心的、允许异步操作的步骤（如发邮件、记录操作日志）剥离出核心事务，通过消息队列（MQ）或 Spring 的异步事件（`@Async`）解耦。保证核心数据库事务“快进快出”。此外，在代码规范上，要求所有业务模块按相同的顺序去更新表，避免交叉等待引发死锁。
    

**3. 字段无休止增加的“上帝表”（God Table）**

- **痛点：** 比如 `User` 表或 `Product` 表，随着十年来的业务迭代，被硬生生加到了上百个字段（甚至存在 `reserve_field_1` 这种备用字段）。这会导致行数据过宽，数据库单个数据页（Page）能装下的行数锐减，导致大量的跨页查询和内存浪费。
    
- **解决思路：垂直拆分。** 根据业务领域，把一张大表拆成“主表 + 扩展表”。将最常用的基础信息留在主表，将低频访问的扩展信息（如冗长的描述文本、复杂的规格参数）拆分到子表，甚至迁移到 MongoDB/Elasticsearch 这种非关系型数据库中处理。
