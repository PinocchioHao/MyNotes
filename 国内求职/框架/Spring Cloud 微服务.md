在我之前的项目中，因为系统架构搭建得比较早，当时前辈们选型使用的是传统的 Eureka + Hystrix 体系。我主要在这个既定框架下负责业务服务的拆分与开发。

但我深知 Netflix OSS 这套组件已经停止维护，所以在后来的技术沉淀中，我重点研究并升级到了 Spring Cloud Alibaba 体系。相比以前我们用的 Eureka 和 Hystrix，我发现 Nacos 的 AP/CP 切换机制更灵活，而 Sentinel 基于滑动时间窗口的轻量级限流，比 Hystrix 的线程池隔离节省了极大的系统开销。

虽然以前是在老架构上开发，但服务拆分、接口幂等性设计、分布式调用的超时重试机制，这些微服务落地的核心痛点和经验，在新架构下是完全互通的。



### 新老微服务组件对照表 

|**微服务痛点**|**传统 Spring Cloud (已过时/停更)**|**现代微服务架构 (目前面试绝对主流)**|**核心优势对比**|
|---|---|---|---|
|**注册中心**|Eureka|**Nacos**|Eureka 只支持 AP 模式且停更；Nacos 支持 CP/AP 动态切换，且自带控制台界面。|
|**配置中心**|Spring Cloud Config|**Nacos**|以前的 Config 还需要依赖 Git 和消息总线（Bus）才能刷新，极度繁琐；Nacos 天然将注册和配置中心合二为一，原生支持秒级热更新。|
|**熔断限流**|Hystrix|**Sentinel**|Hystrix 基于线程池隔离，极其消耗资源且不支持动态修改规则；Sentinel 基于信号量隔离，轻量级，自带强大的可视化面板，且规则可以动态热生效。|
|**API 网关**|Zuul 1.x|**Spring Cloud Gateway**|Zuul 是同步阻塞架构，高并发性能极差；Gateway 是 Spring 官方基于 Netty 开发的异步非阻塞网关，性能碾压。|
|**分布式事务**|无官方标准解法|**Seata**|以前要么手写 TCC，要么用复杂的 MQ；现在 Seata 提供了开箱即用的 AT 模式，零侵入解决微服务数据一致性。|
|**远程调用**|Ribbon + Feign|**LoadBalancer + OpenFeign**|Ribbon 已死，Spring 官方推出了更轻量的 LoadBalancer 替代。|


### 1. 服务通信与负载均衡 (OpenFeign)

既然拆分了微服务，原本本地的方法调用就变成了跨网络调用（HTTP/RPC）。

- **面试考点：OpenFeign 是怎么工作的？**
    
    - **实战回答：** “我们在代码里只写了一个接口并打上 `@FeignClient` 注解。底层是 Spring 在启动时为这个接口生成了动态代理。当业务调用这个接口方法时，代理对象会根据注解里的服务名，去注册中心拉取对方的 IP 列表，然后结合负载均衡算法选出一个机器，最后发起真正的 HTTP 请求。”
        
- **高频踩坑 (亮点)：超时与重试怎么配置？**
    
    - 微服务调用最怕**超时卡死**。你需要知道，Feign 底层依赖 Ribbon（或 Spring Cloud LoadBalancer），必须要合理配置 `ConnectTimeout`（连接超时）和 `ReadTimeout`（读取超时）。
        
    - **慎用重试机制：** 在金融或交易系统中，如果接口没有做**幂等性**设计，绝对不能盲目开启重试。否则超时重试会导致下游系统发生两次扣款。
        

### 2. 服务注册与配置中心 (Nacos)

这是微服务运转的通讯录和控制台。

- **面试考点：配置中心是怎么实现热更新的？**
    
    - **实战回答：** “我们在需要热更新的 Bean 上加上 `@RefreshScope` 注解。当我们在 Nacos 后台修改了配置，Nacos 服务端会通过长轮询机制通知到我们的微服务节点，Spring 容器会销毁旧的 Bean，并在下次请求进来时，读取最新配置重新实例化一个 Bean，从而实现不重启就生效。”
        
- **高可用考点：Nacos 挂了，微服务还能互相调用吗？**
    
    - **实战回答：** “能调用。微服务并不是每次请求都去问 Nacos，而是会在本地缓存一份服务提供者的实例列表。就算 Nacos 宕机了，服务之间依然可以依靠本地缓存正常通信，只是这期间如果有新的服务上线或者宕机，其他节点感知不到了。”
        

### 3. 熔断降级与限流 (Sentinel)

这是微服务架构里的“保险丝”，没有它，一个慢节点会拖死整个集群（雪崩效应）。

- **面试考点：熔断和降级有什么区别？**
    
    - **实战回答：** “**熔断**是被动的防御。比如调用下游的票据核验接口，如果它突然因为慢查询导致大量超时，为了防止把我这边的线程池耗尽，Sentinel 会触发熔断，直接切断对下游的调用，快速返回错误。**降级**是我们的应对策略（Fallback），熔断之后，我们在代码里提供一个兜底方案，比如返回一个默认的缓存结果，或者提示‘当前办理人数过多，请稍后再试’，保证主流程不报错死机。”
        
- **面试考点：怎么防刷和限流？**
    
    - 在网关层或业务入口用 Sentinel 配置 QPS 限流规则。可以讲讲 Sentinel 底层使用的是**滑动时间窗口**算法来精准统计请求量。
        

### 4. 分布式事务 (Seata 或 MQ 最终一致性)

这是微服务拆分后最大的痛点，也是面试必考的压轴题。以前在一个库里，加个 `@Transactional` 就搞定了，现在跨了多个数据库，怎么保证同时成功或失败？

- **面试考点：微服务之间怎么保证数据一致性？**
    
    - **实战方案 A (强一致性 - Seata AT 模式)：** “业务零侵入，直接加 `@GlobalTransactional`。底层是 Seata 帮我们拦截 SQL，生成前后镜像存在 Undo Log 里。如果有一环失败，Seata TC 服务端会通知所有分支事务，利用 Undo Log 自动反向补偿回滚。（缺点：持有了全局锁，高并发性能一般）。”
        
    - **实战方案 B (最终一致性 - MQ 事务消息)：** “在对并发要求极高的核心链路，我们通常放弃强一致性。采用 RocketMQ 的事务消息机制。上游完成本地事务后发送半消息，下游订阅消息慢慢消费，如果下游消费失败就不断重试，或者记录死信队列人工介入，保证**最终一致性**。”
