### 1. MyBatis vs JPA/Hibernate (选型与本质对比)

- **JPA/Hibernate (全自动 ORM)：**
    
    - **核心优势：** 高度抽象，真正的面向对象编程（领域驱动），开发 CRUD 极快，自带完善的级联保存/删除，跨数据库移植性强。
        
    - **致命劣势：** 学习曲线极其陡峭，黑盒运行。对于包含十几张表关联的复杂金融报表查询，生成的 SQL 极难阅读和优化。
        
- **MyBatis (半自动 ORM)：**
    
    - **核心优势：** SQL 完全由开发者掌控，DBA 极度友好，排查慢查询非常方便，学习门槛低。
        
    - **致命劣势：** 编写大量重复的基础 SQL（需配合 MyBatis-Plus 弥补），强依赖具体的数据库方言（比如 MySQL 的特定内置函数）。
        

### 2. JPA 性能杀手：N+1 问题与懒加载机制 (极高频)

面试官如果考 JPA，几乎必考 N+1 性能故障。

- **实战场景：** 假设查询包含 10 个患者 (`Patient`)，每个患者有关联的病历 (`Record`)。
    
- **N+1 灾难：** 如果直接遍历这 10 个患者并调用 `patient.getRecords()`，JPA 默认会先发 1 条 SQL 查出 10 个患者，然后再额外发送 10 条 SQL 去查各自的病历。总共执行了 1+10=11 条 SQL。如果是在微服务高并发场景下，这种操作会瞬间把数据库连接池打满。
    
- **实战解法：** 面试时一定要答出：使用 **Fetch Join (`JOIN FETCH`)** 在一条 SQL 中把关联数据一并查出，或者使用 `@EntityGraph` 动态指定抓取策略，彻底从根源消灭 N+1。
    

### 3. MyBatis 的缓存机制与分布式踩坑

- **一级缓存 (SqlSession 级别)：** 默认开启。在同一个事务内，执行相同的 SQL，第二次会直接从内存拿。**坑点：** 如果中途有 `update` 操作，一级缓存会立刻失效清空。
    
- **面试暴击题：微服务/多实例架构下，为什么严禁开启 MyBatis 二级缓存（Mapper 级别）？**
    
    - **高分话术：** “二级缓存是单机本地缓存。在多实例部署（如 8 个节点）的分布式环境下，如果节点 A 更新了表数据，它只会清空 A 自己的二级缓存，节点 B 根本不知道，B 还会继续读到旧的脏数据。所以我们在微服务中通常**全局关闭 MyBatis 的二级缓存**，将缓存功能统一交给外置的分布式中间件（如 Redis）来管控，保证数据最终一致性。”
        

### 4. MyBatis-Plus 的应用边界 (体现架构意识)

既然国内大家都在用 MyBatis-Plus (MP)，面试中你可以主动谈谈它的使用规范，展现 Clean Code 和架构边界意识。

- **高分话术：** “MP 极大地简化了单表的 CRUD 操作，消灭了大量重复代码。但在处理复杂的深度分页、多表 Join、以及涉及悲观锁/乐观锁的高危核心交易 SQL 时，我们依然坚持**手写原生的 MyBatis XML**，确保 SQL 的执行计划完全可控，避免 MP 动态拼装引发的慢查询。”


#### 1. # 和 $ 的区别

-  `#` 是预编译，防注入；`$` 是字符串替换。表名作参数、order by + 字段等场景用 `$`。
    
- **高级连环问：** “表名作为参数时，一定要用`$`，除了表名，还有什么场景必须用 `$`，因为用`#`会加个单引号，导致语法失效；用 `$` 的场景需要用严格的白名单校验字段来防注入。


#### 2. PageHelper 的致命踩坑（OOM 与数据串号）

- **你的笔记：** 底层是拦截器，拼 `limit`，数据保存在 ThreadLocal 实现隔离。
    
- **高级连环问：** “PageHelper 在生产环境发生过什么故障？”
    
- **实战话术提升：** “PageHelper 极其容易引发 **ThreadLocal 内存泄漏和数据串号** 故障。如果我们调用了 `PageHelper.startPage()`，但紧接着的业务代码里发生异常，或者因为 `if-else` 分支**没有去执行真正的 MyBatis 查询操作**，那么存放在 ThreadLocal 里的分页参数就永远不会被清除。 当这个线程被线程池复用去处理下一个用户的请求时，下个用户本想查全量数据，结果莫名其妙被加上了 `limit`。**解法：** 必须保证 `startPage` 和真正的 Mapper 查询紧紧挨着写，或者在 `finally` 块里手动调用 `PageHelper.clearPage()`。”
    

#### 3. MyBatis 二级缓存 (分布式环境禁用，会存在数据一致性问题)

- **你的笔记：** 存在数据一致性问题，可以自己写 Redis 插件。
    
- **实战话术提升：** 面试时态度要坚决。“在微服务架构或多实例部署下，我们**全局强制关闭 MyBatis 的二级缓存**。因为它的作用域是单台机器的 namespace，A 机器更新了数据清空自己的缓存，B 机器完全感知不到，一定会读到脏数据。我们会把缓存机制完全上移到业务层，统一使用 Redis（配合 Spring Cache 或 Redisson）来做分布式缓存。”
    

#### 4. 为什么只写接口就能执行 SQL？(动态代理底层)

- **你的笔记：** MapperProxy 动态代理，把方法调用转成 SqlSession 操作。
    
- **实战话术提升：** 这块你总结得非常完美！面试时可以直接用一句话概括精髓：“底层利用了 JDK 动态代理，当我们注入 Mapper 接口时，Spring 容器里实际拿到的是一个 `MapperProxy` 代理对象。每次调用方法，代理逻辑会通过**接口全限定名 + 方法名**作为 Key，去大 Map（Configuration）里找到对应的 `MappedStatement` 也就是具体的 SQL 节点，然后交给 `Executor` 去执行。”
