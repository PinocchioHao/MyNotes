### CPU占用高、OOM
**开场白（化解没有经验的尴尬，展现规范性）：**

> “其实在我们的票据核心系统里，因为业务请求链路相对可控，且上线前有压测，线上极少出现真实的 OOM。但我们在演练和日常排查中，团队有一套标准的 SOP 流程。”

**话术 A：排查 CPU 100%（展现 Linux 肌肉记忆）**

思路：
`[找到高占用进程] -> [定位高占用线程] -> [16进制转换] -> [定位具体代码行]`

> “如果是报警提示 CPU 飙升，我一般会按四步走，直接抓到具体的代码行号： 第一步，先用 `top` 找出 CPU 占用最高的 Java 进程 PID。 第二步，用 `top -Hp <PID>` 进去看这个进程里的线程，找到占用最高的那个线程 TID。 第三步，这也是排查最关键的一步，必须用 `printf "%x\n"` 把这个十进制的线程号**转成十六进制**。 第四步，用 `jstack <PID> | grep -A 20 <十六进制TID>`，直接把这段堆栈打出来。
> 
> 根据打出来的日志，通常分两种情况：如果定位到的是我们自己的业务类，那基本就是写了死循环或者复杂的正则回溯；但**在实际场景中，非常大概率我看到的是 `VM Thread`（垃圾回收线程）**。这就意味着 CPU 飙升其实是内存不够导致的频繁 Full GC，这时候我就会立刻切换到 OOM 的排查思路上。”

**神器替代方案：** 如果线上安装了 **Arthas**，直接输入 `thread -n 3`，就能一步列出 CPU 占用最高的前 3 个线程及其堆栈。

**话术 B：排查 OOM（主要是对堆快照进行分析）**

2. **在线观察（不中断服务）：**  
    - 使用 `jstat -gcutil <PID> 1000` 实时观察各区域（Eden、Survivor、Old、Metaspace）的内存使用率和 GC 次数。如果老年代（O区）使用率居高不下且在 Minor GC 后无法释放，说明存在内存泄漏。

> “排查 OOM，核心原则是**先保现场，后做分析**。
> 
> 在发生 OOM 瞬间，最可靠的是依赖启动参数配置的 `-XX:+HeapDumpOnOutOfMemoryError` 自动导出的 `.hprof` 堆快照文件。当然，如果是刚才那种 CPU 飙升、系统假死但还没崩的情况，我会先用 `jstat` 观察一下 Full GC 的频率，确认是内存问题后，手动用 `jmap -dump` 把快照拉下来。
> 
> 拿到 Dump 文件后，我会把它拖到本地用 MAT (Memory Analyzer) 分析。我通常会看三个点：
> 
> 1. 先看 **Histogram（直方图）**，按类名排个序，看是不是有某个对象实例数异常飙升，比如几百万个 String 或者 User 对象。-- 找**数量异常**
>     
> 2. 再看 **Dominator Tree（支配树）**，看哪块内存占据了绝对比例。 -- 找**体积异常**
>     
> 3. 找到大对象后，最关键的是右键执行 **Path to GC Roots**。
>     
> 
> 顺着GC Roots引用链往上追溯，够看到**是哪个具体的类和变量名死死抓住了这些大对象**，基本就能定性是**溢出**还是**泄漏**了。如果是被 `ThreadLocal` 或者没关闭的数据库连接池死死拽着，那就是内存泄漏，要去改代码；如果是千万级报表导出未分页导致瞬间塞满，那就是内存溢出，可以考虑**从业务架构上重构**：将同步导出改为异步任务，后台使用 EasyExcel 一条条流式写入生成文件，完成后上传，最后发通知让用户去下载中心提取，彻底斩断 OOM 的风险。”


相关命令使用链：
- **`top` (系统级监控)：** 收到 CPU 报警时的第一抓手。用 `top` 找异常进程，用 `top -Hp <PID>` 找异常线程。
    
- **`jstat` (GC 状态监控)：** 当系统响应极慢但尚未崩溃时使用。通过 `jstat -gcutil <PID> 1000` 每秒刷新，重点观察 `FGC`（Full GC 次数）和 `FGCT`（耗时）。如果数据疯狂上涨，说明系统正在经历 GC 风暴。
    
- **`jstack` (线程堆栈分析)：** 配合 `top` 定位到的十六进制线程 TID，打印此时 Java 进程的线程快照，用于精准定位死循环、死锁或疯狂运转的 GC 线程。
    
- **`jmap` (内存快照导出)：** 在系统假死、频繁 Full GC 但还没彻底 OOM 时，通过 `jmap -dump:format=b,file=heap.hprof <PID>` 手动把当前内存状态导出来。
    
- **启动参数 (自动现场保留)：** 生产环境必须配置 `-XX:+HeapDumpOnOutOfMemoryError`，确保系统真正 OOM 崩溃时，能自动留下一份 `.hprof` 现场文件。


### 4. 大查询（庞大的 IN）的标准解法：
遇到巨量 IN 查询，我通常会从代码、SQL、架构三个维度进行递进式改造：

1. **代码层（分批查询 Chunking）：** 当 IN 的参数达到数千个时，会引发 MySQL 优化器 AST 解析飙升，且突破 `index_dive_limit` 导致选错索引。我们会使用 `Lists.partition` 将大 List 切分成比如 500 一批，多次查询后在 Java 内存里组合。利用“小步快跑”防止长时间占用连接导致假死。
    
2. **SQL 层（JOIN / EXISTS 替代）：** 如果 IN 的数据来源于另一张表子查询，我会改写为 JOIN。利用 MySQL 优化器的“小表驱动大表”机制提升效率。**（话锋一转）** 但考虑到微服务拆分和跨库问题，大规模的 JOIN 极易触碰架构红线，所以我尽量不在大表中滥用 JOIN。
    
3. **架构层（业务整改 + 灰度/蓝绿）：** 这是终极解法。对于数万级别的查询或导出，我会推翻现有设计，要求产品改为强制分页；或者将只读类的大查询数据通过 Binlog 同步至 Elasticsearch/ClickHouse 中，实现 OLTP 与 OLAP 物理隔离。在上线时，通过配置中心引入灰度开关，先切 5% 流量验证新架构，确保平滑过渡无事故。或使用蓝绿发布，业务整改后运行几个版本没问题再切换。



## 高频面试点 系统中实现的一些功能

### 1. 千万级数据导出 (防 OOM 与架构优化)

面试官问这个问题，绝对不是让你回答 `SELECT *` 然后用 Apache POI 写 Excel。他们想听的是**内存控制**和**异步架构**。

- **内存防爆 (OOM 杀手)：** 千万级数据全部加载进 JVM 会直接宕机。
    
    - **流式查询：** 放弃传统的 `List<User>` 接收。在 MyBatis 中使用 `ResultHandler`（游标读取），或者在 JDBC URL 加上 `fetchSize=Integer.MIN_VALUE`，让 MySQL 一条一条地把数据推给服务器，而不是把结果集全塞进内存。
        
    - **规避深分页：** 如果分批拉取，千万别用 `LIMIT 1000000, 1000`（MySQL 会扫描 100万行然后丢弃，极慢）。必须依靠游标 ID：`WHERE id > #{last_max_id} LIMIT 1000`。
        
    - **流式写入：** 坚决不用原生的 Apache POI，必须使用阿里的 **EasyExcel**。它底层重写了内存分配机制，写一行丢一行，百万级数据导出内存占用稳定在几十 MB。
        
- **架构解耦 (异步交互)：** 千万级导出动辄几分钟，绝对不能阻塞 HTTP 请求。
    
    - **标准交互流程：** 用户点击“导出” $\rightarrow$ 后端生成一条“导出任务”记录插入 DB，并返回“任务提交成功” $\rightarrow$ 后台线程池或 MQ 消费者接手，开始流式查库写文件 $\rightarrow$ 写完后上传到阿里云 OSS 或私有 MinIO $\rightarrow$ 更新任务状态为“已完成”并附上下载链接 $\rightarrow$ 用户在“任务中心”点击下载。


### 2. XXL-JOB 大批量定时任务 (分片广播)

当你有 100 万个处于“处理中”的单据需要在每天凌晨 2 点跑批处理时，单台机器肯定跑不完。面试必考 XXL-JOB 的**分片广播机制**。

- **核心思想：** 把 100 万条数据均匀分摊给集群里的 10 台机器同时跑。
    
- **实战落地：**
    
    1. 在 XXL-JOB 调度中心将路由策略设置为“分片广播”。
        
    2. 当任务触发时，集群里的 10 台机器都会同时收到调度请求。XXL-JOB 会给每台机器下发两个参数：`shardTotal`（总分片数 10）和 `shardIndex`（当前机器的编号 0~9）。
        
    3. **业务代码适配：** 在代码的查库 SQL 中加入取模逻辑：`SELECT * FROM order WHERE status = 'PENDING' AND MOD(id, #{shardTotal}) = #{shardIndex}`。
        
    4. **收益：** 完美实现了分布式环境下的算力打宽，不仅性能提升 10 倍，还避免了多台机器重复处理同一批数据导致的主键冲突或锁竞争。
        

#### 票据系统采用单机定时任务Quartz vs XXL-JOB

我们系统的日终跑批，比如票据结清和对账，采用的是**调度中心集中触发 + 单机路由执行**的模式，集群里的另外两三台机器纯粹作为高可用**容灾节点**。

随着业务量的增长，我确实观察到一些日终任务的执行时间拉长到了一个多小时，达到了单机处理的瓶颈。从纯技术的角度看，如果引入 XXL-JOB 的分片广播机制，让多台实例协同读库处理，性能可以呈指数级提升。

但结合金融业务的底层逻辑，我认为当时的单机架构是**非常合理的架构折中（Trade-off）**。首先，凌晨的批处理窗口期长达数小时，单机 1 小时的耗时完全在容忍范围内；其次，票据结清涉及严密的资金对账，单机串行（或单机本地线程池）的模式彻底规避了**分布式并发修改带来的死锁和一致性风险**，大大降低了系统的**复杂度**和半夜排障的**运维成本**（出错需要分片查日志）。**在金融核心系统中，我们更愿意用时间换取绝对的数据安全和架构极简。**




### 3. 分库分表策略与实际操作 

面试官问分库分表，重点不是问你 ShardingSphere 的配置怎么配，而是问你“拆分维度的抉择”**和**“不停机平滑迁移方案”。

- **什么时候分？(先说底线)：** 单表数据量超过 1000 万 ~ 2000 万行，且通过加索引、Redis 缓存、读写分离、历史数据冷热归档都无法解决性能瓶颈时，才考虑分表。分库分表是最后的底牌，因为它会带来跨表分页、跨库事务等极其头疼的后遗症。
    
- **拆分维度 (Sharding Key 的痛点)：**
    
    - 比如电商订单表，按 `user_id` 取模分表（分了 32 张表）。
        
    - **痛点考点：** C 端用户通过 `user_id` 查询自己的订单极快，但 B 端商家想查自己店铺的订单怎么办？商家查询条件里没有 `user_id`，会导致“全路由”（同时扫描 32 张表），数据库直接瘫痪。
        
    - **解法：** 核心交易链路按 `user_id` 分表。然后通过 Canal 监听 MySQL 的 Binlog，把数据实时同步到 **Elasticsearch (ES)** 中。B 端商家或后台运营的复杂多条件组合查询，全部走 ES。
        
- **实战操作：双写平滑迁移方案 (展现架构师底蕴的绝杀回答)** 如果你接手一个老业务，要把老单表迁移到分表架构，怎么做到**不停机迁移**？
    
    1. **增量双写：** 修改业务代码，让所有新的写操作（增删改）同时写入老库和新库（以老库为准，新库写入失败不影响主流程，记日志后续补偿）。
        
    2. **全量存量同步：** 开启一个后台脚本，把老库的存量数据读取出来，按分表规则写入新库。
        
    3. **数据对账：** 写一个对账程序，每天半夜比对老库和新库的数据是否完全一致。
        
    4. **灰度切读：** 对账完全无误后，先把 10% 的读取流量切到新库，观察几天没问题，慢慢切到 100%。
        
    5. **停跑老库：** 读流量全部切走且稳定后，代码里去掉写老库的逻辑，下线老库。完成不停机迁移。

**场景 1：微服务接口幂等性怎么保证？**

- _问题：_ 用户疯狂连点“提交订单”，或者上游系统因为超时触发了重试机制，导致请求发了两次，怎么防止生成两笔订单？
    
- _实战解法：_
    1. **Token 机制 (防连点)：** 进入表单页面前，先向后端申请一个全局唯一的 UUID Token。点击提交时带上该 Token。后端拿到请求先去 Redis 执行 `DEL token`，如果删除成功（返回 1），说明是首次请求，放行；如果删除失败（返回 0），说明 Token 已被消费，直接拒绝。此外前端也可以简要做一下防连点。
        
    2. **唯一索引 (终极兜底)：** 数据库层面用 `业务流水号` 建唯一索引。即便并发突破了 Redis 的防线，数据库底层也会报 `DuplicateKeyException`，捕获异常视为处理成功即可。

#### 题目： “在一个分布式环境下，两个账户之间转账，如何保证 A 扣钱和 B 增钱是一个原子操作？如果 A 扣了钱，由于网络问题 B 的增加请求超时了，你的系统怎么自动恢复？”


**考察重点：**
分布式事务，或者是补偿机制、本地消息表(本地库里专门针对MQ消息的一个表)。


在分布式环境下做账户转账时，我们一般不会采用传统的分布式事务（比如 2PC），因为它性能开销大、系统耦合高、对可用性影响也比较明显。

在银行系统里，更常见的做法是基于最终一致性的设计，比如采用 **Transactional Outbox Pattern（本地消息表模式）**，结合消息队列来实现可靠传递。

具体来说，在 A 账户扣款时，我们会在本地数据库事务中完成两件事情：  
第一是扣减 A 的余额；  
第二是在本地消息表中插入一条转账事件记录。

这两个操作在同一个数据库事务里提交，要么同时成功，要么同时失败，从而保证本地原子性。

事务提交成功后，由后台异步任务将消息表中的数据投递到 MQ。  
B 系统消费该消息后，在自己的本地事务中完成加钱操作。

如果因为网络问题导致 B 系统处理失败，MQ 会自动重试；  
如果多次重试仍然失败，可以通过补偿机制（比如触发冲正交易）将 A 的扣款回滚。


常见的补偿机制：消息的补收补发，定时对账任务，以及人工介入的交易冲正。

### 2. 自动恢复机制：如何处理“超时”？

**题目问：** 如果 B 增加请求超时了，系统怎么自动恢复？

如果 B 系统因为网络问题导致加款请求超时，我们一般会通过三层机制保障恢复：

第一是重试机制。MQ 会自动重试投递，同时在票据系统中我们还支持报文补收和补发机制，确保消息最终可达。

第二是幂等控制。为了防止重复加钱，B 系统会基于交易流水号或消息 ID 做唯一校验，并记录交易处理状态。如果重复收到同一笔交易，只会返回成功而不会重复执行。

第三是对账与补偿机制。如果多次重试仍然失败，系统会将该交易标记为异常，并进入差错处理流程。定时对账任务会比对 A 和 B 的账务状态。确认异常后，由运营人员审批触发冲正交易或补偿操作。

这样既保证了系统自动恢复能力，又符合金融系统对资金安全和风控的要求。

# ✅ 常见变体二：你怎么区分业务异常和系统异常？


> 我们一般把异常分为两类：
> 
> 第一类是业务异常，比如预约时间已占用、余额不足。这类异常是预期内的，会返回明确的业务错误码以及错误信息，可用作业务提示。
> 
> 第二类是系统异常，比如数据库连接失败、空指针、数组越界等异常等。这类异常会统一返回系统错误码，统一包装成内部服务错误，避免暴露内部细节，并记录详细日志。
> 
> 这样可以保证前端能根据业务码精细处理，而系统异常不会泄露内部信息。





#### 分布式任务调度：“如果你的系统 A 部署了 3 个节点（集群），你的定时对账任务如何保证同一时间只有一个节点在跑？如果 3 个节点同时跑，可能会导致重复退款或数据混乱。”

固定节点执行，可引入Redis分布式锁。

**回答：**
在分布式任务调度场景中，常见有两种实现方式：

第一种是**固定指定节点执行**。任务表中会配置 Cron 表达式以及执行节点信息。系统部署多个节点时，每个节点在触发任务前，会先判断当前机器是否为指定执行节点，如果是才执行任务，否则跳过。

我们之前在银行系统中采用的就是这种方案。任务都配置在任务调度表中，包括任务名称、Cron 表达式、执行节点等信息。任务本身被封装成可独立调用的接口，所以如果调度失败，也可以通过后台手动触发执行，作为一种补偿手段。

这种方式实现简单、可控性强，但缺点是存在单点风险——如果指定节点宕机，任务就无法自动执行，需要人工干预或切换节点。

第二种方式是通过分布式锁或集群调度机制实现“抢占执行”。多个节点同时触发任务，但通过 Redis 分布式锁或者 Quartz Cluster 机制，保证同一时间只有一个节点获得执行权。

这种方式不依赖固定机器，具备更好的高可用性和扩展性，尤其适用于现代微服务或容器化部署环境。


**方案对比：**
如果是在更云原生或弹性扩容场景下，我会更倾向于使用分布式锁或者 Quartz Cluster 模式。

如果系统已经基于 Quartz 并且有共享数据库，那么开启 Quartz Cluster 模式（本质也是分布式锁，只是锁的实现从Redis换成了数据库）是一种更自然的选择。

它通过数据库行锁来保证单节点执行，同时具备心跳检测和故障转移能力。

相比自己实现 Redis 分布式锁，Cluster 模式更成熟，维护成本也更低。

但如果系统是微服务架构、容器化部署，并且调度逻辑不依赖数据库，那么 Redis 分布式锁会更加灵活。

## 单点登录SSO
单点登录的核心思想是“一处登录，处处通行”。在底层架构中，它的本质是建立两套会话体系：**全局会话（SSO 中心侧）** 与 **局部会话（子系统侧）**。

### CAS 与 OAuth 2.0 的本质区别

在如今的互联网时代，OAuth 2.0 已经是绝对的主流，而 CAS 更多是老牌国企、高校或银行内部办公系统在用。

它们的底层设计哲学完全不同：

|**对比维度**|**CAS (企业内部 SSO)**|**OAuth 2.0 (互联网开放授权)**|
|---|---|---|
|**核心目的**|**Authentication (身份认证)：** 证明“你是谁”。|**Authorization (授权)：** 允许第三方系统代表你操作某些资源。|
|**典型场景**|公司内部的 OA系统、财务系统、HR 系统之间的免密切换。大家都是“一家人”。|**微信扫码登录**第三方网站、允许第三方网页读取你的 GitHub 头像。双方是“陌生人”。|
|**核心媒介**|**Ticket (票据)：** 用于核实身份的一次性凭证。|**Access Token (访问令牌)：** 带有权限范围 (Scope) 和有效期的钥匙。|

### 面试话术


> “实现单点登录（SSO）主要分为企业内部场景和开放互联网场景。
> 
> 如果是**企业内部子系统**的 SSO，我们通常参考 **CAS 票据模型**。它的核心是通过 SSO 认证中心维护全局会话（TGT），并为不同子系统颁发一次性的服务票据（ST）。子系统拿到 ST 后，通过后端 RPC 向 SSO 中心校验真伪，从而建立局部会话。这种模式安全性极高，且易于实现全局的统一登出（SLO）。
> 
> 但如果是**面向外部互联网**的场景，比如接入微信/支付宝登录，或者微服务架构下的外部网关鉴权，我们会采用基于 **OAuth 2.0 + OIDC (OpenID Connect)** 的方案。它的核心不再是发票据，而是下发带有权限和有效期的 **JWT (JSON Web Token)**。各个微服务拿到 Token 后，利用公钥直接在本地验签放行，省去了频繁回源校验的性能开销，更适合高并发的分布式架构。”

- **如何实现单点登出 (Single Logout, SLO)？** 用户在系统 A 点击登出，系统 A 销毁局部会话，并请求 SSO 中心登出。SSO 销毁全局会话，随后 **SSO 中心主动向所有已注册且颁发过票据的子系统（如系统 B、C）发送注销回调请求**。各个子系统收到回调后，销毁自身的局部会话。
    
- **票据 (ST) 为什么必须由子系统去 SSO 校验，而不是直接信任？** ST 是通过前端 URL 传递的（如 `?ticket=ST-12345`），极易被拦截或伪造。系统 A 必须走后端安全通道去 SSO 校验，且 ST 必须是一次性、极短过期时间（如 10 秒）的。
    
- **JWT 模式 vs Redis 集中式会话？**
    
    - **JWT：** 无状态，SSO 不存 Session，校验通过公钥解密。性能极高，但**致命缺点是无法主动踢人下线**（Token 只能等过期）。
        
    - **Redis：** 将所有子系统的 Session 集中存在 Redis 中。方便管控，适合金融或对权限要求极高的企业级内部系统。


## 短链接设计
短链接就是把冗长的传统 URL 映射为简短的字符串。

**核心优势：**

- **突破长度限制：** 适应短信（70字符限制）、微博等平台的字数约束，极大节省文本空间。
    
- **优化二维码：** 避免长链接生成密集二维码导致的不易识别，短链二维码更清爽，提升秒扫率。
    
- **安全与美观：** 隐藏原始链接中复杂的业务参数与架构特征，优化视觉与用户体验。
    

**映射原理（全局发号器 + Base62）：**

- **摒弃哈希算法：** 严禁使用 MD5 或 Hash 截取，从物理法则上直接杜绝哈希冲突及解决冲突带来的极高成本。
    
- **发号与转换：** 采用分布式 ID 生成器，如 Redis `INCR`（Redis单线程原子操作保证了唯一性，且轻量级，但是可能有宕机丢失风险）、MySQL号段模式（美团Leaf框架，高可用）、雪花算法（位数太长了，实际在这种场景下并不是很适配），为长链接生成唯一的 10 进制整型 ID，随后将其转换为 **62 进制**（`0-9`, `a-z`, `A-Z`），生成极短字符组合。
    

**存储与高并发策略（读多写少架构）：**

- **双层存储：** 在 MySQL 中进行持久化存储建立映射表，同时利用 Redis 拦截海量高并发读请求。
    
- **防缓存穿透：** 针对查询不存在的短链，必须将“空结果”同时写入 Redis 并设置较短的过期时间，防止恶意伪造的大量虚假短链直接击穿缓存打爆 MySQL。


**重定向机制：**
获取到短链接后需要把原来的长连接给浏览器跳转。

|**状态码**|**机制与缓存行为**|**业务适用场景**|
|---|---|---|
|**301 (永久重定向)**|浏览器会**永久缓存**这个映射关系。下次用户再访问该短链，浏览器直接自己跳转长链，根本不会请求短链服务器。|降低服务器压力。但**致命缺点是无法统计点击次数、用户画像等数据**，因为流量直接被浏览器拦截了。|
|**302 (临时重定向)**|浏览器**不缓存**。每次访问短链，都必须先去短链服务器转一圈，再跳转。|**工业界绝对主流。** 虽然增加了短链服务器的负载，但可以完美实现点击追踪、埋点统计、AB 测试和恶意链接动态封禁。|
