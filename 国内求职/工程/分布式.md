## 票据系统的无状态多实例分布式部署架构

### 调用链

**链路 A：客户发起的业务请求（如：企业在网银点击“发起贴现”）**

这是一条**强同步**链路，客户在页面上等着看“提交成功”还是“余额不足”，系统必须立刻给出结果。

- **调用路径：** 客户前端 $\rightarrow$ F5 (负载均衡) $\rightarrow$ 核心系统 (Controller 接收 HTTP/RPC 请求) $\rightarrow$ 校验流水与状态 $\rightarrow$ 开启本地事务 $\rightarrow$ 扣减额度并更新票据状态落库 $\rightarrow$ 提交事务 $\rightarrow$ **同步返回 HTTP 200 给客户**。
    
- _后续异步动作：_ 核心系统在本地事务提交后，组装一条贴现报文发给 MQ，MQ 慢慢把报文推给前置系统，最后由前置系统发给票交所（客户不需要等这一步完成）。
    

**链路 B：票交所发来的报文请求（如：票交所通知“承兑已清算”）**

这是一条**纯异步**链路，属于系统之间的后台数据对齐。

- **调用路径：** 票交所 $\rightarrow$ 报文前置系统 (解密/格式转换) $\rightarrow$ 投递到 MQ $\rightarrow$ 核心系统 (消费者监听 MQ) $\rightarrow$ 校验流水与状态 $\rightarrow$ 更新本地数据库状态 $\rightarrow$ **回复 MQ ACK 结束消费**。
    
- _特点：_ 核心系统绝对不会直接把 HTTP 接口暴露给票交所，中间必须用 MQ 隔离开，用来削峰填谷和防腐。


### 2. “流水号”的本质：解决幂等性（防重）

你提到的流水号（业务流水号 / 报文标识号），是整个金融系统防止重复提交的“定海神针”。它**一定会入库**，而且通常会有一张专门的 `business_flow` (业务流水记录表)，或者直接在主业务表里给流水号加上**唯一索引 (Unique Index)**。

- **它的核心作用不是防并发，而是防重（幂等性）：** 假设客户手抖，或者网络卡顿导致前端发起两次完全一样的贴现请求。这两个请求带有**相同的流水号**，同时打到你的两个不同实例上。 实例 A 和实例 B 同时去数据库 `INSERT` 这条带有唯一流水号的记录。数据库底层会瞬间拦截，只有实例 A 能插入成功并继续往下走；实例 B 会立刻收到数据库抛出的 `DuplicateKeyException`（主键/唯一键冲突）。代码捕获这个异常，直接返回“该笔业务已在处理中”，完美阻断重复请求。


### 3. 状态机 + 乐观锁：解决真正的并发冲突

如果两个请求**流水号不同**，但试图同时操作**同一张票**（比如业务员 A 在申请贴现，业务员 B 却在操作背书转让），流水号防重就失效了。这时候靠什么？

- 正如你所说，靠的是**严格的票据状态流转**。
    
- 这在底层被转化为经典的**数据库乐观锁**。当这两个请求同时校验完状态，准备执行更新时，SQL 会这样写： `UPDATE bill SET status = '已贴现' WHERE bill_id = 123 AND status = '可贴现'`
    
- 由于数据库行锁的存在，谁先执行这条 SQL，谁就能把状态改掉。后执行的那台实例拿到锁时，发现 `status` 已经不是 '可贴现' 了，更新行数为 0，代码直接抛出“票据状态不符，业务办理失败”。

- 针对非核心业务，容忍度比较高，系统没有显示的并发控制。

## 分布式基础常见面试题

### 1. CAP 定理与 Spring Cloud 选型映射

在分布式网络中，由于机房断电、网线被挖断等物理原因，**P（分区容错性）是必须保证的客观前提**。因此，架构师只能在 C（强一致性）和 A（可用性）之间二选一。

- **CP 架构 (宁可报错，绝不给错数据)：**
    
    - _中间件映射：_ Zookeeper、Consul、Nacos (CP 模式)。
        
    - _场景：_ 当 Zookeeper 的主节点挂掉，重新选举 Leader 的那几十秒内，整个注册中心是**拒绝服务**的。这保证了哪怕服务不可用，也绝不会把错误的路由地址推给消费者。金融核心账务的分布式锁通常选 CP。
        
- **AP 架构 (宁可给旧数据，也绝不报错)：**
    
    - _中间件映射：_ Eureka、Nacos (AP 模式，Spring Cloud 默认)。
        
    - _场景：_ Eureka 是对等节点，哪怕挂得只剩一台，它依然会接收请求并返回服务列表（虽然列表里可能包含已经宕机的死节点）。在大多数微服务（如你们的 CACHI 健康平台或电商电商平台）中，我们宁愿容忍短暂的路由错误（配合客户端重试机制），也绝不能接受整个系统瘫痪。
        

### 2. BASE 理论：大厂最真实的落地基调

BASE 理论是对 CAP 中 AP 架构的延伸。它的核心面试话术是：“在绝大多数互联网和金融非核心业务中，追求绝对的强一致性（CP）会拖死整个系统的并发性能，所以我们退而求其次，通过**软状态（Soft State）**，最终达到**最终一致性（Eventual Consistency）**。”

- **面试实战场景套入：** “虽然我们票据系统的主体流转靠强一致性本地事务，但当我们处理诸如‘票据贴现成功后，跨系统给企业发放高价值积分’这种业务时，运用的就是 BASE 理论。 我们不会让票据系统和积分系统等在同一个大事务里（这会严重阻塞）。我们会先把单据状态改为‘积分发放中’（这就是软状态 Basically Available）**，然后通过 MQ 异步发消息给积分系统。即便积分系统当时宕机了，依靠 MQ 的重试机制或我们的兜底跑批，这笔积分迟早会加上去，达到**最终一致性（Eventual Consistency）。”
    

### 3. 分布式事务：Seata 与 MQ 最终一致性的对比

在面试中，主动坦诚项目边界并展示知识广度，是非常高级的技巧： “为了保证绝对的稳定和极低的延迟，我们在核心票据系统里通过合并数据库来规避了分布式事务。但我对微服务下的分布式事务方案（如 Seata）做过深入研究和技术选型对比：”

- **Seata AT 模式（代码零侵入，适用于内部运营系统）：**
    
    - _原理：_ 业务代码照常写 `@Transactional`，只需在外层加 `@GlobalTransactional`。Seata 底层会拦截 SQL，在修改数据前，把老数据拍个快照存进 `undo_log` 表。如果下游微服务报错，Seata 依据 `undo_log` 生成反向 SQL 把数据回滚。
        
    - _致命缺陷：_ 它是通过“全局锁”来实现隔离的，资源锁定时间极长。在高并发的 C 端交易系统中，极其容易引发死锁和性能雪崩。
        
- **Seata TCC 模式（强掌控，金融级标配）：**
    
    - _原理：_ 分为 Try（资源预留/冻结）、Confirm（实际执行）、Cancel（解冻回滚）。它不依赖数据库的全局锁，而是靠业务层面的“冻结金额”来实现并发控制，性能极高，各大银行微服务改造的核心首选。
        
- **对比 基于 MQ 的最终一致性（本地消息表）：**
    
    - _选型逻辑：_ 如果是**核心资金流转**（比如 A 账户扣 100，B 账户必须加 100），必须用 **TCC**。如果是**主从链路**（比如订单支付成功，去扣减库存或发短信），坚决不用 Seata，直接上 **MQ 最终一致性**。MQ 方案没有资源锁等待，吞吐量是 Seata 的几十倍。
        

### 4. 分布式 ID (Snowflake) 与分库分表的必然联系

面试官问分布式 ID，实际上是在考查你对 MySQL B+ 树索引底层机制的理解。

- **为什么分库分表必须引入分布式 ID？** 如果不分表，MySQL 的自增主键（`AUTO_INCREMENT`）用得好好的。一旦分成了 32 张表，每张表各自自增，必定会出现 32 个 `id=1` 的记录。未来想通过 ID 汇总查询时，直接主键冲突。
    
- **为什么坚决不用 UUID？(高频暴击题)** UUID 是 36 位的无序字符串。MySQL 的 InnoDB 引擎默认使用聚簇索引（B+ 树），数据是按主键顺序紧凑物理排列的。如果用无序的 UUID 每次强行往中间插，会导致极其频繁的**页分裂（Page Split）**，不仅浪费极大的磁盘空间，还会让整个数据库的写入性能断崖式下跌。
    
- **雪花算法 (Snowflake) 的绝妙设计：**
    
    - _结构：_ 生成一个 64 位的 Long 型数字（正好占 8 字节，完美契合 MySQL 的 bigint）。第一部分是 **41 位时间戳**，第二部分是 **10 位机器/数据中心 ID**（防止多台机器生成重复），最后是 **12 位毫秒内自增序列**。
        
    - _优势：_ **“趋势递增”**。因为最高位是时间戳，越晚生成的值越大，插入 MySQL 时永远是追加在 B+ 树的最右侧，不会引发页分裂，写入性能极高。
        
- **痛点：时钟回拨问题怎么解？** 如果服务器的时间通过 NTP 自动校准，突然往回拨了 10 毫秒，雪花算法就会生成和刚刚完全一样的时间戳，导致 ID 冲突。
    
    - _应对方案：_ 在代码底层捕获到时间倒退时，如果回拨时间很短（几毫秒），直接让线程 `Thread.sleep()` 等待时间追平；如果回拨过大，直接抛出异常阻断，或切换到 Zookeeper 里预备的“备用机器 ID”继续生成。
