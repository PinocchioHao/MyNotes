## Linux常见命令

### 1. 日志排查

面试官最爱问：“生产环境报了 Bug，你怎么排查日志？”千万别说用记事本打开，要熟练说出这三个命令：

- **实时查看：** `tail -f xxx.log` (实时滚动查看最新日志，加 `-n 100` 可以看最后 100 行)。
    
- **精准搜索：** `grep -n "NullPointerException" xxx.log` (显示行号搜索)。
    
    - _进阶：_ `grep -C 10 "订单号123" xxx.log` (搜索并显示目标行的**前后 10 行**上下文，排查极度好用)。
        
- **大文件翻阅：** `less xxx.log` (用 `tail` 翻不到历史记录时使用。进入后按 `Shift + G` 直接跳到底部，按 `?` 向上搜索关键字，按 `/` 向下搜索)。
    

### 2. 端口与网络占用 (启动失败必查)

面试官常问：“Tomcat 启动报错端口被占用，怎么找出是哪个程序占的？”

- **根据端口查进程号：** `netstat -nlp | grep 8080` 或 `lsof -i:8080`。
    
- **测试网络连通性：** `telnet ip port` (测目标机器防火墙通不通) 或 `curl -I http://xxx` (测试 HTTP 接口能否返回 200)。
    

### 3. 系统资源监控 (服务卡顿、假死必查)

- **CPU 与整体内存：** `top`。进入界面后，按大写 `M` 按内存排序，按大写 `P` 按 CPU 排序。
    
    - _神级指令：_ `top -H -p <pid>`。专门查看某个 Java 进程内部的**所有线程**资源占用情况（排查 CPU 100% 问题的核心第一步）。
        
- **内存情况：** `free -h` (人类可读格式显示剩余内存)。
    
- **磁盘容量：** `df -h` (如果服务器磁盘写满，程序会一直报 IO 异常甚至无法连接数据库)。
    
	`ps -elf` 看进程
	`kill -9 线程号` 杀进程
### 4. JVM 专属监控命令 (杀手锏)

对于 Java 工程师，纯 Linux 命令是不够的，必须结合 JDK 自带的诊断工具（配合刚刚查出来的进程 PID 使用）：

- **`jps -l`：** Java 专属的 `ps`，直接列出所有 Java 进程及其完整类名。
    
- **`jstat -gcutil <pid> 1000`：** 动态监控垃圾回收（GC）情况，每隔 1000 毫秒打印一次。排查系统频繁 Full GC 导致卡顿的利器。
    
- **`jstack <pid>`：** 打印当前 Java 进程的线程快照（Thread Dump）。专门用于排查**死锁、大量线程阻塞、CPU 飙高**。
    
- **`jmap -dump:format=b,file=heap.hprof <pid>`：** 将当前的堆内存导出一个二进制快照文件。系统发生 OOM 时，把这个文件下下来用 MAT 或 IDEA 分析，就能抓出是哪个对象泄漏了。



## CI/CD
在现代大厂或金融科技公司，流水线（如 Jenkins 或 AWS CodePipeline）是标准配置。面试官主要考察你对**自动化交付流程和安全发布策略**的理解。

### 1. 现代 CI/CD 黄金流水线 (全景流程)

你可以在面试中直接描述你所熟悉的标准发布流程，体现工程化素养：

1. **代码提交 (Commit)：** 开发者推送到 Git 仓库的 master 触发 Webhook。
    
2. **持续集成 (CI)：** Jenkins/CodePipeline 拉取代码，执行单元测试，然后运行 `mvn clean package` 打包。
    
3. **镜像构建与推送：** 触发 `docker build` 将 jar 包打成不可变的 Docker 镜像，并 `docker push` 推送到私有镜像仓库。
    
4. **持续部署 (CD)：** 通知编排工具（如 AWS ECS 或 K8s），拉取最新镜像版本，并替换掉老旧版本的容器实例。
    

### 2. 零停机发布策略 (高级必备)

系统如何做到在白天核心交易时段，用户完全无感知地更新版本？

- **滚动发布 (Rolling Update)：**
    
    - **机制：** 启动一台新版本的容器，没问题后，再下线一台老版本的容器。如此交替，直到全部替换完毕。
        
    - **特点：** 节省机器资源，但发布速度较慢，且如果中途发现新版本有 Bug，回滚比较麻烦。
        
- **蓝绿发布 (Blue-Green Deployment)：**
    
    - **机制：** 同时准备两套完全独立的生产环境（老版本是蓝环境，新版本是绿环境）。新版本在绿环境部署并测试通过后，直接在网关或负载均衡器（Load Balancer）上做一次流量切换，将全部用户流量瞬间切到绿环境。
        
    - **特点：** **秒级回滚！** 如果绿环境发生严重线上事故，只需把网关流量瞬间切回蓝环境即可。缺点是极其消耗服务器资源（需要两倍的机器）。
        
- **灰度发布 / 金丝雀发布 (Canary Release)：**
    
    - **机制：** 新版本上线后，只把 5% 的真实用户流量（比如根据用户 ID 尾号取模）路由到新容器，其余 95% 继续访问老容器。观察一天，如果没有报错和客诉，再逐步扩大比例到 20%、50% 直至 100%。
        

### 3. 微服务 CI/CD 的终极难题：数据库脚本怎么发？

- **面试暴击题：** 如果新版本的代码需要给表新增一个非空字段，蓝绿发布时，代码和 SQL 脚本该按什么顺序上？
    
- **实战回答 (向前兼容法则)：** 在分布式系统中，**数据库结构的变更必须做到向前兼容**。
    
    1. 绝对不能在代码发版的同时锁表改字段，会导致系统瘫痪。
        
    2. 正确的做法是：**第一步**，先单独执行 SQL 脚本，给表新增一个**允许为空**的字段（不影响老代码正常读写老字段）。
        
    3. **第二步**，执行 CI/CD 发布新版代码。新版代码开始对这个新字段进行双写或读取。
        
    4. 这种拆分能确保发版过程随时可以安全回滚。

## Docker
### 一、 极其通俗的理解：Docker 到底是什么？

**核心类比：** 以前开发界有一个世纪难题：“这段代码在我的电脑上跑得好好的，怎么一上生产服务器就报错？”（因为生产环境的 JDK 版本、系统时钟、依赖包路径可能跟你的电脑完全不一样）。 Docker 的核心哲学就是：**“既然在你的机器上能跑，那我就把你这台机器的环境连同代码一起打包，直接搬到服务器上去！”**

Docker 就像是软件界的“集装箱”。以前搬运货物，散装的容易碎、还要挑挑拣拣；现在统统装进标准化的集装箱里，无论底层是卡车、轮船还是火车，只要能放集装箱就能运。对代码来说，只要服务器装了 Docker，你的项目拉过去就能直接跑，绝对不会出现环境不一致的问题。

### 二、 在我们的实际项目中，Docker 用在哪里？

作为研发，我们在项目里通常在两个场景下重度使用 Docker：

1. **本地环境极速搭建 (不脏宿主机)：** 假设你今天刚接手一个新项目，需要本地跑 MySQL 8.0、Redis 6、RabbitMQ。以前你得去官网挨个下载安装包，配置环境变量，极其痛苦。现在只需要几条 `docker run` 命令，几秒钟就能在本地拉起这些数据库，用完直接删掉，电脑干干净净。
    
2. **配合 CI/CD 统一部署代码：** 以前发布 Spring Boot 项目，是把打好的 `xxx.jar` 包扔给运维，运维在服务器上执行 `java -jar`。现在，我们在项目根目录下写一个只有几行代码的 `Dockerfile` 文件，告诉 CI/CD 流水线：“拿一个装好 Java 环境的空盒子，把我的 jar 包放进去，封装死”。以后每次发版，服务器拉取的就是这个“封装死的盒子（镜像）”，直接运行，极其稳定。
    

### 三、 面试实战：基于使用的 4 个高频 Q&A

面试官考你 Docker，大概率就是这 4 个偏概念和日常使用的问题。用下面的话术回答，既接地气又显得概念扎实：

#### 面试题 1：能解释一下 Docker 镜像 (Image) 和 容器 (Container) 的区别吗？

- **Java 视角神级类比：** “它们的本质就是 Java 里的**类 (Class)** 和 **对象 (Object)** 的关系。”
    
- **面试话术：** “**镜像**就像是 Java 里的 Class，它是一个静态的、只读的模板文件，里面打包了操作系统环境、JDK 和我们的应用代码。 **容器**就像是 `new` 出来的 Object，它是镜像的运行实例。我们可以从同一个镜像启动成百上千个容器，它们相互隔离、独立运行。开发构建出镜像，服务器运行的是容器。”
    

#### 面试题 2：Docker 容器和传统的虚拟机 (VMware/VirtualBox) 有什么区别？

- **面试话术：** “核心区别在于**轻量级和启动速度**。 传统的虚拟机，哪怕你只为了跑一个十几兆的小程序，它也要在底层虚拟出一整套完整的操作系统（Guest OS），极其吃内存，启动一次要好几分钟。 而 Docker 容器**没有自己的操作系统**，它直接复用宿主机（物理机）的操作系统内核。所以 Docker 极度轻量，一台机器可以跑上千个容器，启动速度是**秒级甚至毫秒级**的。”
    

#### 面试题 3：你平时是怎么把 Spring Boot 项目打包成 Docker 的？(Dockerfile 怎么写)

- **实战回答：** “其实非常简单，我们只需要在项目里写一个基础的 `Dockerfile`，通常只有核心的四五行：
    
    1. `FROM openjdk:8`：指定基础环境，告诉 Docker 给我拿一个自带 JDK 8 的基础镜像。
        
    2. `COPY xxx.jar /app.jar`：把我们本地 `target` 目录下的 Spring Boot jar 包，复制到镜像的根目录下。
        
    3. `EXPOSE 8080`：声明一下这个容器内部对外暴露的端口。
        
    4. `ENTRYPOINT ["java", "-jar", "/app.jar"]`：指定容器启动时默认执行的启动命令。 写好之后，运行 `docker build` 就能生成我们业务的镜像了。”
        

#### 面试题 4：如果 Docker 容器崩溃了或者被删除了，里面的数据还在吗？(数据持久化)

- **面试话术：** “默认情况下**数据会全部丢失**。因为容器的理念是‘无状态’和‘阅后即焚’的，里面的文件系统是临时的。 所以在实际使用中，如果我们在容器里跑 MySQL 或者需要保存上传的图片，必须使用 **数据卷挂载 (Volume / `-v` 参数)** 机制。它的原理是在启动容器时，把宿主机（物理机）硬盘上的某一个真实目录，映射到容器内部。这样容器不管怎么销毁重启，数据其实都存在物理机的硬盘上，保证了数据的安全。”
