## Redis基础
Redis作为NoSql键值型数据库，基于内存，提供String，List，Set，Zset，Hash，等基础数据结构，以及geospatial（地理位置）、hyperloglog（基数统计，不重复的数）、bitmaps（位图，记录布尔型）等高级数据结构。可应用于缓存，分布式锁，订阅等场景。



## 缓存击穿，缓存雪崩，缓存穿透
缓存击穿：高并发场景下，缓存突然失效时，众多请求查不到缓存会查数据库，数据库压力会突然上升。
解决方案：1. 缓存永不过期，但是会造成内存的浪费，并且设计不合理；2. 加锁，分布式锁和synchronize的JVM锁都可以，分布式锁严格实现一次访问，而JVM锁也削到最多服务器个数的并行，也能大大减缓了压力的同时实现还简单； 3. 服务端进行参数校验（Alibaba编码规范规定）

缓存雪崩：多个缓存同一时间过期，导致海量请求打到数据库上，导致数据库宕机，进而导致应用崩溃的情况，是缓存击穿的超集。
解决方案：1. 缓存过期时间设置某一合理范围内的随机数；   2. 加锁； 3. Redis高可用，比如熔断机制，灾备，多租户等。


缓存穿透：多个恶意请求请求到了不存在的key，如负数、非常大的值等，此时redis中和数据库中都不存在，redis和数据库压力激增。
解决方案：1. 缓存空值； 2. 布隆过滤器，可以设置不存在的为白名单或者黑名单机制（把key是否存在保存为一个boolean值存在布隆过滤器中。查询顺序为：布隆过滤器 --> Redis --> 数据库。如果非空的值在布隆过滤器中，则不需要与Redis和数据库交互。布隆过滤器能大程度降低缓存穿透的概率。）。3. 参数校验



## Redis单线程为什么反而快
1. 基于内存，内存本身就非常快
2. 基于多路复用IO模型
3. 核心逻辑是单线程，不存在线程切换的上下文开销（redis6引入了多线程，主要用于处理网络IO，增大IO吞吐量）
4. 数据结构简单，对数据操作也简单，redis中的数据结构是专门进行设计的；（比如说跳表这些）

## Redis持久化
有RDB和AOF两种方案
RDB采用的是类似快照的方式，定期把内存中的数据dump到一个文件中，这个方案是fork一个后台进程进行操作，效率高。但是宕机后有少量数据丢失的风险。
AOF是将用户对Redis的写操作都记录下来，性能不如RDB但是数据完整性最好。AOF记录每一条命令会导致文件膨胀，会有一个重写机制，就是fork一个后台子进程，读取当前内存中的数据状态，重写一个新的体积更小的AOF文件来覆盖掉老文件。




## Redis集群
#### 主从复制：
启动Redis的主机默认是主节点。
从节点可以通过slave of命令设置。
主节点可读可写，从节点只读不写。
主节点的数据可以复制给从节点，即主从复制。
主从复制可全量复制也可增量复制，主要看校验主节点的复制积压区的复制id(replication Id)和复制偏移量(offset)，如果还能找到这个偏移量就能平滑进行增量复制。

增加鲁棒性可以引入哨兵模式，并且建议多哨兵。
哨兵不提供读写服务只提供监控作用（也会监控其它哨兵）。
哨兵会监控主节点是否健康，主节点挂了之后会投票选出数据最完整的从节点作为下一个主节点。


主从复制解决的是数据健壮性问题，但是如果数据量过大，超过主节点内存大小，则需要Redis集群的数据分片机制，解决单机内存瓶颈。



#### 分片模式：
设置n个主节点以及对应的从节点，数据会基于16384个哈希槽分摊在这n个主节点上，算法为`CRC16(key) % 16384`。然后这n个主节点和对应的从节点拥有对应的主从复制模式。

分片模式下请求需要取数据的话，也是根据这个算法，去对应的分片区去取数据。

`注：CRC16就是哈希散列算法，能将key转为16位固定整数`

#### 集群模式下Spring boot的配置，负载均衡：
在`application.yml`中配置相应的cluster地址，不需要完全列出，只需要列举一个或几个，spring在启动的时候就会把对应的Redis拓扑结构给缓存下来。
随后可以配置`adaptive: true # 开启拓扑动态刷新`，以及读取策略优先从副本（从节点）读取`read-from: REPLICA_PREFERRED`，如果存在多个从节点，则默认按照轮询方式读取。




#### 热key问题
根据寻址公式`CRC16(key) % 16384`，热 Key 的名字是固定的，那么无论你算多少次，它得出的哈希槽绝对是同一个。这就意味着，**单纯的机器扩容对热key问题失效！不管你的集群里有 10 台机器还是 100 台机器，针对这个热 Key 的几十万次读写请求，永远都会被死死地路由到拥有这个槽位的那一台主节点（或其对应的从节点）上。**

热key问题分为读热key（热点新闻，热点商品详情）和写热key（抢红包，秒杀，需要同一数据扣减库存等改值操作）。在分片模式和普通主从都会出现热key问题。

读热key和写热key也有不同的解决方案。

解决方案：1. 读热key可以做本地缓存（拦截打到redis的流量，注意数据一直性问题）。2. 针对超高并发的写热key，可以请求分摊，原始key给分在几个机器上，比如`key1#1, key1#2`，请求时给请求拼接上对应的数字；但是这样做对代码侵入性极高！维护一致性的成本极高！！！  3. 无法预知的key引入监控和报警机制，（如京东开源的 `hotkey` 框架），在毫秒级内探测到突发热 Key，并且系统动态探测到某个 Key 访问频次极高，被判定为热 Key 时，系统会自动把这**一个** Key 和它的 Value 推送到应用服务器的本地缓存（通常使用 `Caffeine` 或 `Guava Cache`，设置一个很短的过期时间，比如 3-5 秒）。4. 限流兜底（配合压测设置限流值）




## 缓存一致性问题，延迟双删问题
更新数据后怎么同步缓存。
首先不建议使用更新缓存的方法，这个操作量太大了；选择删除缓存的方法，请求的时候查不到缓存自动就会查数据库然后更新一波缓存到Redis，这样只会有一次操作。

先删缓存，需要延迟双删；
先更新数据库（更推荐，因为这样更能保证最终一致性），再删除缓存需要考虑极端情况删除是否生效这点，更推荐MQ等可靠队列执行这步删除缓存的操作，支持重试等操作。但是这样需要引入MQ。。。且逻辑过多耦合。。。看取舍。。


我们系统可以通过操作来避免并发。。。例如在非业务时间管理员修改参数。。。并且我们的并发量其实不大。。。

如果要完全保证原子性，得上锁才能实现，这样会大大降低吞吐量。一般保持最终一致性即可。



双删背景：早期代码很多是开发者考虑到数据库更新比较慢，如果不删缓存，此时大量请求过来读到的就是数据库的旧数据，但如果先删缓存，那么后续请求哪怕慢一点，也会去数据库里等新数据（串行条件下）。但是并发条件下，先删缓存后，若并发的另一个线程来读到数据库的旧数据，就会把这个数据给刷回缓存，此时延时双删作为一种补救措施诞生了。这个时候在先删缓存之后延迟一段时间（这个sleep时间需要根据业务逻辑耗时来预估）再将数据库新数据刷回缓存。

延迟双删，它主要是为了解决“先删缓存，再更新数据库”方案中，由于并发读写导致的旧数据回写问题。通过延时一段时间再删一次，来清除这段时间内可能产生的脏缓存。

**但在实际开发中，我个人极不推荐这种做法。**

首先，第一步的删除不仅意义不大，反而制造了缓存击穿的风险；其次，代码里强行 `Thread.sleep()` 会导致当前线程阻塞，极大降低了系统的吞吐量；最后，这个延迟的时间在复杂的线上环境中根本无法准确评估。

所以在我的架构设计里，我更倾向于直接采用“更新数据库，再删除缓存”的策略。虽然在极其极端的并发下（比如缓存刚好失效，读请求拿到旧值，同时写请求更新了数据库并删了缓存，随后读请求又把旧值刷了回去），依然有理论上的脏数据风险，但这个概率微乎其微。配合缓存本身的 TTL 过期兜底，以及引入 MQ 做异步的删除重试，这才是兼顾性能和最终一致性的最佳实践。





## 过期策略
惰性删除：
key过期后，Redis不会主动删除，而是当下一次用户访问的时候，发现这个key 过期了，才会删除。
key不会立马被删除，会造成内存占用。

定期删除：
Redis后台任务会间隔一定时间去扫描一部分key，发现过期则删除。

Redis采用惰性删除和定期删除结合的模式管理过期key。

内存已经写满了，而所有的 key 都没过期，或者根本没设置过期时间，这时候进来的新请求怎么办？这就不属于过期策略了，而是**内存淘汰机制（Eviction Policy）**。包括 `allkeys-lru`（最近最少使用）、`allkeys-lfu`（最不经常使用）、`volatile-ttl` 等淘汰策略。这是保障 Redis 不会直接 OOM 崩溃的最后防线。


问：MySQL里面有2000w数据，Redis中只存20w的数据，如何保证Redis中的数据都是热点数据
1. 计算出20w数据所占用的内存大小，设置最大内存
2. 选择合适的内存淘汰策略，保持热点数据选择lru或者lfu



## Key - Value 设计原则
Key：
保证全局唯一性；
尽量短小精炼；
使用分隔符`:`，且符合业务需求，尽量保持层级结构，如`user:1001:profile`
尽量避免产生热key

Value：
选择合适的数据结构；
设置过期时间；
限制大小，如利用分片等机制；
合理压缩以节省内存以及网络传输开销；


## 分布式锁 - 生产没用过只了解过
基于setnx命令，即set if not exist.
实际应用中可以使用`Boolean rlt = redisTemplate.setIfAbsent(key, value，10, TimeUnit.SECONDS)`使用（其中value必须具备唯一性，一般是`UUID + ThreadId`），其中是否获得锁可以根据rlt的结果来判断，为真则说明获取到锁，为假则说明没获取到锁，然后在对应代码块执行对应逻辑。注意要考虑到健壮性，如过期时间，finally中释放锁（删除这个key），redisTemplate命令的原子性，锁续期机制等。（释放的时候不能简单地用 Java 代码写 `if (value == myValue) { delete(key) }`。因为判断和删除是两步网络请求，不具备原子性。**必须使用 Lua 脚本**将这两个操作打包丢给 Redis 执行）

一般直接使用 **Redisson** 框架实现分布式锁，它不仅封装了 Lua 脚本，还自带了 WatchDog（看门狗）机制来自动给未执行完的业务锁续期。引入它之后就可以像使用Lock类一样使用分布式锁。

分布式锁开销太大，也可以考虑zookeeper，etdc等。。。或者看业务场景能不能使用JVM锁，乐观锁等机制实现，非迫不得已不要上分布式锁。

并且锁的粒度尽量精细，对用户操作的锁应该分开，并且能用单机锁的就不要用分布式锁。
