## 事务与并发控制

### 1. 事务的核心特性 (ACID) 及底层支撑

事务是一个不可分割的业务执行单元。在金融票据清算等高要求场景中，必须严格保证 ACID：

- **原子性 (Atomicity)：** 事务中的操作要么全做，要么全不做。
    
    - _底层支撑：_ **Undo Log (回滚日志)**。记录反向操作，崩溃或 Rollback 时用于恢复数据。
        
- **持久性 (Durability)：** 事务一旦提交，结果永久保存，即使宕机也不丢失。
    
    - _底层支撑：_ **Redo Log (重做日志)**。记录物理数据页的修改，用于崩溃恢复 (Crash-Safe)。
        
- **隔离性 (Isolation)：** 并发执行的事务之间互相独立，中间状态互不干扰。
    
    - _底层支撑：_ **锁机制 (物理隔离) + MVCC (逻辑隔离)**。
        
- **一致性 (Consistency)：** 事务执行前后，业务规则和数据完整性不被破坏（如转账前后总金额不变）。
    
    - _底层支撑：_ 一致性是**最终目的**，由 A、I、D 以及业务代码共同保证。
        

### 2. 事务的并发问题与隔离级别

并发事务操作同一批数据时，会导致三种典型问题：

1. **脏读：** 读到了别人未提交的“脏”数据（破坏隔离性）。
    
2. **不可重复读：** 同一个事务内，两次读取同一行，发现**值被改了**（针对 `UPDATE`）。
    
3. **幻读：** 同一个事务内，两次同样的范围查询，发现**记录数量变了**（针对 `INSERT`/`DELETE`）。
    

**MySQL 的四种隔离级别与解决能力：**

|**隔离级别**|**脏读**|**不可重复读**|**幻读**|**InnoDB 底层实现机制**|
|---|---|---|---|---|
|**读未提交 (RU)**|会|会|会|不加锁，不使用 MVCC，直接读最新物理数据。|
|**读已提交 (RC)**|-|会|会|普通读使用 MVCC 快照读，**每次 SELECT 重新生成快照**。不加锁。|
|**可重复读 (RR)** _(MySQL默认)_|-|-|会_(InnoDB基本解决)_|普通读使用 MVCC 快照读，**整个事务共用第一次 SELECT 的快照**，不加锁。当前读依靠 **Next-Key Lock (临键锁)** 拦截插入，基本解决幻读。|
|**可串行化 (SE)**|-|-|-|彻底放弃 MVCC。所有普通 `SELECT` 隐式转换为 `LOCK IN SHARE MODE`，读写完全互斥，极度影响并发。|

### 3. 读操作的分类与锁机制

在 InnoDB 中，读取操作被严格分为两大阵营。

**阵营一：快照读 (Snapshot Read)**

- **语句：** 最普通的 `SELECT ... FROM ...`
    
- **机制：** **绝对不加任何锁！** 完全依靠 MVCC 机制读取 Undo Log 里的历史版本数据。别人在疯狂 `UPDATE`，你的查询依然畅通无阻，读写互不阻塞。
    

**阵营二：当前读 (Current Read)**

- **语句：** `UPDATE`, `DELETE`, `INSERT`, `SELECT ... FOR UPDATE`, `SELECT ... LOCK IN SHARE MODE`
    
- **机制：** 必须读取数据库中**最新**的物理数据。为了防止并发修改，**必须加底层排他锁（X锁）或共享锁（S锁）**。
    
- **实战场景：** 在票据状态流转或账户扣款时，`SELECT * FROM tickets WHERE id=1 FOR UPDATE` 是防止并发超卖的最后一道物理防线。在事务提交前，这条记录被死死霸占，其他任何修改或当前读都会被阻塞。
    

### 4. MySQL 锁的粒度分类

绝大多数锁由 InnoDB 引擎自动隐式管理，对开发者透明。

- **全局锁：** 锁整个数据库，只用于全库逻辑备份（`Flush tables with read lock`）。
    
- **表级锁：**
    
    - **表锁：** 粗暴锁全表。
        
    - **元数据锁 (MDL)：** 自动加。防止执行 `SELECT` 时，别人偷偷用 `ALTER TABLE` 篡改表结构。
        
    - **意向锁 (Intention Lock)：** 自动加的表级标记。为了快速判断表里有没有行被锁住，避免逐行扫描判断。
        
- **行级锁 (InnoDB 专属)：**
    
    - 粒度最细，并发最高。
        
    - **避坑核心：InnoDB 的行锁是加在索引上的！** 如果你的 `WHERE` 条件没有命中索引（或者索引失效导致全表扫描），行锁会**直接退化为表锁**，导致整个业务瘫痪。
        

### 5. MVCC (多版本并发控制) 底层机制

MVCC 是“读写不冲突”的核心基石。它由三个组件构成：

1. **隐藏列：** 每行数据都有两个隐秘字段：`trx_id`（最后一次修改这行数据的事务 ID）和 `roll_pointer`（回滚指针）。
    
2. **Undo Log 版本链：** 每次修改数据，旧版本都会被存入 Undo Log，通过 `roll_pointer` 指针串联成一条单向的历史版本链表。
    
3. **Read View (读视图)：** 事务执行快照读时，会拍一张当前数据库中“活跃未提交事务”的快照（包含一个活跃事务 ID 列表）。InnoDB 会拿着数据行当前的 `trx_id`，沿着 Undo Log 版本链逐个与 Read View 进行可见性规则比对，直到找到一个对当前事务可见的历史版本。


### MySQL 三大核心日志对比

这三大日志是 MySQL 保障数据不丢、主从同步的命脉。

| **维度**   | **Redo Log (重做日志)**                      | **Undo Log (回滚日志)**                       | **Binlog (归档日志)**                                |
| -------- | ---------------------------------------- | ----------------------------------------- | ------------------------------------------------ |
| **所属组件** | InnoDB 引擎特有                              | InnoDB 引擎特有                               | MySQL Server 层 (所有引擎共用)                          |
| **日志格式** | **物理日志** (记录“在某个数据页的某个偏移量上修改了什么值”)       | **逻辑日志** (记录与执行相反的语句，如你 INSERT，它记 DELETE) | **逻辑日志** (记录所有的 DDL 和 DML 语句，格式有 row, statement) |
| **核心作用** | 保障事务的**持久性 (Crash-Safe)**，宕机后用于恢复未落盘的数据。 | 保障事务的**原子性**（用于回滚）和实现 **MVCC**。           | 用于**主从复制 (Replication)** 和**数据备份恢复**。            |
| **写入方式** | 循环写（空间固定，写满后会覆盖旧日志）                      | 追加写                                       | 追加写（写满切换到下一个文件，不覆盖）                              |

#### 如果事务提交了一半，数据库宕机了，怎么保证 Redo Log 和 Binlog 的数据一致性？”

 “MySQL 为了防止这两个日志出现‘一个写成功，一个没写成功’的撕裂状态，在底层事务提交时，采用了**两阶段提交**机制：

1. **Prepare 阶段：** InnoDB 先把物理修改写入 Redo Log，此时 Redo Log 标记为 `Prepare` 状态。
    
2. **写 Binlog：** Server 层把逻辑修改写入 Binlog。
    
3. **Commit 阶段：** InnoDB 收到 Binlog 写入成功的信号，将 Redo Log 标记为 `Commit` 状态。

如果中途发生崩溃：MySQL 重启恢复时，只要发现 Redo Log 处于 `Prepare` 状态，就会去检查 Binlog 是否完整。如果 Binlog 完整就强行 Commit，如果不完整就 Rollback。这就完美保证了主从架构下的数据绝对一致。”

## 索引体系
索引是用来快速寻找具有特定值的记录，类似于书的目录。  
如果没有索引，一般来说要执行查询时遍历整张表。  
索引是帮助MySQL高效获取数据的排好序的数据结构。

由于数据是存在磁盘上的如果没有索引，那么每次查询都要跟磁盘来一次IO交互

虽然索引大大提高了查询速度，同时却会降低更新表的速度，如对表进行INSERT、UPDATE和DELETE。因为更新表时，MySQL不仅要保存数据，还要保存一下索引文件。

MySql的索引基于底层的数据引擎，InnoDB和 MyISAM是基于B+树实现的，而MEMORY是基于hash实现的。


- **B+Tree 的优势 (必考)：** 为什么不用 Hash、二叉树、红黑树？
    
    - 相比二叉树/红黑树：B+Tree 是多叉树，树更矮胖。数据库每次加载一个节点就是一次磁盘 I/O，树越矮，I/O 次数越少。
        
    - 相比 Hash：Hash 不支持范围查询 (`>，<，BETWEEN`)。
        
    - B+Tree 叶子节点之间用双向链表相连，极大地优化了范围查询和排序。
        
- **聚簇索引 vs 非聚簇索引：**
    
    - **聚簇索引（主键索引）：** 叶子节点直接存放**整行真实数据**。
        
    - **非聚簇索引（二级索引）：** 叶子节点存放的是**主键的值**。
        
    - **回表（重点）：** 当你通过普通索引查到了主键 ID，再去主键索引树里查出完整数据的过程叫“回表”。
        
- **索引下推 (ICP) 与覆盖索引：**
    
    - **覆盖索引：** 查询字段在索引树上全都有，完全不需要回表。如：`SELECT id, name FROM users WHERE name = 'John'`。如果建立了 `(name)` 索引，因为索引树里已经包含了 `id` 和 `name`，所以不需要回表，直接返回。
    - **索引下推 (Index Condition Pushdown, MySQL 5.6 引入)：** 用来减少回表次数的利器。
		- _场景：_ 联合索引 `(name, age)`，查询 `WHERE name = '张三' AND age > 20`。
		- _没有 ICP 时：_ 存储引擎层只用 `name = '张三'` 在索引树里找，找到 100 个张三，拿着 100 个主键 ID 去**回表 100 次**查出完整数据。传给 Server 层后，Server 层再去过滤 `age > 20`。
		- _开启 ICP 后：_ 存储引擎层在索引树里找到张三后，**直接在索引树内部**顺便把 `age > 20` 这个条件也判断了（因为联合索引里有 age 的值）。过滤后发现只有 5 个张三符合，最终只需**回表 5 次**。大大降低了磁盘 I/O。
		
    - **最左前缀原则：** 联合索引 `(A, B, C)`，查询条件必须包含 A 才能用上索引。如果是 `WHERE B = 1 AND C = 2` 则索引失效。


### 索引失效可能的情况

1. 以%开头的like语句，模糊匹配
2. or语句前后没有同时使用索引
3. 数据类型出现隐式转换（如varchar不加单引号可能自动转成int型，本质上是调用了函数）
4. where中的索引列使用函数
5. where中的索引列有运算
6. 复合索引未使用左列字段

### 不推荐使用索引的情况

1. 数据唯一性差（散列度太低）  
    例如一个字段取值只有几种，如性别、年级等
2. 频繁更新的字段  
    比如logincount登陆次数这种，会增大数据库工作量，效率降低
3. 不在where语句中的字段  
    只有where语句里面的字段MySQL才会使用索引



### 索引的目的是什么？

1. 提高检索速度
2. 创建唯一性索引，保证数据库中行数据的唯一性
3. 加速表之间的连接
4. 使用分组和排序语句时，能减少分组和排序的时间


### MySQL索引为什么用B+树，为什么不用B树或者跳表

对比跳表：B+树索引层级更小，与磁盘的IO交互更少。（尽量把数据结构设计得矮一点）

对比B树：

1. **B+树的磁盘读写代价更低**：B+树的内部节点并没有指向关键字具体信息的指针（关键字信息全在叶子结点），因此其内部节点相对B树更小，一次性读入内存的需要查找的关键字也就更多。
2. **B+树的查询效率更加稳定**：查询任何关键字的查找必须走一条从根结点到叶子结点的路。所有关键字查询的路径长度相同，导致每一个数据的查询效率相当。
3. **B+树更方便扫库**：由于B+树的数据都存储在叶子结点中，分支结点均为索引，方便扫库，只需要扫一遍叶子结点即可，但是B树因为其分支结点同样存储着数据，我们要找到具体的数据，需要进行一次中序遍历按序来扫，所以B+树更加适合在区间查询的情况，所以通常B+树用于数据库索引。

**为什么 MySQL 用 B+Tree，而 Redis 用跳表 (SkipList)？** 

- **MySQL 数据在磁盘：** 磁盘 I/O 极慢，所以数据结构必须尽可能“矮胖”，B+Tree 的高扇出率（一个节点存几百个 Key）让千万级数据只需 3 层树高（3 次 I/O）。
    
- **Redis 数据在内存：** 内存访问极快，不在乎所谓的“树高”。跳表实现起来远比 B+Tree 简单，而且在并发环境下，B+Tree 遇到节点分裂时需要锁住大量相邻节点，而跳表只需要用 CAS 修改局部指针，并发写性能极高。

## MySQL 性能优化与架构调优

### 核心 SQL 优化准则 (避免索引失效)

在排查高并发接口性能瓶颈时，90% 的慢查询都源于以下几种索引失效场景：

- **隐式类型转换：** 字符串类型字段（如单据号 `varchar`）在查询时不加单引号（`WHERE order_no = 123`）。MySQL 底层会自动套用 `CAST` 函数强转，直接破坏 B+Tree 有序性，导致全表扫描。
    
- **左模糊匹配：** `LIKE '%abc'`。B+Tree 只能利用前缀比较大小，左边是不确定的字符时无法走索引。若是 `LIKE 'abc%'` 则可以走索引（范围查询）。
    
- **在索引列上使用函数或运算：** 如 `WHERE YEAR(create_time) = 2026` 或 `WHERE amount + 100 > 1000`。必须改造为 `WHERE create_time >= '2026-01-01'`。
    
- **违背最左前缀原则：** 联合索引 `(A, B, C)`，查询条件跳过 A 直接查 B 或 C，或者 A 是范围查询（`>`、`<`），导致后面的 B 和 C 无法走索引。
    
- **OR 的两边不全有索引：** 只要 `OR` 前后有一个字段没建索引，优化器为了查出那部分数据，只能选择全表扫描。
    

**研发层面的硬性规范：**

1. **禁止 `SELECT *`：** 浪费网络带宽与内存，且直接摧毁了触发**覆盖索引**（不用回表）的可能性。
    
2. **避免复杂多表 JOIN：** 阿里规范建议 JOIN 不超过 3 张表。大表 JOIN 极其消耗内存（Block Nested-Loop 算法），微服务架构下应在 Java 内存中做数据拼装。
    
3. **禁止使用存储过程与外键：** 存储过程难以调试调试与版本控制；物理外键会引发高并发下的死锁及级联性能雪崩，数据一致性必须由 Java 逻辑和分布式事务保证。
    

### 写入性能优化与“页分裂”灾难

当发现数据库 `INSERT` 极慢、且磁盘 I/O 异常飙高时，通常是主键无序引发的**页分裂**。

- **页分裂的本质：** InnoDB 的数据按照主键大小严格顺序存放在大小为 16KB 的数据页中。如果插入的主键是绝对递增的（如自增 ID、雪花算法 ID），数据直接在页末尾顺序追加，性能极高。如果插入**完全无序的主键（如 UUID）**，新数据需要硬塞到已写满的旧数据页中间，MySQL 不得不申请新页并将老页的一半数据搬迁过去，造成巨大的随机 I/O 与内存碎片。
    

### 分库分表后ID选择

| **分布式主键方案**          | **特性描述**                | **对 B+Tree 的影响**                         | **适用场景**                  |
| -------------------- | ----------------------- | ---------------------------------------- | ------------------------- |
| **Snowflake (雪花算法)** | 64 位 Long 型，**时间戳趋势递增** | **完美适配。** 保证数据顺序追加写，彻底避免页分裂，占用空间小。       | **首选。** 金融交易流水、票据系统的标配。   |
| **UUID**             | 32/36 位随机字符串，完全无序       | **毁灭性打击。** 引发极高频的页分裂，且占用大量空间，导致二级索引极其臃肿。 | 严禁作为主键。可作为业务字段单独建非聚簇索引。   |
| **数据库自增 ID**         | Int/BigInt，绝对递增         | 完美适配。但存在单库性能瓶颈。                          | 单机、小规模非拆分表业务。             |
| **Redis 原子生成**       | 利用 `INCR` 指令生成          | 完美适配。单点依赖严重，Redis 宕机找回极难。                | 发号器服务的高可用设计成本较高，不如雪花算法轻量。 |

### 大批量插入 (Bulk Insert) 提速方案：

1. **JDBC 批处理：** 开启 `rewriteBatchedStatements=true`，在 Java 代码中使用 `executeBatch()`，将多条 SQL 重写为 `INSERT INTO table VALUES (),(),()` 结构。
    
2. **临时关闭校验：** 批量导入历史数据时，可临时执行 `SET UNIQUE_CHECKS=0;`（关闭唯一性校验）与 `SET AUTOCOMMIT=0;`，完成后再开启。
    
3. **原生工具：** 极大数据量搬迁直接使用 `LOAD DATA INFILE`，绕过 SQL 解析引擎，速度最快。
    

### 大表架构级优化 (千万级以上数据)

单表行数一旦越过阈值（经验值 1000 万 ~ 2000 万），B+Tree 树高可能突破 3 层，常规索引调优收效甚微，必须从架构层面开刀：

1. **限制查询范围（降维打击）：** C 端接口严禁提供无边界的条件搜索，强制要求传入时间窗口（如“近 30 天”、“近 3 个月”）。
    
2. **读写分离：** 引入主从架构。主库专干高并发的 `INSERT/UPDATE`，从库负责报表导出和重度 `SELECT`。
    
3. **垂直分库分表：** 按业务域“剥离”。比如将核心票据表拆分为“票据基础信息表”和“票据流转记录表”，将不常查的大字段（TEXT、长字符串）单独拆表。
    
4. **水平分库分表 (Sharding)：** 终极杀招。利用 ShardingSphere 或 MyCat，按分片键（如 user_id 的 Hash 值）将数据打散到多个物理库表，突破单机 I/O 和存储瓶颈。
    

### 生产环境慢 SQL 排查实战 (EXPLAIN)

1. **定位慢 SQL：** 开启 `slow_query_log`，使用 `mysqldumpslow` 或阿里 Druid 监控面板抓取执行耗时越过阈值（如 1s）的 SQL 语句。
    
2. **分析执行计划：** 在 SQL 前加上 `EXPLAIN`（或 `EXPLAIN FORMAT=JSON` 看更详细的开销估算），紧盯以下三个致命指标：
    

- **`type` (连接/访问类型)：**
    
    - _好：_ `system` > `const` (主键等值查询) > `eq_ref` > `ref` (普通索引等值查询) > `range` (范围查询)。
        
    - _极差：_ `index` (遍历整棵索引树) > `ALL` (全表扫描)。见到这俩必须优化。
        
- **`key` vs `possible_keys`：**
    
    - 如果 `possible_keys` 有值但 `key` 是 NULL，说明优化器认为走索引回表成本太高，强行选择了全表扫描。
        
- **`Extra` (扩展状态信息)：**
    
    - _☠️ 致命死穴：_ `Using filesort`（在内存或磁盘上对结果进行了外部排序，极其消耗 CPU）或 `Using temporary`（使用了临时表处理，多见于复杂的 GROUP BY）。
        
    - _🎉 完美状态：_ `Using index`（触发了**覆盖索引**，数据直接从索引树上拿完，一刀不回表）。
        
    - _👍 良好状态：_ `Using index condition`（触发了**索引下推 ICP**，在引擎层提前过滤了数据，大幅减少了回表次数）。
