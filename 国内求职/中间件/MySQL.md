## 事务与并发控制

### 1. 事务的核心特性 (ACID) 及底层支撑

事务是一个不可分割的业务执行单元。在金融票据清算等高要求场景中，必须严格保证 ACID：

- **原子性 (Atomicity)：** 事务中的操作要么全做，要么全不做。
    - _底层支撑：_ **Undo Log (回滚日志)**。记录反向操作，崩溃或 Rollback 时用于恢复数据。
- **一致性 (Consistency)：** 事务执行前后，业务规则和数据完整性不被破坏（如转账前后总金额不变）。
    - _底层支撑：_ 一致性是**最终目的**，由 A、I、D 以及业务代码共同保证。
- **隔离性 (Isolation)：** 并发执行的事务之间互相独立，中间状态互不干扰。
    - _底层支撑：_ **锁机制 (物理隔离) + MVCC (逻辑隔离)**。
- **持久性 (Durability)：** 事务一旦提交，结果永久保存，即使宕机也不丢失。
    - _底层支撑：_ **Redo Log (重做日志)**。记录物理数据页的修改，用于崩溃恢复 (Crash-Safe)。
        


### 2. 事务的并发问题与隔离级别

并发事务操作同一批数据时，会导致三种典型问题（根据**SQL92规范**里面的表层定义如下，注意跟MySql底层实现略有出入）：

1. **脏读：** 读到了别人未提交的“脏”数据（破坏隔离性）。
    
2. **不可重复读：** 侧重于**已存在数据**的修改。同一个事务内，两次读取同一批数据，发现**数据内容被修改或记录被删除**（针对 `UPDATE` / `DELETE`）。因为这些数据是客观存在的，InnoDB 底层可以直接用**行锁 (Record Lock)** 锁住它们来防范。
    
3. **幻读（早期也翻译为虚读）：** 侧重于**新数据的凭空出现**。同一个事务内，两次同样的范围查询，发现**多出了之前不存在的新记录**（严格针对 `INSERT`，规范中笼统针对插入和删除）。因为无法给不存在的数据加行锁，InnoDB 必须引入**间隙锁 (Gap Lock)** 来防范。
    

**MySQL 的四种隔离级别与解决能力：**

| **隔离级别**                  | **脏读** | **不可重复读** | **幻读**                   | **InnoDB 底层实现机制**                                                                                                    |
| ------------------------- | ------ | --------- | ------------------------ | -------------------------------------------------------------------------------------------------------------------- |
| **读未提交 (RU)**             | 会      | 会         | 会                        | 不加锁，不使用 MVCC，直接读最新物理数据。                                                                                              |
| **读已提交 (RC)**             | -      | 会         | 会                        | 普通读使用 MVCC 快照读，**每次 SELECT 重新生成快照Read View**。不加锁。                                                                    |
| **可重复读 (RR)** _(MySQL默认)_ | -      | -         | 极小概率会(快照读和当前读混用并插入了冲突数据) | 普通读使用 MVCC 快照读，**整个事务共用第一次 SELECT 的快照**，不加锁。当前读依靠 **Next-Key Lock (临键锁，即行锁+间隙锁的组合)** ，把那个数据范围直接锁死，不允许别人插入，从而彻底解决了幻读。 |
| **可串行化 (SE)**             | -      | -         | -                        | 彻底放弃 MVCC。所有普通 `SELECT` 隐式转换为 `LOCK IN SHARE MODE`，读写完全互斥，极度影响并发。                                                    |

#### 隔离级别举例
在一个包含 3 步 `UPDATE` 的 Spring 事务中，数据是**每执行一步就立刻修改落盘的（写入 Buffer Pool 及 Redo/Undo Log），绝不是等到最后才一波流修改**。如果在第 1 步执行完后打断点卡住，此时的数据可见性如下：

1. **当前事务内（同一个 Connection）：可见。** 因为是在同一条数据库连接里，代码往下走或者直接在当前断点的上下文里查，看到的绝对是第 1 步修改后的**新值**。
    
2. **事务外部（Navicat / 其他前端请求）：不可见（查到的是老值）。** 由于事务还未 Commit，MySQL 利用 MVCC（多版本并发控制）机制，让外部的其他查询去读取系统底层 Undo Log 里的**历史快照**。这完美避免了“脏读”。
    
3. **异常回滚：** 如果第 3 步报错，Spring 触发 `rollback()`，引擎顺着底层的 Undo Log，将第 1、2 步已经修改在磁盘上的值硬生生还原回初始状态。


### 3. 读操作的分类与锁机制

在 InnoDB 中，读取操作被严格分为两大阵营。

**阵营一：快照读 (Snapshot Read)**

- **语句：** 最普通的 `SELECT ... FROM ...`
    
- **机制：** **绝对不加任何锁！** 完全依靠 MVCC 机制读取 Undo Log 里的历史版本数据。别人在疯狂 `UPDATE`，你的查询依然畅通无阻，读写互不阻塞。
    

**阵营二：当前读 (Current Read)**

- **语句：** `UPDATE`, `DELETE`, `INSERT`, `SELECT ... FOR UPDATE`, `SELECT ... LOCK IN SHARE MODE`
    
- **机制：** 必须读取数据库中**最新**的物理数据。为了防止并发修改，**必须加底层排他锁（X锁）或共享锁（S锁）**。
    
- **实战场景：** 在票据状态流转或账户扣款时，`SELECT * FROM tickets WHERE id=1 FOR UPDATE` 是防止并发超卖的最后一道物理防线。在事务提交前，这条记录被死死霸占，其他任何修改或当前读都会被阻塞。
    

### 4. MySQL 锁的粒度分类

绝大多数锁由 InnoDB 引擎自动隐式管理，对开发者透明。

- **全局锁：** 锁整个数据库，只用于全库逻辑备份（`Flush tables with read lock`）。
    
- **表级锁：**
    
    - **表锁：** 粗暴锁全表。
        
    - **元数据锁 (MDL)：** 自动加。防止执行 `SELECT` 时，别人偷偷用 `ALTER TABLE` 篡改表结构。
        
    - **意向锁 (Intention Lock)：** 自动加的表级标记。为了快速判断表里有没有行被锁住，避免逐行扫描判断。
        
- **行级锁 (InnoDB 专属)：**
    
    粒度最细，并发最高，细分为：
	- **1. 记录锁 (Record Lock)：**
	    
	    - **锁什么：** 只锁具体的某一条索引记录。
	        
	    - **场景：** 精确命中主键或唯一索引的等值查询。比如 `SELECT * FROM user WHERE id = 1 FOR UPDATE;`，只锁 `id=1` 这一行。
	        
	- **2. 间隙锁 (Gap Lock)：**
	    
	    - **锁什么：** 锁住两条记录之间的“空隙”，**不包含记录本身**。
	        
	    - **场景：** 为了**防止幻读**。比如表里有 id=10 和 id=20 的数据，你执行 `WHERE id BETWEEN 12 AND 18 FOR UPDATE`。MySQL 会把 (10, 20) 这个间隙锁住，别的线程想 `INSERT` 一条 id=15 的数据就会被阻塞。
	        
	    - **注意：** 间隙锁只在 **RR（可重复读）** 隔离级别下才会生效。而且间隙锁之间是不互斥的，大家都可以给同一个间隙加锁，它们只排斥 `INSERT` 操作。
	        
	- **3. 临键锁 (Next-Key Lock)：**
	    
	    - **锁什么：** = **记录锁 + 间隙锁**。它不仅锁住某条记录，还锁住这条记录前面的间隙，形成一个**左开右闭**的区间，比如 `(10, 20]`。
	        
	    - **场景：** 这是 InnoDB 默认的行锁算法。当你进行范围查询，或者等值查询但没有命中唯一索引时，默认加的就是临键锁，彻底封死幻读的可能。
        
- **避坑核心：InnoDB 的行锁全都是加在“索引树”上的！** 如果你执行 `UPDATE` 或 `FOR UPDATE` 时，`WHERE` 条件没有命中索引（或者索引失效），InnoDB 找不到该去锁哪一行的索引，为了保证安全，它会把整张表所有的记录和所有的间隙全部用临键锁锁上。**在宏观表现上，行锁就直接退化成了开销巨大的“表锁”**，这会导致整个业务的写操作瘫痪。


### 5. MVCC (多版本并发控制) 底层机制

MVCC 是“读写不冲突”的核心基石。它由三个组件构成：

1. **隐藏列：** 每行数据都有两个隐秘字段：`trx_id`（最后一次修改这行数据的事务 ID）和 `roll_pointer`（回滚指针）。
    
2. **Undo Log 版本链：** 每次修改数据，旧版本都会被存入 Undo Log，通过 `roll_pointer` 指针串联成一条单向的历史版本链表。
    
3. **Read View (读视图)：** 事务执行快照读时，会拍一张当前数据库中“活跃未提交事务”的快照（包含一个活跃事务 ID 列表）。InnoDB 会拿着数据行当前的 `trx_id`，沿着 Undo Log 版本链逐个与 Read View 进行可见性规则比对，直到找到一个对当前事务可见的历史版本。
	**比对过程的目的：判断“这行数据的这个版本，我能不能看？”** 因为 Undo Log 版本链上挂着这行数据的 N 个历史版本，每个版本都标有修改它的 `trx_id`。 事务拿着这个 `trx_id` 去跟 Read View 对比：
	- 如果 `trx_id` 比黑名单里最小的 ID 还小：说明修改它的人早就提交了，**可见**。
	- 如果 `trx_id` 在黑名单列表里：说明修改它的事务正在跟我并发执行，还没提交，**不可见**。顺着版本链往下找更老的版本。
	- 如果 `trx_id` 是我自己：自己改的，**可见**。 通过这个比对，完美实现了读写不加锁的隔离，每个事务都能精确读到属于自己那个时间节点该看的数据。


### MySQL 三大核心日志对比

这三大日志是 MySQL 保障数据不丢、主从同步的命脉。

| **维度**   | **Redo Log (重做日志)**                      | **Undo Log (回滚日志)**                       | **Binlog (归档日志)**                                |
| -------- | ---------------------------------------- | ----------------------------------------- | ------------------------------------------------ |
| **所属组件** | InnoDB 引擎特有                              | InnoDB 引擎特有                               | MySQL Server 层 (所有引擎共用)                          |
| **日志格式** | **物理日志** (记录“在某个数据页的某个偏移量上修改了什么值”)       | **逻辑日志** (记录与执行相反的语句，如你 INSERT，它记 DELETE) | **逻辑日志** (记录所有的 DDL 和 DML 语句，格式有 row, statement) |
| **核心作用** | 保障事务的**持久性 (Crash-Safe)**，宕机后用于恢复未落盘的数据。 | 保障事务的**原子性**（用于回滚）和实现 **MVCC**。           | 用于**主从复制 (Replication)** 和**数据备份恢复**。            |
| **写入方式** | 循环写（空间固定，写满后会覆盖旧日志）                      | 追加写                                       | 追加写（写满切换到下一个文件，不覆盖）                              |

#### Redo Log和Undo Log区别
它们虽然在崩溃恢复中都起作用，但分工完全相反（一个管往前冲，一个管往后退）：

- **Redo Log (重做日志 - 保证持久性)：** 它是物理日志，记录了“在某个数据页上做了什么修改”。**它的作用是 Roll Forward（向前滚）**。数据库宕机重启时，如果有些提交的事务还没来得及刷入磁盘，依靠 Redo Log 重新执行一遍，把数据找回来。
    
- **Undo Log (回滚日志 - 保证原子性和 MVCC)：** 它是逻辑日志，记录了数据的历史快照。**它的作用是 Roll Back（向后滚）**。宕机重启时，如果发现有些事务只执行了一半还没提交，数据库必须依靠 Undo Log 把这些“半拉子”脏数据撤销掉。 简单说：Redo Log 保证**已提交的绝对不丢**，Undo Log 保证**未提交的绝对不留**。

#### 如果事务提交了一半，数据库宕机了，怎么保证 Redo Log 和 Binlog 的数据一致性？”

 “MySQL 为了防止这两个日志出现‘一个写成功，一个没写成功’的撕裂状态，在底层事务提交时，采用了**两阶段提交**机制：

1. **Prepare 阶段：** InnoDB 先把物理修改写入 Redo Log，此时 Redo Log 标记为 `Prepare` 状态。
    
2. **写 Binlog：** Server 层把逻辑修改写入 Binlog。
    
3. **Commit 阶段：** InnoDB 收到 Binlog 写入成功的信号，将 Redo Log 标记为 `Commit` 状态。

如果中途发生崩溃：MySQL 重启恢复时，只要发现 Redo Log 处于 `Prepare` 状态，就会去检查 Binlog 是否完整。如果 Binlog 完整就强行 Commit，如果不完整就 Rollback。这就完美保证了主从架构下的数据绝对一致。”

## 索引体系
索引是用来快速寻找具有特定值的记录，类似于书的目录。  
如果没有索引，一般来说要执行查询时遍历整张表。  
索引是帮助MySQL高效获取数据的排好序的数据结构。

由于数据是存在磁盘上的如果没有索引，那么每次查询都要跟磁盘来一次IO交互

虽然索引大大提高了查询速度，同时却会降低更新表的速度，如对表进行INSERT、UPDATE和DELETE。因为更新表时，MySQL不仅要保存数据，还要保存一下索引文件。

MySql的索引基于底层的数据引擎，InnoDB和 MyISAM是基于B+树实现的，而MEMORY是基于hash实现的。


- **B+Tree 的优势 (必考)：** 为什么不用 Hash、二叉树、红黑树？
    
    - 相比二叉树/红黑树：B+Tree 是多叉树，树更矮胖。数据库每次加载一个节点就是一次磁盘 I/O，树越矮，I/O 次数越少。
        
    - 相比 Hash：Hash 不支持范围查询 (`>，<，BETWEEN`)。
        
    - B+Tree 叶子节点之间用双向链表相连，极大地优化了范围查询和排序。
    
- **索引下推 (ICP) 与覆盖索引：**
    
    - **覆盖索引：** 查询字段在索引树上全都有，完全不需要回表。如：`SELECT id, name FROM users WHERE name = 'John'`。如果建立了 `(name)` 索引，因为索引树里已经包含了 `id` 和 `name`，所以不需要回表，直接返回。
    - **索引下推 (Index Condition Pushdown, MySQL 5.6 引入)：** 用来减少回表次数的利器。
		- _场景：_ 联合索引 `(name, age)`，查询 `WHERE name = '张三' AND age > 20`。
		- _没有 ICP 时：_ 存储引擎层只用 `name = '张三'` 在索引树里找，找到 100 个张三，拿着 100 个主键 ID 去**回表 100 次**查出完整数据。传给 Server 层后，Server 层再去过滤 `age > 20`。
		- _开启 ICP 后：_ 存储引擎层在索引树里找到张三后，**直接在索引树内部**顺便把 `age > 20` 这个条件也判断了（因为联合索引里有 age 的值）。过滤后发现只有 5 个张三符合，最终只需**回表 5 次**。大大降低了磁盘 I/O。
		
    - **最左前缀原则：** 联合索引 `(A, B, C)`，查询条件必须包含 A 才能用上索引。如果是 `WHERE B = 1 AND C = 2` 则索引失效。

### ### 聚簇索引 & 非聚簇索引 & 回表

- **聚簇索引（主键索引）：** 整张表的数据本身就是一棵 B+ 树。它的叶子节点存放的就是**完整的一行真实业务数据**，非叶子节点存放主键。找到主键，就直接拿到了整行数据。
    
- **非聚簇索引（二级索引）：** 除了主键之外，你给表里的其他字段（比如 `name`）建立的普通索引，也会各自生成一棵**独立的 B+ 树**。但这棵树的叶子节点**不存放完整的行数据，只存放“被索引的字段值 (name)”和“对应的主键 ID”**，非叶子节点存放的是这个普通索引的值。
    

**“回表”的过程与痛点：** 假设你执行 `SELECT * FROM table WHERE name = '张三'`。

1. **第一步（查二级索引树）：** 数据库先去 `name` 这个二级索引的 B+ 树里找，在叶子节点找到了“张三”，顺便拿到了“张三”的主键 ID（假设 ID=10）。
    
2. **第二步（查主键索引树，即回表）：** 因为你的 SQL 写的是 `SELECT *`（需要所有字段），二级索引的叶子节点里没有其它字段，所以数据库必须拿着 `ID=10`，**再跑回到主键索引的 B+ 树里**，从上到下重新搜一遍，查出完整的行数据。
    
3. **结论：** 跑了两次 B+ 树，这种性能损耗就叫“回表”。
    
- **面试高阶优化（覆盖索引）：** 怎么避免回表？如果你把 SQL 改成 `SELECT id, name FROM table WHERE name = '张三'`。因为你要查的 `id` 和 `name` 在二级索引的叶子节点里已经全有了，数据库查完第一步就直接返回了，不需要去查主键树，这叫**覆盖索引**，是极高频的 SQL 优化手段。



### 索引失效可能的情况

1. 以%开头的like语句，模糊匹配
2. or语句前后没有同时使用索引
3. 数据类型出现隐式转换（如varchar不加单引号可能自动转成int型，本质上是调用了函数）
4. where中的索引列使用函数
5. where中的索引列有运算
6. 复合索引未使用左列字段

### 不推荐使用索引的情况

1. 数据唯一性差（散列度太低）  
    例如一个字段取值只有几种，如性别、年级等
2. 频繁更新的字段  
    比如logincount登陆次数这种，会增大数据库工作量，效率降低
3. 不在where语句中的字段  
    只有where语句里面的字段MySQL才会使用索引



### 索引的目的是什么？

1. 提高检索速度
2. 创建唯一性索引，保证数据库中行数据的唯一性
3. 加速表之间的连接
4. 使用分组和排序语句时，能减少分组和排序的时间


### MySQL索引为什么用B+树，为什么不用B树或者跳表

对比跳表：B+树索引层级更小，与磁盘的IO交互更少。（尽量把数据结构设计得矮一点）

对比B树：

1. **B+树的磁盘读写代价更低**：B+树的内部节点并没有指向关键字具体信息的指针（关键字信息全在叶子结点），因此其内部节点相对B树更小，一次性读入内存的需要查找的关键字也就更多。
2. **B+树的查询效率更加稳定**：查询任何关键字的查找必须走一条从根结点到叶子结点的路。所有关键字查询的路径长度相同，导致每一个数据的查询效率相当。
3. **B+树更方便扫库**：由于B+树的数据都存储在叶子结点中，分支结点均为索引，方便扫库，只需要扫一遍叶子结点即可，但是B树因为其分支结点同样存储着数据，我们要找到具体的数据，需要进行一次中序遍历按序来扫，所以B+树更加适合在区间查询的情况，所以通常B+树用于数据库索引。

**为什么 MySQL 用 B+Tree，而 Redis 用跳表 (SkipList)？** 

- **MySQL 数据在磁盘：** 磁盘 I/O 极慢，所以数据结构必须尽可能“矮胖”，B+Tree 的高扇出率（一个节点存几百个 Key）让千万级数据只需 3 层树高（3 次 I/O）。
    
- **Redis 数据在内存：** 内存访问极快，不在乎所谓的“树高”。跳表实现起来远比 B+Tree 简单，而且在并发环境下，B+Tree 遇到节点分裂时需要锁住大量相邻节点，而跳表只需要用 CAS 修改局部指针，并发写性能极高。

## MySQL 性能优化与架构调优

### 核心 SQL 优化准则 (避免索引失效)

在排查高并发接口性能瓶颈时，90% 的慢查询都源于以下几种索引失效场景：

    
- **左模糊匹配：** `LIKE '%abc'`。B+Tree 只能利用前缀比较大小，左边是不确定的字符时无法走索引。若是 `LIKE 'abc%'` 则可以走索引（范围查询）。
    
- **在索引列上使用函数或运算：** 如 `WHERE YEAR(create_time) = 2026` 或 `WHERE amount + 100 > 1000`。必须改造为 `WHERE create_time >= '2026-01-01'`。
- **隐式类型转换：** 字符串类型字段（如单据号 `varchar`）在查询时不加单引号（`WHERE order_no = 123`）。MySQL 底层会自动套用 `CAST` 函数强转，直接破坏 B+Tree 有序性，导致全表扫描。
- **联合索引违背最左前缀原则：** 联合索引 `(A, B, C)`，查询条件跳过 A 直接查 B 或 C，或者 A 是范围查询（`>`、`<`），导致后面的 B 和 C 无法走索引。
    
- **OR 的两边不全有索引：** 只要 `OR` 前后有一个字段没建索引，优化器为了查出那部分数据，只能选择全表扫描。
    

**研发层面的硬性规范：**

1. **禁止 `SELECT *`：** 浪费网络带宽与内存，且直接摧毁了触发**覆盖索引**（不用回表）的可能性。
    
2. **避免复杂多表 JOIN：** 阿里规范建议 JOIN 不超过 3 张表。大表 JOIN 极其消耗内存（Block Nested-Loop 算法），微服务架构下应在 Java 内存中做数据拼装。
    
3. **禁止使用存储过程与外键：** 存储过程难以调试调试与版本控制；物理外键会引发高并发下的死锁及级联性能雪崩，数据一致性必须由 Java 逻辑和分布式事务保证。
    

### 写入性能优化与“页分裂”灾难

当发现数据库 `INSERT` 极慢、且磁盘 I/O 异常飙高时，通常是主键无序引发的**页分裂**。

- **页分裂的本质：** InnoDB 的数据按照主键大小严格顺序存放在大小为 16KB 的数据页中。如果插入的主键是绝对递增的（如自增 ID、雪花算法 ID），数据直接在页末尾顺序追加，性能极高。如果插入**完全无序的主键（如 UUID）**，新数据需要硬塞到已写满的旧数据页中间，MySQL 不得不申请新页并将老页的一半数据搬迁过去，造成巨大的随机 I/O 与内存碎片。
    

### 分库分表后ID选择

| **分布式主键方案**          | **特性描述**                | **对 B+Tree 的影响**                         | **适用场景**                  |
| -------------------- | ----------------------- | ---------------------------------------- | ------------------------- |
| **Snowflake (雪花算法)** | 64 位 Long 型，**时间戳趋势递增** | **完美适配。** 保证数据顺序追加写，彻底避免页分裂，占用空间小。       | **首选。** 金融交易流水、票据系统的标配。   |
| **UUID**             | 32/36 位随机字符串，完全无序       | **毁灭性打击。** 引发极高频的页分裂，且占用大量空间，导致二级索引极其臃肿。 | 严禁作为主键。可作为业务字段单独建非聚簇索引。   |
| **数据库自增 ID**         | Int/BigInt，绝对递增         | 完美适配。但存在单库性能瓶颈。                          | 单机、小规模非拆分表业务。             |
| **Redis 原子生成**       | 利用 `INCR` 指令生成          | 完美适配。单点依赖严重，Redis 宕机找回极难。                | 发号器服务的高可用设计成本较高，不如雪花算法轻量。 |

### 大批量插入 (Bulk Insert) 提速方案：

1. **JDBC 批处理：** 开启 `rewriteBatchedStatements=true`，在 Java 代码中使用 `executeBatch()`，将多条 SQL 重写为 `INSERT INTO table VALUES (),(),()` 结构。
    
2. **临时关闭校验：** 批量导入历史数据时，可临时执行 `SET UNIQUE_CHECKS=0;`（关闭唯一性校验）与 `SET AUTOCOMMIT=0;`，完成后再开启。
    
3. **原生工具：** 极大数据量搬迁直接使用 `LOAD DATA INFILE`，绕过 SQL 解析引擎，速度最快。
    

### 大表架构级优化 (千万级以上数据)

单表行数一旦越过阈值（经验值 1000 万 ~ 2000 万），B+Tree 树高可能突破 3 层，常规索引调优收效甚微，必须从架构层面开刀：

1. **限制查询范围（降维打击）：** C 端接口严禁提供无边界的条件搜索，强制要求传入时间窗口（如“近 30 天”、“近 3 个月”）。
    
2. **读写分离：** 引入主从架构。主库专干高并发的 `INSERT/UPDATE`，从库负责报表导出和重度 `SELECT`。
    
3. **垂直分库分表：** 按业务域“剥离”。比如将核心票据表拆分为“票据基础信息表”和“票据流转记录表”，将不常查的大字段（TEXT、长字符串）单独拆表。
    
4. **水平分库分表 (Sharding)：** 终极杀招。利用 ShardingSphere 或 MyCat，按分片键（如 user_id 的 Hash 值）将数据打散到多个物理库表，突破单机 I/O 和存储瓶颈。
    

### 生产环境慢 SQL 排查实战 (EXPLAIN)

1. **定位慢 SQL：** 开启 `slow_query_log`，使用 `mysqldumpslow` 或阿里 Druid 监控面板抓取执行耗时越过阈值（如 1s）的 SQL 语句。
    
2. **分析执行计划：** 在 SQL 前加上 `EXPLAIN`（或 `EXPLAIN FORMAT=JSON` 看更详细的开销估算），紧盯以下三个致命指标：
    

- **`type` (连接/访问类型)：**
    
    - _好：_ `system` > `const` (主键等值查询) > `eq_ref` > `ref` (普通索引等值查询) > `range` (范围查询)。
        
    - _极差：_ `index` (遍历整棵索引树) > `ALL` (全表扫描)。见到这俩必须优化。
	    
    - **底线：** 生产环境的 SQL 至少要达到 `range` 或 `ref` 级别，出现 `ALL` 必须优化。
        
- **`key` vs `possible_keys`：**
    
    - 如果 `possible_keys` 有值但 `key` 是 NULL，说明优化器认为走索引回表成本太高，强行选择了全表扫描。
        
- **`Extra` (扩展状态信息)：**
    
    - _☠️ 致命死穴：_ `Using filesort`（在内存或磁盘上对结果进行了外部排序，极其消耗 CPU）或 `Using temporary`（使用了临时表处理，多见于复杂的 GROUP BY）。
        
    - _🎉 完美状态：_ `Using index`（触发了**覆盖索引**，数据直接从索引树上拿完，一刀不回表）。
        
    - _👍 良好状态：_ `Using index condition`（触发了**索引下推 ICP**，在引擎层提前过滤了数据，大幅减少了回表次数）。



### MySQL 死锁：现象、定位与业务级根治

线上遇到死锁，靠重启数据库是极其业余的操作，不仅中断业务，而且只要高并发流量一进来，交叉锁的逻辑没改，立马又会死锁。

**1. 现象与报错：** 业务日志中会出现经典的异常：`Deadlock found when trying to get lock; try restarting transaction`。同时伴随相关接口大面积超时。

**2. 标准定位思路（SOP）：**

- **看案发现场：** 登录 MySQL，执行 `SHOW ENGINE INNODB STATUS;`。
    
- **找死锁日志：** 在输出结果中找到 `LATEST DETECTED DEADLOCK` 段落。
    
- **分析争用：** 日志会清晰地列出 Transaction 1 在等哪把锁，Transaction 2 拿着什么锁又在等什么锁。拿到涉及到的 SQL 语句后，去业务代码里反查。
    

**3. 业务代码层面的根治方案：** 死锁的本质是“交叉排队”（A 拿了锁 1 等锁 2，B 拿了锁 2 等锁 1）。在金融或交易系统中，绝大多数死锁是因为**资源加锁顺序不一致导致的**。

> **面试防坑话术：** “如果是线上报死锁，重启数据库只是掩耳盗铃。我会通过 `SHOW ENGINE INNODB STATUS` 拿到死锁日志，锁定是哪两段业务逻辑产生了交叉。
> 
> 最常见的业务死锁场景是转账或互相更新：比如线程 A 处理‘账户 1 转给账户 2’，先锁账户 1 再锁账户 2；同时线程 B 处理‘账户 2 转给账户 1’，先锁 2 再锁 1，并发时必死锁。 **我的改造方案是：** 强行在业务层统一加锁顺序。比如根据账户 ID 的大小，无论谁转给谁，**永远先锁 ID 小的，再锁 ID 大的**。顺序一旦统一，死锁的闭环就被彻底打破了。此外，我也会审查代码，把**大事务拆小**，尽量缩短行锁的持有时间。”



### 锁等待超时问题
#### 现象：
“某行数据始终操作不上，像被卡死了一样”，是因为**有一个‘流氓’事务拿到了这行数据的排他锁（X锁），并且迟迟不提交（Commit）或回滚（Rollback）。** 你的业务线程去请求这行数据时，只能苦苦排队，直到触发了 MySQL 的默认超时时间。

#### 问题原因：
 1. 大事务里裹挟了慢的网络调用
 2. Java线程假死，线程被阻塞住没有向MySQL发送commit命令
 3. 索引失效导致行锁变表锁，进行全表扫描，整个业务阻塞。比如：InnoDB 的行锁，**是加在索引树上的，而不是加在数据行上的。** 假设你执行 `UPDATE table SET status = 1 WHERE name = '张三'`。 如果 `name` 字段没有加索引，或者因为某些“脏数据/隐式类型转换”导致 MySQL 优化器认为**索引失效**了，MySQL 无法精确定位到“张三”这一行。为了保证数据一致性，MySQL 会直接退化为**全表扫描，把整张表的所有行全部锁住（锁升级）**。
 
#### 定位与解决：
**定位思路话术：** “遇到这种长期锁等待的问题，我的第一反应是去查 MySQL 的 `information_schema` 库。

1. 先查 `sys.innodb_lock_waits`（或者 5.7 以下的 `innodb_locks`），看看当前到底是**谁在等谁**，直接能看到被阻塞的 SQL 和阻塞别人的 SQL。
    
2. 再查 `information_schema.innodb_trx` 表，按照事务的运行时间（`trx_started`）倒序排。
    
3. 通常能抓到一个运行了极其久（比如好几分钟）但依然没提交的**长事务 (Long Transaction)**。拿到它的线程 ID (`trx_mysql_thread_id`)。
    

**临时解决：** 如果情况紧急，我会直接执行 `KILL <线程ID>`，把这个流氓事务强杀掉，释放行锁让业务先恢复运转。

**根源排查：** 杀掉后，根据刚刚抓到的涉事 SQL，去代码里反查业务逻辑。如果是外部接口拖垮了事务，就做大事务拆分；如果是索引失效导致锁表，就优化 SQL 强制走索引。杜绝它再次发生。”

#### 死锁 VS 锁等待超时
- **死锁（Deadlock）：MySQL 会“秒报”错误。**
    
    - **原理：** 发生了环形等待（A 等 B，B 等 A）。InnoDB 引擎底层有一个极其聪明的“死锁检测机制（wait-for graph）”。只要一发生死锁，MySQL 会**瞬间**察觉到，并立刻主动牺牲掉其中一个事务（回滚它），打破僵局。
        
    - **现象：** 业务代码会**瞬间**收到异常 `Deadlock found when trying to get lock`，根本不会卡死半天。
        
- **锁等待超时（Lock Wait Timeout）：业务会“一直卡死”，直到触发阈值。**
    
    - **原理：** 发生了线性等待（A 拿着锁在睡大觉，B 在外面苦苦等）。MySQL 觉得 A 迟早会释放的，所以让 B 慢慢等。默认要等 **50 秒**（`innodb_lock_wait_timeout` 参数）。
        
    - **现象：** 业务线程就像死机了一样卡在那里，前端一直在 Loading。卡满 50 秒后，突然抛出异常：`Lock wait timeout exceeded; try restarting transaction`。
        
> **🌟 面试话术修正：** “锁等待超时和死锁是两个截然不同的现象。死锁是交叉等待，InnoDB 的死锁检测器会**瞬间**报错，抛出 `Deadlock found`，不会让线程长时间阻塞。而锁等待超时是线性阻塞，通常是因为遇到了‘流氓长事务’一直霸占着排他锁（X锁），导致我们的业务线程卡死，直到等满 MySQL 默认的 50 秒超时时间，才会抛出 `Lock wait timeout exceeded` 异常。”




### MySQL `INSERT` 加锁的四个核心阶段

**背景设定：** 假设 `user` 表（主键 `id`）中存在数据 `id=10` 和 `id=20`，当前间隙为 `(10, 20)`。事务 A 准备执行 `INSERT id=15`，且尚未提交。

**第一阶段：插入前的间隙冲突检测（插入意向锁）** 在实际写入数据前，事务 A 会先检查目标间隙 `(10, 20)` 是否被其他事务加了排他的“间隙锁（Gap Lock）”。

- **若冲突：** 如果有间隙锁存在，事务 A 阻塞等待。
    
- **若无冲突：** 事务 A 在该间隙挂载一个**插入意向锁 (Insert Intention Lock)**。该锁具有极强的包容性：如果此时事务 B 并发插入 `id=12`，也会获取该间隙的插入意向锁。只要具体插入的 ID 不冲突，**意向锁之间绝对互不阻塞**，极大提升了并发写入性能。
    

**第二阶段：数据写入与无锁优化（隐式锁）** 数据真正写入 B+ 树后，InnoDB 并不会立即在内存中创建重量级的锁对象（以节省内存和 CPU 开销）。

- **底层占位：** InnoDB 会利用这行新数据底层的隐藏字段 `trx_id`（事务 ID）来记录当前是由事务 A 写入的。
    
- 只要事务 A 尚未提交，这个 `trx_id` 就充当了一个低成本的**隐式锁**。
    

**第三阶段：遭遇异构读写冲突（锁升级）** 如果此时事务 C 试图执行 `UPDATE ... WHERE id=15`。

- 事务 C 读取到 `id=15` 这条记录，并通过校验底层的 `trx_id`，发现对应的事务 A 依然处于“活跃/未提交”状态。
    
- **锁升级动作：** 事务 C 不能直接修改，它会主动“唤醒”隐式锁，在内存中为事务 A 生成一个真正的**排他记录锁（X锁）**，挂在 `id=15` 上。随后，事务 C 自己生成一个等待锁，进入 `BLOCKED` 状态排队。
    

**第四阶段：并发写入遭遇唯一键冲突（退化防守）** 如果此时事务 D 并发执行 `INSERT ... id=15`，触发了主键/唯一索引冲突。

- 事务 D 不能直接报 `Duplicate Key` 错误退出，因为事务 A 随时可能回滚（若 A 回滚，D 理应可以插入）。
    
- **退化防守：** 为了安全排队，事务 D 的插入操作会触发隐式锁升级，并主动在该记录上申请一把**共享记录锁（S锁）或临键锁（Next-Key Lock）**（视具体索引和事务隔离级别而定）将其挂起。
    
- 待事务 A 最终提交或回滚后，事务 D 才会收到主键冲突报错或继续执行插入。

**面试话术：**
“InnoDB 针对 `INSERT` 的加锁机制设计得极其精妙，整体上遵循 **乐观策略与延迟加锁**的原则，以此来最大化并发性能。它的核心流程可以概括为四步：

1. **插入前（插入意向锁）：** 事务首先会在目标区间申请插入意向锁。这是一种特殊的间隙锁，只要多个并发插入操作的主键不冲突，它们在同一个间隙内完全互不阻塞。
    
2. **插入时（隐式锁优化）：** 数据成功写入 B+ 树后，InnoDB 默认**不加显式的锁对象**，而是利用数据行底层的 `trx_id`（隐藏事务 ID）作为‘隐式锁’进行极低成本的占位。
    
3. **修改冲突（锁升级）：** 只有当其他事务（如 `UPDATE`）试图操作这行未提交的数据时，才会通过校验 `trx_id` 发现冲突。此时，它会主动将该隐式锁升级为真正的**排他记录锁（X锁）**，随后自己进入阻塞等待。这种设计极大降低了常规无冲突情况下的内存与系统开销。
    
4. **并发插入冲突（退化防守）：** 如果多个事务并发插入了相同的唯一键，后来的事务不能直接抛出异常，必须等待前一个活跃事务的最终状态。此时，隐式锁会退化，后续事务会申请**共享锁或临键锁（视索引和隔离级别而定）** 进行安全排队，以防止脏写或幻读。”






### 讲讲MYSQL索引（面试宽泛版）
**1. 破冰切入（目的与基础）：** “提到 MySQL 索引，它的核心目的确实是为了**加速查询**和**保证数据唯一性**。但要真正用好索引，我通常会直接从 InnoDB 的底层数据结构看起。” _(一句话带过基础，迅速把战场拉到你擅长的底层)_

**2. 核心原理（B+ 树与磁盘 I/O）：** “InnoDB 选择了 **B+ 树**作为索引结构。核心原因是为了**对抗磁盘的随机 I/O**。 相比普通的二叉树，B+ 树是一种极其‘矮胖’的数据结构，非叶子节点只存键值，千万级数据树高也才 3 层，这意味着最多只需 3 次磁盘 I/O。而且它的叶子节点用双向链表相连，把关系型数据库最高频的‘范围查询’，完美转化成了高效的磁盘顺序读取。”

**3. 物理模型（聚簇与非聚簇 ➡️ 引出“回表”）：** “基于 B+ 树，InnoDB 在物理存储上做了两极分化，分为**聚簇索引**和**非聚簇索引（二级索引）**。 聚簇索引就是主键树，叶子节点挂着整行真实数据；而非聚簇索引的叶子节点，只存了主键 ID。 这种物理隔离直接导致了日常开发中最痛的一个问题——**‘回表’**。也就是通过普通索引查到主键 ID 后，还得再去主键树查一遍真实数据，白白增加了磁盘开销。”

**4. 业务落地（SQL 优化就是“打怪升级”）：** “所以，我们日常做的所有 SQL 优化，本质上都是在‘对抗回表’**和**‘迎合 B+ 树的有序性’。

- 为了彻底消灭回表，我们强制避免 `SELECT *`，尽量使用**覆盖索引**。
    
- 为了减少回表次数，我们利用 MySQL 5.6 的**索引下推（ICP）**，在引擎层提前过滤数据。
    
- 而为了迎合 B+ 树底层的绝对排序规则，我们在建联合索引和写查询条件时，必须严格遵守**最左前缀法则**，否则二分查找瘫痪，就会退化为全表扫描。”




### 加了索引，查询还是很慢，如何排查
#### 基于 EXPLAIN 结果的慢查询排查兵法

“面试官您好，如果遇到加了索引依然慢的情况，我第一时间会用 `EXPLAIN` 看执行计划。根据 `EXPLAIN` 的结果，排查方向会截然不同。我会把它分为两大类场景：

##### 场景一：EXPLAIN 揭示了问题 —— 发现【没走索引】或【走错了索引】

这种情况属于**静态的 SQL 语法问题**或**优化器决策问题**。

1. **第一种可能：SQL 写法破坏了 B+ 树规则（索引隐性失效）**
    
    - **现象：** `EXPLAIN` 显示 `type = ALL`（全表扫描），`key = NULL`。
        
    - **排查：** 我会立刻检查 SQL 语句。是不是发生了**隐式类型转换**（比如给 varchar 传了 int），或者在索引列上**套用了函数/参与了数学运算**，又或者联合查询违背了**最左前缀法则**。另外，如果是 `LIKE '%xxx'` 左模糊查询，也会直接失效。
        
2. **第二种可能：优化器算账后主动放弃（成本问题）**
    
    - **现象：** `possible_keys` 里明明有我的索引，但 `key` 最终选了 `NULL`，`type = ALL`。
        
    - **排查：** 这是 CBO 优化器的决定。说明我要查的数据量太大，或者字段区分度太低。优化器核算后认为：走二级索引带来的**海量回表随机 I/O 成本**，远大于直接扫主键聚簇索引的顺序 I/O 成本。此时我会考虑缩小查询范围（比如加时间限制），或者修改 SELECT 字段，尝试升级为**覆盖索引**（看 `Extra` 是否出现 `Using index`）来消除回表。
        
3. **第三种可能：统计信息失真（MySQL 选错了索引）**
    
    - **现象：** 明明有更优的联合索引，`EXPLAIN` 却选了一个区分度很差的单列索引。
        
    - **排查：** 这种往往是由于底层表数据频繁更新，导致索引基数（Cardinality）统计滞后。我会直接执行 `ANALYZE TABLE` 重新采校准，或者紧急情况用 `FORCE INDEX` 强行干预。
        
##### 场景二：EXPLAIN 是完美的，但接口依然慢 —— 发现【完美命中索引】

如果 `EXPLAIN` 显示 `type = ref`，甚至 `Extra = Using index`（完美覆盖索引），但查询依然卡顿长达几秒。这就进入了 `EXPLAIN` 的盲区，问题绝对出在**动态的并发环境或物理资源**上。

1. **排查并发锁争用（被别人卡住）**
    
    - **原理：** `EXPLAIN` 在预估时，假定只有我这一条 SQL 在跑，但实际上我的行可能正被另一个大事务用排他锁（X锁）死死锁住。
        
    - **动作：** 我会查询 `performance_schema.data_locks` 和 `innodb_trx` 表，看是否有其他长事务在阻塞我，必要时把那个占着茅坑不拉屎的长事务 `KILL` 掉。
        
2. **排查极其隐蔽的 CPU 杀手：Undo Log 版本链过长**
    
    - **原理：** 如果系统里有一个昨天开启却一直没提交的“幽灵长事务”，InnoDB 为了维持 MVCC，绝对不敢清理 Undo Log。此时我去查这一行数据，虽然走索引飞快地找到了，但我必须在 CPU 里**一层一层地遍历比对这几万个版本的 Undo Log 快照**。
        
    - **表现：** 这种慢查询的特点是磁盘 I/O 不高，但 CPU 利用率瞬间飙升。同样需要揪出那个老旧的长事务。
        
3. **排查物理资源瓶颈（内存与磁盘竞争）**
    
    - **Buffer Pool 被洗劫：** `EXPLAIN` 不知道数据是在内存里还是磁盘上。如果刚刚有跑批任务把内存热数据全挤出去了，我的查询就必须去磁盘排队拉取数据页，发生物理读，速度断崖式下跌。
        
    - **排队效应：** 数据库毫无压力，但应用端的 HikariCP 数据库连接池被打满了，请求在 Java 内存里排队就耗了 3 秒；或者是同一台宿主机上其他进程榨干了磁盘 IOPS。”
