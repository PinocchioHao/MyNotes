## JMM
JMM 是JAVA为了屏蔽各种硬件和操作系统的内存访问差异而制定的一套规范。是多线程安全性的基础。

JMM规定所有的共享变量存储在主内存中，线程对变量的操作必须在工作内存中进行，首先要将主内存中的变量拷贝一份到工作内存中，对其进行操作后，再刷回主内存，并且加解锁必须为同一把锁。  

可见性：一个线程对共享变量的修改，能及时被其它线程给看到  
原子性：一个操作不会被打断，操作要么都成功，要么都失败，类似于事务机制。  
有序性：禁止指令重排。对于没有数据依赖性（主要指内存分配依赖而不是计算依赖）的语句，CPU会进行优化重排操作，由于多线程情况下是进行资源抢占操作，此时指令重排会造成一些不可预计的错误。

**volatile**
volatile是Java虚拟机提供的轻量级的同步机制。  
volatile三大特性：**保证可见性，禁止指令重排（有序性），不保证原子性**。

原理：强制线程不从工作内存（寄存器/L1缓存）读，而是每次都从主内存读写；底层通过插入内存屏障（Memory Barrier）来禁止屏障前后的指令重排序。

**单例模式的双重检查锁（DCL - Double Check Lock）：**
- **问：** 为什么 DCL 里的 `instance` 变量必须加 `volatile`？
- **答：** 因为 `new Object()` 不是原子操作，分为：分配内存 -> 初始化对象 -> 将指针指向内存。如果不加 `volatile` 发生指令重排（变成：分配内存 -> 指针指向内存 -> 初始化对象），其他线程就会拿到一个还没初始化的“半成品”对象。
```java
public class Singleton {
    // 添加volatile关键字禁止指令重排
    private static volatile Singleton instance = null;
    public static Singleton getInstance() {
        // 双端检锁第一步
        if (instance == null) {
            // 同步代码块
            synchronized (Singleton.class) {
                // 双端检锁第二步
                if (instance == null) {
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```


### Synchronized 底层原理 (从字节码到操作系统的全链路串联)

面试官问 `synchronized`，想听的是你能不能把它从“表象”一直扒到“操作系统内核”。你可以按照这四个层次来串联话术：

- **字节码层面 (表象)：** 当你用 `synchronized` 修饰代码块时，编译后的 `.class` 文件中会生成 `monitorenter` 和 `monitorexit` 两个指令。注意，通常会有一个 `enter` 和**两个** `exit`（一个是正常退出释放锁，一个是发生异常时由 JVM 兜底释放锁，防止死锁）。
    
- **Monitor 层面 (核心机制与可重入)：** 每个 Java 对象在 JVM 内部（C++ 层面）都关联着一个 `ObjectMonitor` 对象。当线程执行 `monitorenter` 时，就是试图去获取这个对象的 Monitor 控制权。 Monitor 内部有两个核心属性：`_owner`（指向当前拿到锁的线程）和 `_recursions`（锁的重入次数）。如果同一个线程再次进入，`_owner` 不变，`_recursions` 直接加 1，这就是**可重入性**的底层实现。
    
- **操作系统层面 (重量级锁的痛点)：** 在 JDK 1.6 之前，`synchronized` 是纯粹的“重量级锁”。只要没抢到 Monitor，线程就会被挂起。这底层依赖的是操作系统的 **Mutex Lock (互斥量)**。调用 Mutex 会导致当前线程从“用户态”切换到“内核态”，这个上下文切换极其耗时，这就是以前大家觉得 `synchronized` 慢的根本原因。
    
- **锁升级机制 (JDK 1.6+ 性能救星)：** 为了避免频繁调用 Mutex，JVM 引入了锁升级机制（只能升级，不能降级）：
    
    1. **无锁：** 对象刚创建。
        
    2. **偏向锁：** 认为锁基本不会有竞争。直接在对象的“对象头 (Mark Word)”里记录当前线程的 ID。下次这个线程再来，对比一下 ID 就直接放行，几乎零开销。（注：JDK 15 后已逐渐废弃偏向锁）。
        
    3. **轻量级锁：** 出现轻微竞争（偏向锁被打破）。线程不再挂起，而是在原地通过 **CAS 自旋**（不断循环尝试）来修改对象头获取锁。
        
    4. **重量级锁：** 自旋次数超过阈值，或者竞争极其激烈。自旋太浪费 CPU 了，只能彻底升级为重量级锁，把没抢到锁的线程丢进操作系统的阻塞队列，调用底层 Mutex。


#### 对锁的理解 
**1. 锁的客体与竞争主体** 
锁永远锁的是“对象”**（如 Object Monitor 或 AQS 的 state），而不是“代码”；而**“线程”**则是来竞争抢锁的主体。无论是 `synchronized` 还是 `ReentrantLock` 修饰的方法或代码块，本质上只是在代码层面划定了一道关卡，强制所有执行到此处的线程，必须**串行去争夺那个特定的“锁对象”。

**2. 线程池场景下的锁** 
线程池仅仅是管理线程生命周期的容器，池中的线程依然是纯正的 JVM 线程。因此，多线程/线程池环境下处理并发，根本核心只在于“对象地址是否唯一”**。只要池中的多个线程访问的是内存里的**同一个对象实例，`synchronized` 依然绝对生效，完全能实现严格的互斥与阻塞。

**3. 临界区与锁的性能** 
锁内部包裹的内容，应当**仅限**于程序对“共享资源/变量”的核心修改逻辑（如扣减库存、更新状态）。这段被互斥锁保护的代码区域称为“临界区”。 并发优化的铁律是：**极力缩小临界区**。必须将查库、RPC 外部调用、发送消息等耗时且非线程安全的逻辑剥离出锁的范围。临界区越小，线程持有锁的时间就越短，后续排队线程的阻塞时间就越少，系统的整体并发吞吐量才能最大化。


### 面试高频追问：多线程到底是怎么抢锁的？（底层 Monitor 机制）

当面试官问：“你讲讲 synchronized 底层是怎么实现阻塞和唤醒的？”，你可以直接用“Monitor 状态机”来秒杀：

每个 Java 对象在底层结构（对象头）里，都有一根指针指向一个由 C++ 实现的 **Monitor（管程）** 对象。你可以把 Monitor 想象成一个带有一个包间和两个候客区的 VIP 室：

1. **抢锁（Enter）：** 线程 A 遇到 `synchronized`，尝试修改 Monitor 里的 `owner` 标记。没人占，`owner` 写上线程 A 的名字，抢锁成功。
    
2. **阻塞排队（EntryList）：** 线程 B 来了，一看 `owner` 是 A，抢锁失败。系统底层会剥夺 B 的 CPU 执行权，强制把 B 扔进 Monitor 的 **EntryList（阻塞队列）** 中，状态变为 `BLOCKED`。如果此时 C、D 线程来，也全部塞进 EntryList。
    
3. **释放与唤醒（Exit）：** 线程 A 走出 `synchronized` 代码块，把 `owner` 清空，锁释放。随后，系统会去唤醒 EntryList 里的线程。B、C、D 醒来后，**没有先来后到，大家再次公平乱战抢锁**（非公平锁机制）。
    
4. **WaitSet（等待队列，对应 wait/notify）：** 如果线程 A 在包间里发现条件不满足（比如账户没钱了），主动调用了 `wait()`，A 会立刻交出锁，并走到 **WaitSet** 休息区睡觉（变为 `WAITING` 状态），把包间让给别人，直到有人调用 `notify()` 把他叫回 EntryList 重新排队。
    

> **进阶反杀（JDK 1.6 锁升级优化）：** “在早期，`synchronized` 因为底层重度依赖操作系统的 Mutex Lock（重量级锁），导致线程挂起和唤醒极其消耗内核资源。但在 JDK 1.6 之后，官方引入了**锁升级机制**： 刚开始没有竞争时，只是在对象头里贴个标签记录线程 ID（**偏向锁**）；如果发生了轻微竞争，线程不会马上去操作系统排队，而是原地转圈圈重试抢锁（**轻量级锁/CAS自旋**）；只有当竞争极其激烈、自旋很久都抢不到时，才会真正挂起线程排队（膨胀为**重量级锁**）。这使得 `synchronized` 在现代 Java 开发中的性能已经非常逼近 `ReentrantLock` 了。”



### Happens-Before 原则

在多线程环境下，编译器和 CPU 为了优化性能，会疯狂地对你的代码进行**指令重排**。JMM 制定了 Happens-Before（先行发生）原则，就是为了告诉开发者：**只要符合这些原则，JVM 就向你保证，前一个操作的结果对后一个操作绝对可见，且绝不允许重排倒置。**

面试中不需要背所有规则，牢记并讲清以下三条最常用的即可：

1. **程序次序规则（单线程兜底）：** 在一个线程内，写在前面的代码 Happens-Before 写在后面的代码。单线程里你怎么重排，都不能改变最终运行结果。
    
2. **管程锁定规则（`synchronized` 的基石）：** 解锁（`unlock`）操作必然 Happens-Before 于对**同一个锁**的加锁（`lock`）操作。
    
    - _业务解释：_ 线程 A 退出 `synchronized` 块释放锁，线程 B 随后抢到这把锁进入代码块，线程 B 绝对能看到线程 A 在同步块里修改过的所有变量。
        
3. **Volatile 变量规则（`volatile` 的基石）：** 对一个 `volatile` 变量的写操作，Happens-Before 于后续对这个变量的读操作。
    
    - _业务解释：_ 线程 A 修改了被 `volatile` 修饰的状态标记 `flag = true`，只要线程 B 随后去读这个 `flag`，读到的绝对是 `true`，JMM 强制清空工作内存并刷回主内存来保证可见性。

## JUC (Java.util.concurrent) 与并发工具类

JUC 是 Java 处理高并发的核心工具包，它的架构是分层的。**底层基础**由 `volatile`（保证可见性，有序性）和 CAS（提供硬件级原子指令）筑基；**核心框架**是 AQS（提供统一的线程排队与状态管理机制）；**上层实现**则是基于 AQS 和 CAS 封装出的各种锁（ReentrantLock, ReentrantReadWriteLock）和同步器（CountDownLatch, CyclicBarrier, Semaphore）。  
(`synchronized` 是 JVM 级别的内置关键字，由C++ 实现，不属于JUC的范畴)

### 1. CAS (Compare-And-Swap) — 乐观并发的基石

- **是什么：**
    
    - CAS 是一条 CPU 并发原语，能够从硬件层面保证操作的原子性。
        
    - 它包含三个操作数：内存地址（V）、预期旧值（A）、新值（B）。只有当内存地址 V 的值等于预期旧值 A 时，才将内存地址 V 的值更新为 B。如果不同，说明被其他线程改过，则更新失败并不断自旋重试。
    
- **CAS 自旋重试逻辑：**
    
    - CAS 机制下，只有没被改过的值才能被正常处理。如果更新失败，线程会进入下一次自旋等待，**重新读取主内存的新值**来进行第二轮比较操作。
        
    - **代码本质：** `do { 老值 = 读取主内存(); 新值 = 老值 + 1; } while(!CAS(内存地址, 老值, 新值));`

- **解决什么问题：**
    
    - 在极短的指令修改中（如 `count++`），替代笨重的 `synchronized` 悲观锁。它不需要上下文切换，通过**无锁化编程**保证了极高的并发性能。
        
- **面试高频缺陷与对策：**
    
    1. **高并发下开销大：** 如果并发极高，大量线程抢占失败会长时间处于 `while(true)` 的自旋状态，榨干 CPU。
        
        - _解法：_ JDK 1.8 引入了分段累加机制（如 `LongAdder`）来打散热点。
            
    2. **只能保证单个共享变量：** 针对多变量操作，CAS 鞭长莫及。
        
        - _解法：_ 只能改用传统加锁，或者将多个变量封装进一个对象，使用 `AtomicReference`。
            
    3. **ABA 问题：** 线程 1 准备把 A 改成 C，此时线程 2 飞快地把 A 改成了 B，线程 3 又飞快地把 B 改回了 A。线程 1 检查时发现还是 A，于是更新成功。但实际上数据中途被篡改过。
        
        - _解法：_ 引入时间戳或**版本号**（`AtomicStampedReference`），每次修改版本号 +1，检查时同时核对值和版本号。
            

CAS机制下，只有没被改过的值才能被正常处理，否则进入下一次自旋等待，重新读取主内存的新值来进行第二轮比较操作。如果高并发情况下，其它所有线程不休眠而是继续自旋等待抢锁，开销极大。


### 2. 原子类 (Atomic Classes) — CAS 的直接落地

- **是什么：**
    
    - JUC 提供的 `java.util.concurrent.atomic` 包下的类，如 `AtomicInteger`、`AtomicBoolean`、`AtomicReference`。
    - 现代 Java 中，其底层依赖 `VarHandle` 配合硬件级 CAS 实现。
        
- **解决什么场景：**
    
    - **高并发计数器：** 秒杀扣库存预扣减、接口访问限流统计（`incrementAndGet`）。
        
    - **轻量级并发开关：** 利用 `AtomicBoolean.compareAndSet(false, true)` 实现系统初始化时的“只执行一次”逻辑，或者简单自旋锁。
        
    - **复杂对象原子替换：** 使用 `AtomicReference` 保证对象引用的原子更新。
        

### 3. AQS (AbstractQueuedSynchronizer) — 构建锁的核心引擎

- **是什么：**
    
    - 它是 JUC 中众多重量级同步组件（如 `ReentrantLock`, `CountDownLatch`, `Semaphore`）的底层抽象框架。
        
    - **核心结构：** 维护了一个被 `volatile` 修饰的 `int state` 变量（代表资源或锁的状态，类似状态机），以及一个基于双向链表的 FIFO 同步队列（CLH 队列）。
        
- **解决什么问题：**
    
    - 统一解决了“线程抢不到锁该去哪里排队、什么时候该被唤醒”的问题。
        
    - 开发者只需要重写 AQS 的 `tryAcquire()` / `tryRelease()` 方法定义如何修改 `state`，排队挂起和唤醒的脏活累活全由 AQS 负责。

- **核心流转过程：**
    
    - **抢占：** 线程来办业务，先看 `state` 是不是 0。如果是，直接通过 CAS 将其改为 1（拿到锁，开始执行业务逻辑）。
        
    - **排队与休眠：** 如果 `state` 不是 0（锁被其他线程占用），AQS 就会把当前线程包装成一个 `Node` 节点，加入到 CLH 队列的尾部，并调用 `LockSupport.park()` 将该线程挂起（阻塞休眠，让出 CPU 资源）。
        
    - **唤醒：** 持有锁的线程执行完毕释放锁（将 `state` 变为 0）时，会调用 `LockSupport.unpark()` 唤醒 CLH 队列中最前面的第一个有效节点。被唤醒的线程重新尝试 CAS 抢占锁。
        
#### AQS 中的公平锁和非公平锁怎么体现的？**

- **非公平锁（默认，效率高）：** 新来的线程不管队列里有没有人排队，一上来直接尝试一次 CAS 抢占锁。抢不到再去队尾乖乖排队挂起。
        
- **公平锁：** 新来的线程在尝试抢锁前，会先判断 CLH 队列是否为空。只要队列里有排队的节点，它绝不插队，直接走到队尾封装成 Node 节点排队。


#### AQS 应用底层原理：基于 state 状态机与独占/共享模式的底层机制

AQS (AbstractQueuedSynchronizer) 是 JUC 的底层核心框架。它将并发同步的共性问题进行了抽象，核心维护了两个部分：一个 `volatile int state`（同步状态）和一个基于 FIFO 的 CLH 双向等待队列。

不同的并发工具类通过重写 AQS 的方法赋予 `state` 不同的业务含义，并配合独占或共享的唤醒机制，实现了多样化的同步器：

**模式一：独占模式 (Exclusive)**： 资源同一时刻只能被一个线程获取。底层等待队列采用“**单点唤醒**”机制——当前持有锁的线程释放资源后，只会唤醒队列中最前排的一个等待节点，保证互斥性。

- **代表作：`ReentrantLock`**
    
    - **`state` 的含义：** 表示锁的获取状态与重入次数。
        
    - **工作机制：** `state = 0` 表示锁空闲；线程 A 通过 CAS 将 `state` 修改为 1，表示成功获取锁。如果线程 A 再次获取锁（重入），`state` 递增为 2。此时其他尝试获取锁的线程发现 `state > 0` 且持有锁的不是自己，便会被封装成节点加入 CLH 队列并阻塞。
        
    - **唤醒机制：** 当线程 A 释放锁，将 `state` 减为 0 时，AQS 会唤醒排在队首的下一个线程 B。线程 B 醒来后尝试竞争锁资源，队列后续的线程继续保持阻塞状态。
        

**模式二：共享模式 (Shared)：** 资源允许多个线程同时获取。底层等待队列采用“**链式传播唤醒**机制 (Propagate)”——当一个排队的节点被唤醒并成功获取到共享资源后，如果发现当前资源还有剩余，会立刻唤醒后续的排队节点，后续节点获取资源后继续向后传播唤醒。

- **代表作 1：`Semaphore` (信号量)**
    
    - **`state` 的含义：** 表示可用的许可证 (Permit) 数量。
        
    - **工作机制：** 初始化 `state = 5`，表示有 5 个可用许可证。线程请求获取时，`state` 减 1；当 `state = 0` 时，后续请求获取许可的线程进入队列阻塞等待。
        
    - **唤醒机制：** 假设当前有其他线程释放了 3 个许可证。排在队首的阻塞线程被唤醒并获取 1 个许可证，它发现还有 2 个剩余许可证，此时会触发传播机制，唤醒身后的下一个节点，直至可用许可证被分配完。
        
- **代表作 2：`CountDownLatch`**
    
    - **`state` 的含义：** 表示需要等待的计数量。
        
    - **工作机制：** 初始化 `state = 5`。主线程调用 `await()` 进入队列阻塞等待。5 个工作线程各自完成任务后调用 `countDown()`，使 `state` 依次递减。
        
    - **唤醒机制：** 当 `state` 减为 0 时，AQS 会触发共享模式的唤醒逻辑，将队列中阻塞等待的主线程（或多个处于等待状态的线程）全部唤醒，继续向下执行。
        

**独占与共享的结合实现：`ReentrantReadWriteLock`** 如何在同一个 `state` 变量和 CLH 队列中兼容读锁（共享）和写锁（独占）？

- **实现机制：** Doug Lea 将 32 位的 `int state` 变量按位拆分：高 16 位用于记录读锁的获取状态和重入次数（共享模式，触发链式传播唤醒），低 16 位用于记录写锁的获取状态和重入次数（独占模式，触发单点唤醒）。
    

AQS 的设计思想在于将资源状态管理与线程调度阻塞解耦。具体工具类（如 `ReentrantLock`、`CountDownLatch`）通过实现具体的 `tryAcquire/tryRelease` 或 `tryAcquireShared/tryReleaseShared` 方法来定义 `state` 值的增减逻辑；而 AQS 框架自身则根据调用的模式（独占或共享），统一负责线程的入队、阻塞以及对应的唤醒分发机制。这两者的结合，构成了 Java 并发工具类的底层基石。


### 4. ReentrantLock (可重入互斥锁)

- **是什么：**
    
    - 基于 AQS 独占模式实现的显式锁。
        
- **执行流程简述：**
    
    1. 线程尝试 CAS 修改 AQS 的 `state`（从 0 改为 1）来获取锁。
        
    2. 如果失败，包装线程到 Node 节点加入 AQS 等待队列，调用 `LockSupport.park()` 挂起。
        
    3. 锁释放时，唤醒队头节点的下一个线程重新参与 CAS 竞争。
        

### 5. 并发协同工具三剑客 (基于 AQS 共享模式)

| **工具类**              | **核心机制**                                 | **典型应用场景**                         |
| -------------------- | ---------------------------------------- | ---------------------------------- |
| **`CountDownLatch`** | **减计数（不可重置）。** 主线程阻塞，等子线程们干完活减到 0，主线程放行。 | 大数据分片跑批，所有分片汇总后，主线程合并结果并落库。        |
| **`CyclicBarrier`**  | **加计数（可重置）。** 一组线程等到某种条件下，一起开始执行。        | 并发性能压测，模拟100个并发用户，等凑齐100个线程同时发起请求。 |
| **`Semaphore`**      | **信号量控制。** 控制同时访问某资源的线程数量。               | 数据库连接池限流、限流削峰网关（超过配额直接排队或报错）。      |

### 6. ConcurrentHashMap (JDK 1.8) — 极致的并发容器

- **是什么：**
    
    - 线程安全的 HashMap。JDK 1.8 中采用 `Node(哈希桶元素，当Node链长大于8时自动转为红黑树)数组 + 链表/红黑树` 结构。
        
- **并发加锁机制 (面试核心)：**
    - **放弃 Segment 分段锁：** 抛弃了 1.7 中笨重且内存开销大的 `ReentrantLock` (Segment 数组，一个Segment存在好多个Hash桶，一共只有16个Segment，并发级别只有16)。
    - **锁粒度极度细化：** 将锁的粒度缩小到了数组的每一个哈希桶首节点（Node 头节点，多线程下只需要在哈希冲突时同一个桶内元素阻塞，其它哈希桶的元素能正常并发写）。
        
    - **CAS + `synchronized` 组合拳：**
        - 当往一个空的数组索引处插入第一个节点时，直接使用 **CAS**，完全无锁。
        - 当发生哈希冲突，需要往链表/红黑树追加节点时，只用 **`synchronized`** 锁住当前的头节点对象。
            
- **为什么改用 `synchronized`？**
    
    - 锁细化到单个头节点后，如果还用 `ReentrantLock`，成千上万个锁对象会导致内存灾难。而 `synchronized` 利用对象头存储锁状态，内存开销为 0。且 JVM 对 `synchronized` 做了锁升级和粗化优化，轻微竞争下的性能极佳。

## 多线程 & 线程池 & ThreadLocal

多线程的本质是榨干 CPU 性能，但在 Java 传统模型中，线程极其昂贵。因此，我们必须深刻理解线程的状态流转，并熟练使用线程池进行资源池化管理。
### 线程的生命周期
Java 线程生命周期定义了 6 种明确的状态（`NEW`, `RUNNABLE`, `BLOCKED`, `WAITING`, `TIMED_WAITING`, `TERMINATED`）。面试官常通过 `sleep` 和 `wait` 的区别来考察你对状态转换的理解。

- **`RUNNABLE` (运行/就绪)：** 线程分配到了时间片正在执行，或正在等待 CPU 调度。
    
- **`BLOCKED` (阻塞)：** **专门用于 `synchronized`**。进入同步块且没抢到锁时进入该状态，锁释放后自动恢复。 （注意这里只有使用synchronized这种情况j等待Monitor锁的时候才会进入，ReentrantLock是进入AQS等待队列里面睡觉处于Waiting状态！）
    
- **`WAITING` (无限期等待)：** 调用 `wait()`、`join()` 等进入。此时**会释放持有的锁**。必须等待其他线程调用 `notify()` 或 `notifyAll()` 唤醒。
    
- **`TIMED_WAITING` (限期等待)：** 调用 `sleep(time)`、`wait(time)` 等进入。
    
    - _避坑点：_ `sleep(time)` **绝不释放锁**，时间到了自动醒来继续占着茅坑；`wait(time)` **会释放锁**，时间到了如果锁空闲则去抢锁，不空闲则变为 `BLOCKED`。



### 对线程安全的理解：

线程安全可以简单理解为一个方法或者一个实例可以在多线程环境中使用而不会出现问题。
当多个线程访问一个对象时，如果不需要进行额外的同步控制或协调操作，调用这个对象都可以获得正确结果，则它是线程安全的。
针对方法层面，各个方法独立使用自己的栈帧，不存在资源竞争。

产生线程不安全的原因
在同一程序中运行多个线程本身不会导致问题，问题在于多个线程访问了相同的资源。如，同一内存区（共享变量，数组，或对象）、系统（数据库，web services等）或文件。实际上，这些问题只有在一或多个线程向这些资源做了写操作时才有可能发生，只要资源没有发生变化,多个线程读取相同的资源就是安全的。



### 线程池

#### 核心参数
- corePoolSize：线程池中的核心线程数量，这几个核心线程，即使在没有用的时候，也不会被回收
    
- maximumPoolSize：线程池中可以容纳的最大线程的数量。当workQueue队列已满，放不下新的任务，再通过execute添加新的任务则线程池会再创建新的线程，线程数量大于corePoolSize但不会超过maximumPoolSize，如果超过maximumPoolSize，那么会抛出异常，如RejectedExecutionException。
    
- keepAliveTime：线程池中**非核心线程**最长可以保留的空闲时间。核心线程执行完任务进入`WAITING`状态，而非核心线程执行完进入`TIMED_WAITING`状态，等待`keepAliveTime`之后被唤醒，线程池此时发现它此时是个null任务之后，就清理掉它。
    
- unit：keepAliveTime 的时间单位。
    
- workQueue：等待（阻塞）队列，任务可以储存在任务队列中等待被执行，执行的是FIFIO原则（先进先出）。当线程池正在运行的线程数量已经达到corePoolSize，那么再通过execute添加新的任务则会被加到workQueue队列中，在队列中排队等待执行，而不会立即执行。
    
- threadFactory：创建线程的线程工厂。
    
- handler：拒绝策略，我们可以在任务满了之后，拒绝执行某些任务。


**Java编码规范要求：**
线程资源必须通过线程池提供， 不允许在应用中自行显式创建线程。  
传统 Java 线程本质上是操作系统的内核线程（1:1 映射）。创建和销毁成本极高，且每个线程都要分配至少 1MB 的线程栈内存。高并发下线程上下文切换会消耗大量CPU资源，还可能导致OOM。

不允许使用Executors工具类创建线程池，返回的线程池对象的弊端如下：  
1） FixedThreadPool, SingleThreadPool, ScheduledThreadPool：  
允许的请求队列长度为 Integer.MAX_VALUE， 如果流量激增，可能会堆积大量的请求， 从而导致 OOM。  
2） CachedThreadPool：  
允许的创建线程数量为 Integer.MAX_VALUE， 可能会创建大量的线程， 从而导致 OOM。  

#### 线程池执行流程 & 积压问题 & 队列大小的选择

##### **执行流程选型：**
传统线程池执行流程：
> 1. 任务进来，判断**核心线程数**满没满？没满就新建核心线程处理。
>     
> 2. 核心线程满了，判断**阻塞队列**满没满？没满就把任务扔进队列排队。
>     
> 3. 队列也塞满了，判断**最大线程数**满没满？没满就紧急新建“非核心线程”来处理任务。
>     
> 4. 如果最大线程数也满了，果断执行**拒绝策略**。
>


最大并发量（最大任务容纳量） = 最大线程数 + 阻塞队列容量， 最大任务同时执行数 = 最大线程数。以及线程池尽量按照核心线程数量运行，**即使任务积压了如果数量没超过队列，也不会新建线程消耗掉积压**。其实这是一种偏向**复用资源**的思想，认为核心线程数跑的任务就能吃满CPU资源。适合CPU密集型任务或者平常通用的任务。

而对于IO密集型任务，为了降低延迟，需要解决积压问题，Tomcat、Dubbo 这样的工业级中间件，**直接魔改了 Java 的线程池规则！**
以 Tomcat 为例，它重写了队列的 `offer()` 方法。当核心线程满了，任务准备塞进队列时，Tomcat 的定制队列会“撒谎”说：“我满了（返回 false）！”。这会立刻逼迫线程池跳过排队，直接去创建非核心线程。直到最大线程数也满了，Tomcat 才把任务真正塞进无限队列里。
**这就变成了：核心 $\rightarrow$ 最大 $\rightarrow$ 队列。**

- **为什么排队会致命？** 在查数据库时，线程可能 99% 的时间都在**等待**网络回包，此时 CPU 是完全空闲的。如果按照 JDK 的逻辑，核心线程满了就把请求扔进队列排队，那这会导致大量的 HTTP 请求在排队等待，用户端直接感受到“网站卡死了”、“请求超时”。
    
- **结论：** 对于 I/O 密集型任务，既然 CPU 闲着也是闲着，那就**赶紧开新的线程去接客！** 把所有的 I/O 等待并发起来，直到线程数达到最大极限，实在接不下了，再去排队。**用户的响应延迟高于一切。**


**线程任务超时熔断：**
我们在提交任务到线程池时，通常会拿到一个 `Future` 对象。外层主线程会调用 `future.get(3, TimeUnit.SECONDS)`。如果 3 秒没出结果，主线程就会抛出超时异常，并调用 `future.cancel(true)`。这个 `cancel` 底层就是向那个干活的线程发送一个 **`interrupt` 中断信号**，防止僵尸任务把线程池耗尽。


##### **队列大小选择：**
队列大小的设计，本质上是在**内存安全和业务响应时间**之间找平衡。

第一，我绝对不会设置无界队列，以防 OOM。我会先评估单条任务对象的内存占用，确保队列满载时不会对 JVM 内存造成压力。

第二，我会**结合接口的超时时间反推**。假设核心线程 1 秒能处理 200 个任务，而接口超时要求是 2 秒，那我的队列长度绝对不会超过 400。因为排队超过 2 秒的任务，执行了也是白费资源（僵尸任务）。我会将队列大小设定在 200 左右。

第三，既然在标准线程池模型下，必须等队列满了才会触发最大线程数，那我会**配合 `CallerRunsPolicy` 拒绝策略**。队列满了没关系，让提交任务的主线程自己去跑，这能起到天然的限流反压作用。

最后，就跟线程数一样，静态计算永远是不准的。在生产环境中，最稳妥的做法还是将队列容量参数接入如 Nacos 这样的配置中心，并对线程池的 `QueueSize` 进行打点监控，在压测或大促期间进行**动态扩缩容调优**。



#### 阻塞队列
阻塞队列就是线程排队等待执行的数据结构。

**阻塞队列选型：**

1. **通用首选：`LinkedBlockingQueue` (必须指定大小)**。利用其底层的**双锁分离（putLock/takeLock，消费者消费队头，生产者放入队尾）** 设计，实现极高的生产者/消费者并发吞吐量。
    
2. **内存严控环境：`ArrayBlockingQueue`**。基于连续数组，创建时不仅要指定大小，还可以预先分配好内存，不会像链表那样频繁 `new Node()` 产生额外的垃圾回收开销。但**存取共用一把锁**，并发性能略低。
    
3. **极速响应/零排队：`SynchronousQueue`**。容量为 0，纯粹的线程握手机制，适用于类似 `CachedThreadPool` 这种需要将任务立刻转交给可用线程执行、对排队延迟零容忍的 I/O 密集型场景（Tomcat, Dubbo）。
    
4. **绝对红线：** 严禁使用任何无界队列（包括 `PriorityBlockingQueue` 和未指定大小的 `LinkedBlockingQueue`），必须从物理上斩断任务无限堆积引发 OOM 的可能性。如果业务场景需要带优先级的任务，权衡后再使用 `PriorityBlockingQueue` （基于小顶堆）。


**使用阻塞队列时一定要显式指定队列大小，防止OOM！！！**

#### 拒绝策略

当请求任务不断的过来，超过最大线程数时，需要采用拒绝策略拒绝服务。RejectedExecutionHandler接口提供了拒绝任务处理的自定义方法的机会。在ThreadPoolExecutor中已经包含四种处理策略：

- AbortPolicy  
    该策略会直接**抛出异常**，阻止系统正常工作。  
    默认使用该策略。 -- 抛异常要不得！！！
    
- **CallerRunsPolicy（最常用的拒绝策略！！！其它几种都会抛异常或者丢弃数据，一般系统绝不允许）**  
    只要线程池未关闭，该策略直接在调用者线程中，运行当前的被丢弃的任务。（哪来的去哪里，打回原线程处理该任务）  
    建议不允许失败、性能要求不高、小并发的任务使用此策略。
    
- DiscardPolicy  
    该策略默默的丢弃无法处理的任务，不予任何处理。（队列满了，**丢弃新来的任务**，不抛出异常）  
    建议无关紧要的任务使用该策略。
    
- DiscardOleddestPolicy  
    该策略将丢**弃最老的一个请求**，也就是即将被执行的任务，并尝试再次提交当前任务。（“蓄意插队”，尝试丢掉最老的任务，即队列中即将被执行的任务，与DiscardPolicy相反）  
    喜新厌旧的策略，比如发布消息可以采用此策略。
    

除了JDK默认提供的四种拒绝策略，我们可以根据自己的业务需求去自定义拒绝策略，自定义的方式很简单，直接实现RejectedExecutionHandler接口即可。（**实战上基本就这两种场景，打回反压，或自定义拒绝策略，落标或进入死信队列，后台慢慢补偿**）


**如果线上流量突增，你的线程池和队列全满了，该怎么选拒绝策略才能保证数据不丢？**

“JDK 自带的四种策略往往无法满足金融级的核心业务。 `AbortPolicy` 抛异常太粗暴，`DiscardPolicy` 直接丢数据在银行系统里是绝对红线。 如果是重要但不紧急的任务，我会用 **`CallerRunsPolicy`（调用者运行策略）**。比如主线程是从 MQ 里拉取报文的，一旦线程池满了，主线程就被迫自己去处理这个报文。这会产生天然的**反压（Backpressure）效果**，使得主线程拉取 MQ 的速度变慢，从而把压力挡在 MQ 层面，保护了核心数据库。 **最稳妥的方案是自定义拒绝策略（实现 `RejectedExecutionHandler`）：** 一旦线程池满了，触发自定义策略，直接把这条任务序列化落表，或者发送到一个专门的死信 MQ 中，交由后台的定时任务去慢慢补偿拉取执行，确保金融数据绝对零丢失。”


#### execute和submit的区别？

execute适用于不需要关注返回值的场景，只需要将线程丢到线程池中去执行就可以了。  
submit方法适用于需要关注返回值的场景。

- 线上跑得好好的线程池，为什么有时候里面的线程莫名其妙就没了，连异常日志都没有？
    
- **实战防坑回答：**
    
> “除了有没有返回值（`Future`）的区别外，线上最容易踩坑的是**异常处理机制**。 如果用 `execute`，任务代码抛出未捕获的 RuntimeException，这个线程会直接崩溃被销毁，并且异常堆栈会直接打印到控制台（可以通过定制 `ThreadFactory` 的 `UncaughtExceptionHandler` 来兜底）。 如果用 `submit`，底层会把任务包装成 `FutureTask`。如果抛出异常，**异常会被默默吞没掉**，绝对不会打印日志。只有当你调用 `future.get()` 尝试获取结果时，异常才会被重新抛出。如果线上只 `submit` 却不 `get`，出了 Bug 连日志都查不到。” -- 强调编码规范



#### shutdown和shutdownNow的区别

shutdown：调用了shutdown后，线程池不会再接受新的任务，已提交任务自然结束，不会强行终止。  
shutdownNow：对所有执行中的任务发出interrupt()操作，强行停止；对未开始执行的任务全部取消。


#### 如何合理设置线程数？


- **CPU 密集型 (经验值 N + 1)：**
    
    - 比如加密解密、复杂算法等复杂运算和逻辑判断。CPU 利用率一直 100%。设置 `核心数 + 1`，加 1 是为了防止某个线程偶尔发生缺页中断（Page Fault）卡住时，有一个备用线程能立刻顶上，保证 CPU 不闲着。
        
- **IO 密集型 (经验值 2N，精确值看比例)：**
    
    - 比如 RPC 调用、数据库查询、网络、磁盘IO操作。大部分时间都在等网络响应，CPU 是闲置的。
        
    - **精确计算公式：** `线程数 = CPU核心数 * (1 + (I/O耗时 / CPU计算耗时))`。
        
- **实战推演：**
    
    > 以我们微服务去查数据库为例。一个请求总耗时 105ms，其中只有 5ms 在做 CPU 数据封装，100ms 都在等数据库。那么 I/O 与 CPU 时间比例就是 20。 假设是 8 核服务器，理论上为了让 CPU 吃满，线程数应该设为 `8 * (1 + 20) = 168`（这里也可以用1s做除法倒推）。 但这只是理论值，实际中我们还要考虑**下游系统（数据库）的抗压能力**。如果 DB 的最大连接数或者 QPS 瓶颈只有 1000，按 168 个线程算出来的并发流量会打垮 DB，我们必须按比例将线程数反向回调缩小（当前QPS为168*(1000/(100+5))=1600，如果DB的最大QPS为1000，则最大设置的线程数为：168*(1000/1600)=105），保护底层资源。


实际上，好多系统的线程池都是整个系统复用一个线程池，里面业务千奇百怪，根本不可能按照这种理想的状态来！工业解决方案1：业务物理隔离，不同业务配置各自的线程池；方案2：动态线程池模式，如美团开源的`Hippo4j` 或 `DynamicTp`，将 `corePoolSize`、`maximumPoolSize`、`队列容量` 暴露到配置中心（如 Nacos / Apollo）。配合 Grafana 监控大盘，大促前如果发现积压，直接在配置中心修改数字，**不重启应用即可动态刷新线程池参数**。一边看监控一边调，调到不堵了为止。




#### Java 21 虚拟线程：

- Java 21 引入了虚拟线程，由 JVM 在**用户态调度**（M:N 映射）。创建一个虚拟线程的开销不到 1KB，几十万个随便开。
    
- **最强特性：** 当虚拟线程遇到网络 I/O 等待时，JVM 会自动把它从底层的真实平台线程（Carrier Thread）上**卸载（Unmount）**，让平台线程去跑别的虚拟线程。等网络数据回来了，再把它挂载（Mount）回去继续执行。
    
- **结论：** 在 Java 21 时代，对于纯 IO 密集的 CRUD 业务，甚至连复杂的线程池配置都不需要了，直接 `Executors.newVirtualThreadPerTaskExecutor()`，回归最简单的同步阻塞式写法，就能获得吊打 `Node.js/Go` 的吞吐量。



### ThreadLocal (线程本地变量)

ThreadLocal 可以**为每一个线程**创建一个**属于其自己的“局部变量”**，实现在线程的上下文传递对象。多个线程互相不可见，因此多线程操作该变量不必加锁。

- **与 `synchronized` 的区别：**
    
    - `synchronized` 采用“时间换空间”，多个线程排队访问同一个共享变量，加锁导致并行度降低变成了串行。
        
    - `ThreadLocal` 采用“空间换时间”，为每个线程分配一份独立的变量副本，彻底消除竞争，实现无锁并发。
        

#### 1. ThreadLocal核心机制与数据结构

- 每个 `Thread` 线程对象内部都有一个 `ThreadLocalMap` 类型的成员变量。
    
- `ThreadLocalMap` 里面存储的是键值对：**Key 是 `ThreadLocal` 对象本身，Value 是线程的变量副本**。
    
- **哈希冲突解决：** `ThreadLocalMap` 没有采用链表，它的 Hash 算法采用了**斐波那契散列法**（Golden Ratio 黄金分割），计算得到的散列值极其分散。如果依然发生了 Hash 冲突，采用**开放寻址法**，以步长为 1 向后线性探测，直到找到下一个空闲的可存放位置。（算出来在 1000，如果 1000 已经有了，就看看 1001；1001 有了就看 1002。因为散列算法足够好，且 `ThreadLocalMap` 会在达到阈值（2/3）时扩容，所以冲突概率极小。）
    

#### 2. 内存泄漏陷阱与弱引用设计

`ThreadLocalMap` 中的 Entry 继承自 `WeakReference`，它的 **Key 是弱引用，Value 是强引用**。

- **面试高频：为什么 Key 要设计成弱引用？**
    
    - **反证法：** 如果 Key 是强引用，当业务代码中 `threadLocal` 实例被置为 null 打算回收时，由于线程内部的 `ThreadLocalMap` 里的 Key 依然强引用着它，导致 `ThreadLocal` 对象无法被 GC 回收。只要线程不死亡（比如线程池中的核心线程），这个 Map 就会一直存在，必然引发内存泄漏。
        
    - **弱引用的好处：** 设计为弱引用后，一旦外界将 `threadLocal = null`，在下一次 GC 时，这个 Key 就会被自动回收，此时 Key 就变成了 null。
        
- **面试高频：Key 被回收了，Value 怎么办？（真正的内存泄漏元凶）**
    
    - Key 被 GC 回收变成了 null，但 Value 依然被 Entry 强引用着。此时出现了一个状态：**外界永远无法通过 null Key 访问到这个 Value，但 Value 又和线程同生命周期，无法被回收。** 这才是 ThreadLocal 造成内存泄漏的真正风险。
        
- **兜底与终极防线：**
    
    - 虽然 `ThreadLocal` 在执行 `get()`、`set()` 时，底层会有启发式清理逻辑，顺手把 Key 为 null 的 Entry 清理掉，但这依赖于后续的操作。如果长期不调用，泄漏依然存在。
        
    - **终极解决：** 每次使用完毕后，**必须在 `finally` 代码块中显式调用 `remove()` 方法**彻底清除该 Entry。
        

##### 面试话术
简单来讲，弱引用其实就是**兜底机制**，如果 Key 是强引用，即使业务代码里把 `threadLocal` 对象置为了 null，但线程池里线程底层的`ThreadLocalMap`依然保留着对它的强引用，这个对象和它的 Value 永远无法回收，这是**必然且无法挽救的彻底泄漏**。

改为弱引用后，一旦外界将 `threadLocal` 置为 null，下一次 GC 就会把 Key 回收掉。虽然此时 Value 依然存在，导致了所谓的内存泄漏，但这触发了一个重要的**协同清理机制**。

`ThreadLocal` 内部在执行 `get()`, `set()` 或者 `remove()` 时，都有启发式的清理逻辑。它们在遍历数组时，一旦发现当前槽位的 **Key == null**，就会顺手把这个槽位的 Value 也置为 null 从而释放内存。

所以，弱引用配合底层源码的顺手清理，是尽最大努力在拯救粗心的程序员。当然，最规范的做法永远是不依赖这层兜底，用完后务必在 `finally` 块中调用 `remove()`。”

#### 3. 线程池场景下的 ThreadLocal 实战

在结合线程池使用时，面临两大痛点：

**痛点一：复用导致的脏数据污染**

- 线程池中的线程是复用的。如果任务 A 在执行结束时没有 `remove()` 掉 ThreadLocal 里的用户信息，当该线程被调度去执行任务 B 时，任务 B 就能直接读到任务 A 的用户上下文。
    
- **规范：** 使用完 ThreadLocal 必须清理，这是生产环境的红线。
    

**痛点二：异步任务的上下文透传**

- 当主线程把任务提交给线程池处理时，子线程无法获取主线程存入 `ThreadLocal` 的 Trace ID 或用户 Token。
    
- **工业级方案：** 阿里开源的 **`TransmittableThreadLocal (TTL)`**。它通过装饰器模式包装 `Runnable/Callable`，在主线程提交任务的那一刻主动抓取 ThreadLocal 快照，并在子线程执行前进行回放，执行后恢复，完美解决跨线程池的透传问题。
    

#### 4. 最佳实践规范

在阿里巴巴 Java 开发规范等业界标准中，`ThreadLocal` 变量通常必须被 **`private static final`** 修饰。

- **原因：** `ThreadLocal` 只是一个作为一个访问其内部 Map 的“钥匙”存在。如果把它定义为普通成员变量，那么每次 new 一个新实例对象，就会在 `ThreadLocalMap` 里新增一个 Entry 键值对。使用 `static` 修饰可以确保全局只有一把钥匙（一个 Key），避免无意义的内存消耗和垃圾对象创建。

## 锁
从 JDK 1.6 开始，JVM 对 `synchronized` 进行了**史诗级优化**，引入了“锁升级”机制。现在的 `synchronized` 默认是非常轻量的，**只有在竞争极其激烈、升级为“重量级锁”时，才会去调用操作系统的 mutex 机制**。在无竞争或轻微竞争下，它的性能和 `ReentrantLock` 不相上下，甚至在某些单线程重入场景下由于偏向锁的存在，性能更好（注：JDK 15 后偏向锁被废弃，但在面试八股文中依然是必考点）。

### 锁的使用
#### synchronized使用场景
**`synchronized` 永远锁的是“对象（Object）”，它绝不锁“代码”，更不会去锁“线程”。**

在 Java 中，任何一个对象天生自带一把“隐形的锁”（Monitor，管程）。多线程抢夺 `synchronized` 资源，本质上就是**多个线程在抢夺同一个对象的 Monitor 拥有权**。

`synchronized` 是 Java 语言级别的关键字（底层是 JVM 指令）。因为有编译器的特殊照顾，它可以直接贴在不同地方，表现出不同粒度的锁：

1. **贴在代码块上 `synchronized(obj)`：** 锁指定对象，这个obj一般是类的`final`成员变量。
    
2. **贴在普通方法上 `public synchronized void do()`：** 隐式锁住 `this` 对象。
    
3. **贴在静态方法上 `public static synchronized void do()`：** 隐式锁住 `Class` 类对象。
    
它的特点是：**强作用域、全自动解绑。** 代码执行完或者抛出异常，JVM 自动释放，绝对不可能让你跨方法加解锁。

##### 场景一：修饰普通实例方法（锁 `this` 当前对象）

这是最常见的写法，也是初学者最容易翻车的地方。

```Java
public class BankAccount {
    private int balance = 1000;

    // 修饰普通方法，隐式地锁住了当前调用该方法的对象实例（this）
    public synchronized void withdraw(int amount) {
        balance -= amount;
    }
}
```

**多线程抢夺实况分析：**

- **会发生互斥（阻塞）的情况：** 线程 A 和线程 B 都拿到了**同一个银行账户对象** `account1`。 线程 A 执行 `account1.withdraw(100)`，此时线程 A 抢到了 `account1` 对象的锁。 如果线程 B 同时执行 `account1.withdraw(200)`，因为 `account1` 的锁在 A 手里，B 抢不到，B 就会被迫进入 `BLOCKED` 状态，在门外排队死等，直到 A 执行完方法释放锁。
    
- **绝对不会互斥的情况（最易踩坑）：** 线程 A 拿到 `account1`，线程 B 拿到 `account2`。 线程 A 执行 `account1.withdraw(100)`，抢的是 `account1` 的锁。 线程 B 执行 `account2.withdraw(200)`，抢的是 `account2` 的锁。 **井水不犯河水，两把不同的锁，两个线程完全并行，毫无阻塞。**
    
##### 场景二：修饰静态方法（锁 `Class` 类对象）

一旦加上 `static`，事情就升级了，从“个人资产”变成了“国有资产”。

```Java
public class BankAccount {
    private static int totalBankReserves = 1000000; // 银行总准备金

    // 修饰静态方法，锁住的是 BankAccount.class 这个全局唯一的类对象！
    public static synchronized void decreaseReserves(int amount) {
        totalBankReserves -= amount;
    }
}
```

**多线程抢夺实况分析：** 在 JVM 内存的堆区，不管你 `new` 了多少个 `BankAccount` 实例（`account1`, `account2`, `account3`...），代表它们图纸的 `BankAccount.class` 对象**永远只有一个**。

- **绝对互斥：** 线程 A 拿着 `account1` 实例调用 `decreaseReserves()`，抢走了 `BankAccount.class` 的锁。 此时，线程 B 哪怕拿着完全不同的 `account2` 实例去调用 `decreaseReserves()`，**也得老老实实排队阻塞！** 因为全天下只有这一把类锁，此时在 A 手里。
    

##### 场景三：修饰代码块（锁指定的任意对象）

这是大厂**最推荐的写法**，因为前两种方法把整个方法都锁住了，粒度太大，严重拖慢并发性能。修饰代码块可以实现“细粒度锁”。

```Java
public class BankAccount {
    private int balance = 1000;
    // 专门建一个对象来当锁，不带有任何业务属性，非常干净
    private final Object lockObj = new Object(); 

    public void withdraw(int amount) {
        System.out.println("前面是一些耗时的查库、校验逻辑，不需要同步，大家一起跑...");
        
        // 只把真正需要防并发的扣款核心逻辑锁起来
        synchronized (lockObj) { 
            if (balance >= amount) {
                balance -= amount;
            }
        }
        
        System.out.println("后面是发短信等耗时逻辑，也不需要同步...");
    }
}
```

**多线程抢夺实况分析：** 线程 A 执行到 `synchronized (lockObj)` 时，尝试抢夺 `lockObj` 的 Monitor。抢到了就进去执行核心扣款。 线程 B 如果也执行到了这里，发现 `lockObj` 的锁被 A 拿了，B 就会在 `synchronized (lockObj)` 这行代码处挂起（变为 `BLOCKED` 状态），等 A 走出大括号，B 才能抢锁进入。这种方式让非核心代码得以并行，极大提升了吞吐量。

**注意：** 语法上synchronized的传参是一个对象就可，但是编码规范强制要求传`final Object`，因为`Object`没有任何业务属性，纯粹是用作一把锁，并且轻量；用`final`防止`Object`被改变，对象改变会`synchronized`失效，且没有任何报错提示！



#### ReentrantLock 使用场景
`ReentrantLock`（可重入锁）就像是给开发者提供了一把“手动挡”的高级武器。对比 `synchronized`（全自动傻瓜相机），它提供了极高的灵活性，但也把解锁的责任完全交给了你。
##### 场景一：基础使用与“最致命的血坑”（忘记解锁）

这是日常开发中最标准的写法，也是面试手撕代码时面试官**眼睛死死盯着的第一行代码**。

```Java
import java.util.concurrent.locks.ReentrantLock;

public class BankAccount {
    private int balance = 1000;
    // 全局声明一把显式锁，默认是非公平锁
    private final ReentrantLock lock = new ReentrantLock();

    public void withdraw(int amount) {
        // 1. 加锁（千万不要写在 try 里面！）
        lock.lock(); 
        
        try {
            // 2. 核心业务逻辑
            if (balance >= amount) {
                // 假设这里发生了一个空指针异常 (NullPointerException)
                balance -= amount; 
            }
        } finally {
            // 3. 释放锁（必须放在 finally 的第一行！）
            lock.unlock(); 
        }
    }
}
```

**多线程实况与避坑指南：**

- **底层的 `state` 争夺：** 线程 A 执行 `lock.lock()`，底层 AQS 的 `state` 从 0 变成 1，A 抢锁成功。线程 B 过来一看 `state` 是 1，乖乖去 AQS 的双向链表队列里排队挂起。
    
- **致命血坑（不写 `finally` 的灾难）：** `synchronized` 的好处是，就算你的代码抛出异常崩溃了，JVM 也会自动帮你把锁释放掉。但 `ReentrantLock` **绝对不会自动释放**。如果你没写 `finally` 块，一旦 `try` 里面的代码抛出异常，这把锁就永远成了“死锁”，后续所有来排队的线程全部永久饿死。
    
- **面试扣分细节：** `lock.lock()` 必须写在 `try` 的**外面**。如果写在 `try` 里面，一旦 `lock()` 方法本身抛出异常，进入 `finally` 执行 `unlock()` 就会报 `IllegalMonitorStateException`（你都没拿到锁，凭什么解锁）。
    

##### 场景二：解决死锁的神技 `tryLock()`（限时抢锁）

这是 `ReentrantLock` 碾压 `synchronized` 的最大卖点，也是解决线上高并发系统“雪崩”的利器。

```Java
public void withdrawWithTimeout(int amount) throws InterruptedException {
    // 尝试抢锁，最多只等 3 秒。
    // 如果 3 秒内抢到了，返回 true；如果 3 秒到了别人还没释放，返回 false，绝不死等！
    if (lock.tryLock(3, TimeUnit.SECONDS)) {
        try {
            balance -= amount;
        } finally {
            lock.unlock();
        }
    } else {
        // 抢锁失败（降级逻辑）
        System.out.println("系统繁忙，当前排队人数过多，请稍后再试...");
        // throw new BusinessException("系统繁忙");
    }
}
```

**开发与面试双杀场景：**

- **传统 `synchronized` 的痛点：** 遇到死锁或者慢 SQL 卡住，后面的线程会像春运买票一样，无限制地排队死等，最终导致 Tomcat 的几百个工作线程全部耗尽，系统彻底假死崩溃。
    
- **`tryLock` 的降维打击：** 我们允许线程等 3 秒。3 秒等不到，直接走 `else` 快速失败（Fast-Fail），给前端返回“系统繁忙”的 JSON。这在微服务高可用架构中，是极其优雅的**熔断保护**手段。
    

##### 场景三：公平锁 vs 非公平锁（插队机制）

面试高频突击题：“`ReentrantLock` 默认是公平锁还是非公平锁？为什么这么设计？”

```Java
// 非公平锁（默认）：允许插队。性能极高。
ReentrantLock unfairLock = new ReentrantLock(); 

// 公平锁：讲究先来后到。性能较差。
ReentrantLock fairLock = new ReentrantLock(true); 
```

**多线程抢夺实况（底层真相）：**

- **公平锁（老实人排队）：** 线程 A 在包间里，B、C、D 在外面排队。A 出来了，AQS 唤醒排在最前面的 B。此时线程 E 刚好跑过来，E 发现有人在排队，只能乖乖去队尾站着。
    
- **非公平锁（流氓插队）：** 线程 A 出来释放锁。AQS 刚准备唤醒 B（B 还在从睡眠态转为运行态，需要耗费 CPU 上下文切换时间）。就在这微秒级的空隙，线程 E 冲过来了，E 根本不看队列，直接尝试修改 `state` 抢锁。**大概率 E 抢到了！** 醒来的 B 发现锁没了，只能悲愤地继续睡。
    
- **面试完美话术：**
    
    > “`ReentrantLock` 默认是非公平锁。因为线程的挂起和唤醒需要进行内核态到用户态的切换，开销很大。非公平锁允许刚来的线程直接‘插队’抢锁，大概率能抢到，这就省去了唤醒队列头部线程的开销，**整体系统的吞吐量会提升好几倍**。只有在要求绝对按时间顺序处理业务的特殊场景下，才会开启公平锁。”
    

##### 场景四：为什么叫“可重入”锁？（防自锁机制）

很多初学者天天背 `ReentrantLock`，却不知道 `Reentrant`（可重入）到底是什么意思。

```Java
public void methodA() {
    lock.lock(); // state 从 0 变成 1
    try {
        System.out.println("进入A方法");
        // 关键点：在拿到了锁的情况下，去调用同样需要这把锁的 methodB
        methodB(); 
    } finally {
        lock.unlock(); // state 减 1
    }
}

public void methodB() {
    lock.lock(); // 发现锁在自己手里，直接放行！state 从 1 变成 2
    try {
        System.out.println("进入B方法");
    } finally {
        lock.unlock(); // state 减 1，变回 1。等 methodA 解锁才彻底变 0
    }
}
```

**开发排坑指南：**

- **原理：** 所谓“可重入”，就是**自己可以再次进入自己已经拿到的锁**。底层原理是判断当前拿着锁的线程 ID，是不是就是自己。如果是，就不阻塞，直接把 AQS 里面的 `state` 变量加 1。
    
- **巨坑：加锁次数必须等于解锁次数！** 如果你在 `methodA` 和 `methodB` 里总共调用了 2 次 `lock()`，但只调用了 1 次 `unlock()`，底层 `state` 变成了 1，并没有清零。这就导致这把锁依然没释放，其他线程照样全军覆没！


#### ReentrantLock 只是用来锁代码块的细粒度锁吗？

**1. 推荐“锁代码块”是因为性能（缩小临界区）** 你说的非常对，**在绝大多数情况下，无论是用 `synchronized(obj)` 还是 `ReentrantLock`，我们都极力推荐只锁“核心业务代码块”，而不是锁整个方法。** 在并发编程中，这段被锁住的代码叫**临界区 (Critical Section)**。临界区越小，线程排队的时间就越短，系统的并发吞吐量就越高。把耗时的查库、RPC 调用、发消息等放在锁外面，是后端开发的基本素养。

**2. ReentrantLock 的“越级用法”：跨方法加解锁** 虽然 `ReentrantLock` 在形态上表现为锁住了一段代码，但它和 `synchronized` 有一个**极其本质的区别**：

- `synchronized` 是一个代码块的语法糖，它的加锁和解锁必须在同一个作用域（同一个大括号 `{}` 内）完成，JVM 依靠编译出的 `monitorenter` 和 `monitorexit` 指令自动帮你收尾。
    
- `ReentrantLock` 是基于 API 调用的。这意味着，你完全可以**在方法 A 里调用 `lock.lock()`，然后把资源传给方法 B，最后在方法 B 里调用 `lock.unlock()`！**

**3. 在方法第一行lock，在方法结尾unlock，就实现了方法锁; 把ReentrantLock生命为static变量，就实现了类锁。**

> **面试话术/实战场景：** “`ReentrantLock` 不仅仅是细粒度锁，它提供的是**极致的灵活性**。比如在一些极其复杂的底层框架（如并发容器、链路追踪）中，我们可能需要根据复杂的 `if-else` 条件，在不同的方法链路甚至不同的类中去决定什么时候解锁。这种**跨方法级别的锁控制**，是 `synchronized` 这种强作用域锁根本做不到的。”（当然，日常业务开发极不推荐这么写，容易漏掉 `unlock()` 导致死锁）。

### 锁的分类
#### 维度一：看待并发冲突的态度（悲观 vs 乐观）

这是最宏观的设计理念分类。

- **悲观锁：** 认为只要我不加锁，就一定会有其他线程来捣乱。所以每次读写数据前，必须先锁住。
    
    - _代表实现：_ `synchronized`、`ReentrantLock`。
        
- **乐观锁：** 认为冲突发生的概率很低，干脆不加锁，直接去修改数据。但在更新的那一刻，会去判断一下这期间别人有没有动过数据（比较旧值），没动过就更新成功，动过就重试。
    
    - _代表实现：_ CAS 机制（Compare And Swap）、各种 `AtomicInteger` 原子类。**这就是你笔记中提到的无锁化编程。**
        

#### 维度二：锁的资源独占性（排他 vs 共享）

- **排他锁（独占锁/写锁）：** 这把锁一次只能被一个线程持有。别人想读想写都得在外面等着。
    
    - _代表实现：_ `synchronized`、`ReentrantLock`。
        
- **共享锁（读锁）：** 这把锁可以被多个线程同时持有。只要大家都是来读数据的，没人在写，那大家就可以一起读，互不阻塞。
    
    - _代表实现：_ `ReentrantReadWriteLock` 里面的读锁（ReadLock）。
        

#### 维度三：拿不到锁时的应对策略（阻塞 vs 自旋）

- **阻塞锁：** 线程没抢到锁，直接让出 CPU 使用权，进入休眠状态（内核态阻塞），等锁释放了再被操作系统唤醒。缺点是线程上下文切换开销大。
    
- **自旋锁：** 线程没抢到锁，不休眠，而是原地写一个 `while(true)` 死循环，不断地去试探锁释放了没。优点是响应极快，没有上下文切换开销；缺点是如果锁被别人占用的时间很长，它会在那里白白浪费 CPU。
    

#### 维度四：抢锁时的排队规则（公平 vs 非公平）

- **公平锁：** 严格按照线程排队的顺序来分配锁，先到先得。优点是不会有线程饿死；缺点是吞吐量低（因为每次都要排队唤醒）。
    
- **非公平锁：** 线程不管排队的队伍有多长，一上来直接先尝试“插队”抢一下锁。如果刚好碰上锁被释放，插队成功就直接拿走；抢不到再去乖乖排队。
    
    - _特点：_ **Java 里的锁默认全部是非公平锁**（包括 `synchronized` 和 `ReentrantLock` 的默认构造），因为这种“允许适度插队”的机制能极大地减少线程唤醒的开销，整体吞吐量远高于公平锁。
        

#### 维度五：同一线程的重复获取（可重入 vs 不可重入）

同一线程外层函数获得锁后，内层的递归函数仍然能获取该锁的代码。即：线程可以进入任何一个它已经拥有的锁所同步的代码块。

- _代表实现：_ `ReentrantLock` 名字就叫可重入锁，`synchronized` 也是可重入的。


### 一些Lock API
一般就是`Lock lock = new ReentrantLock();`，JDK15以后`synchronized`性能就跟`ReentrantLock`不相上下。

| **API 类名**                   | **悲观/乐观**     | **排他/共享** | **公平性支持** | **是否可重入** | **核心应用场景**           |
| ---------------------------- | ------------- | --------- | --------- | --------- | -------------------- |
| **`synchronized`**           | 悲观            | 排他        | 仅非公平      | 是         | 常规同步，代码块/方法级加锁       |
| **`ReentrantLock`**          | 悲观            | 排他        | 公平/非公平    | 是         | 需要灵活控制加锁（如超时中断、公平排队） |
| **`ReentrantReadWriteLock`** | 悲观            | 读共享 / 写排他 | 公平/非公平    | 是         | 读多写少场景，提高读并发         |
| **`StampedLock`**            | **乐观读** / 悲观写 | 读共享 / 写排他 | 仅非公平      | **否**     | 极高并发读多写少，防写线程饥饿      |
| **`Atomic*` 系列**             | 乐观 (CAS)      | 共享竞争      | N/A       | N/A       | 纯粹的共享变量原子递增/状态翻转     |



**核心概念与常考面试题：**

- **`synchronized` 与 `ReentrantLock` 对比：**
     首先，底层原理上，`synchronized` 是 JVM 级别的关键字，基于 monitor 和对象头部的锁信息，加解锁自动完成，并支持锁升级优化。而 `ReentrantLock` 是 JUC 包下的 API，通过 AQS 和 CAS 实现。
     其次，`ReentrantLock` 提供了更多功能和更高的灵活性，支持公平锁与非公平锁、尝试锁、响应中断以及多条件变量，但是创建销毁开销比synchronized大，需要手动加解锁。
     最后，在选型上，通常优先使用 `synchronized`，代码简洁且开销可控；当需要高级并发特性时，再采用 `ReentrantLock`。


- **锁的升级机制（必考）：**
    
    - **问：** 讲讲 `synchronized` 的锁升级过程？
        
    - **答：** 无锁 $\rightarrow$ 偏向锁（单线程重入）$\rightarrow$ 轻量级锁（出现竞争，CAS 自旋）$\rightarrow$ 重量级锁（竞争激烈，向 OS 申请互斥量，阻塞挂起）。
        
    - _(装 X 提示：顺口提一句，由于高并发下撤销开销大，偏向锁在 JDK 15 已经被废弃，展示你的前沿视野)_。
        
- **锁的分类概念：**
    
    - **问：** 解释一下公平锁/非公平锁、悲观锁/乐观锁、独占锁/共享锁。
        
    - **答：** `ReentrantLock` 默认是非公平锁（为了高吞吐，允许插队）；传统锁都是悲观独占锁，而读写锁（`ReentrantReadWriteLock`）的读锁是共享锁。



## 相关面试题
### 进程，线程，多核提升在哪
- **进程（Process）：是操作系统分配资源的最小单位。** 相当于一座“工厂”。它有自己独立的内存空间（堆、方法区）。进程之间互相隔离，一个崩了不影响另一个（比如微信崩溃不会导致 QQ 退出）。
    
- **线程（Thread）：是 CPU 调度的最小单位。** 相当于工厂里的“流水线工人”。一个进程里可以有多个线程，它们共享这座工厂的内存资源（所以需要加锁来保证安全），线程切换的开销远小于进程。
    
- **多核处理器的提升（物理并行 vs 逻辑并发）：**
    
    - **单核 CPU 下的多线程：** 只是**并发（Concurrency）**。CPU 像个超级杂耍大师，在多个线程间疯狂切换时间片，让你“感觉”它们在同时运行。但同一物理时刻，只有一个线程在跑。
         
    - **多核多 U（多颗物理 CPU）提升在哪：** 带来了真正的**并行（Parallelism）**。4 核意味着有 4 个真正的物理计算单元，同一时刻可以有 4 个线程“肩并肩”地全速执行，没有任何时间片切换的开销。
        
    - **实战意义：** 对于 CPU 密集型任务（如视频渲染、复杂加密），线程数设置超过“核数 + 1”不仅没用，反而会因为线程切换导致性能下降。多核最大的意义，就是让 CPU 密集型任务有了真正的物理加速。
