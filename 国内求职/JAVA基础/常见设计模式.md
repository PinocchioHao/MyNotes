## 1. 策略模式 + 工厂模式 (消灭千行 `if-else`)

这是业务开发中最容易落地的模式组合，完美契合开闭原则 (OCP)。

- **实战场景：** 在处理复杂的商业汇票业务时，单据往往有多种核心流转操作（如**承兑**、**背书**、**贴现**）。
    
- **重构前 (坏味道)：** 一个超级庞大的 `BillProcessService`，里面充斥着 `if (type.equals("ACCEPTANCE")) { ... } else if (type.equals("ENDORSEMENT")) { ... }`。每次新增一种票据流转规则，都得修改这个核心类，极易引发线上 Bug。
    
- **Clean Code 改造：**
    
    - **策略层：** 定义一个统一的 `BillStrategy` 接口，包含 `process()` 方法。然后让承兑、背书、贴现各自实现这个接口，成为独立的策略类。
        
    - **工厂层：** 结合 Spring 的特性，在策略类上打上 `@Service("acceptanceStrategy")` 等注解。通过一个 `Map<String, BillStrategy>` 将所有策略一次性注入到工厂类中。
        
    - **收益：** 业务入口只需要 `strategyMap.get(type).process()` 一行代码。未来即使再接入新的票据类型，老代码完全不用动，直接加一个新类即可。
        

## 2. 模板方法模式 (规范业务骨架)

这个模式在复杂的交易全链路或者微服务协同中极其常见，体现了良好的架构顶层设计。

- **实战场景：** 无论是微服务的发布迁移，还是票据的统一核验，往往都有标准化的生命周期。
    
- **Clean Code 改造：**
    
    - 定义一个抽象父类 `AbstractBillHandler`，在这个类里写死主流程方法（加 `final` 防止子类篡改），比如：`校验前置参数 -> 执行核心流转 -> 异步发消息 -> 记录审计日志`。
        
    - 其中，“校验参数”和“记录日志”是通用逻辑，直接在父类实现；而“执行核心流转”定义为 `abstract` 方法，交由子类（如承兑子类）去填空。
        
    - **收益：** 把代码重复率降到最低，强制规范了团队其他成员的开发流程。
        

## 3. 观察者模式 (基于 Spring Event 的终极解耦)

在单体或微服务内部，想要实现模块间的完全解耦，除了 MQ，最轻量级的就是观察者模式。

- **实战场景：** 在 CACHI 这种健康医疗平台中，当一个“新患者注册成功”后，系统不仅要写库，还需要：给患者发欢迎短信、初始化健康档案、推送数据给数据中台。
    
- **重构前 (强耦合)：** 注册方法里直接 `Autowired` 了短信 Service、档案 Service，一个方法干了所有事，响应极慢，且任何一个下游报错都会导致注册失败。
    
- **Clean Code 改造：**
    
    - 注册逻辑完成后，直接通过 `ApplicationEventPublisher` 发布一个 `PatientRegisteredEvent`。
        
    - 短信模块和档案模块通过 `@EventListener`（或 `@TransactionalEventListener`）去监听这个事件。
        
    - **收益：** 核心的注册链路完全不知道其他模块的存在，彻底解耦。而且利用 Spring 的特性还可以轻松实现异步监听，提升接口响应速度。
        

## 4. 建造者模式 (Builder - 优雅的对象构建)

这是防御性编程和 Clean Code 在实体类定义上的直接体现。

- **实战场景：** 业务层需要构建一个包含十几个字段的复杂对象（如调用第三方网关的复杂请求报文）。
    
- **重构前 (坏味道)：** 不停地 `new` 对象，然后写十几行 `setXxx()`。不仅代码难看，而且如果在多线程环境下，对象处于“半初始化”状态时被别人拿到，会导致极其隐蔽的 Bug。
    
- **Clean Code 改造：**
    
    - 直接使用 Lombok 的 `@Builder` 注解。
        
    - 通过链式调用 `User.builder().name("Yorrick").age(28).build()` 一气呵成。
        
    - **收益：** 配合不可变对象（所有属性用 `final` 修饰），强制对象在被创建出来的那一刻就是完整的、合法的，从根源上杜绝了一大批空指针和并发修改异常。
