### 一、 HashMap 核心机制 (极高频，必考)

在面试中，HashMap 通常会结合 JDK 1.7 和 JDK 1.8 的底层变更来进行深度对比考察。

#### 1. 数据结构演进

- **JDK 1.7：** 数组 + 单向链表。
    
- **JDK 1.8：** 数组 + 单向链表 + **红黑树**。当链表长度 $\ge 8$ 且数组总容量 $\ge 64$ 时，链表会转化为红黑树，将查询的时间复杂度从 $O(n)$ 优化到 $O(\log n)$。
    

#### 2. 哈希算法与路由寻址

- **扰动函数 (Hash 算法)：** JDK 1.8 中，`hash()` 方法将对象的 `hashCode` 的高 16 位与低 16 位进行异或运算 (`h ^ (h >>> 16)`)。目的是让高位特征参与进寻址计算，减少哈希冲突。
    
- **寻址算法：** 不使用取模 `%`，而是使用按位与运算 `(n - 1) & hash`（前提是数组长度 $n$ 必须是 2 的次幂）。位运算的 CPU 执行效率远高于取模运算。
    

#### 3. 经典故障：HashMap 多线程扩容死循环

- **成因（仅限 JDK 1.7）：** JDK 1.7 扩容迁移数据时，采用的是**头插法**。在多线程并发扩容时，由于线程上下文切换，会导致链表节点引用的顺序被反转，最终形成**环形链表**。后续调用 `get()` 方法触发遍历时，就会陷入死循环，导致 CPU 100%。
    
- **JDK 1.8 的修复：** JDK 1.8 改为了**尾插法**，保证了数据迁移前后链表节点的相对顺序不变，彻底解决了死循环问题。
    
- _面试防坑：_ 虽然 JDK 1.8 解决了死循环，但 HashMap 依然是**非线程安全**的。在多线程环境执行 `put`，依然会导致数据覆盖、节点丢失等严重问题。多线程场景必须使用 `ConcurrentHashMap`。
    

### 二、 扩容机制对比：HashTable vs HashMap vs ConcurrentHashMap

针对你的疑问：“几种 Hash 的扩容机制都一样吗？” —— **完全不同，特别是 ConcurrentHashMap 的扩容机制，是高阶面试的绝对区分点。**

1. **HashTable (已淘汰)：**
    
    - 扩容机制非常粗暴：直接将整个方法用 `synchronized` 锁住。单线程进行新建数组、遍历、重新哈希、迁移。扩容期间，其他所有读写线程全部阻塞。
        
2. **HashMap：**
    
    - 单线程扩容。当元素个数大于阈值（`capacity * loadFactor`）时，创建一个两倍大小的新数组。
        
    - **JDK 1.8 的高位优化：** 迁移数据时，不需要重新计算哈希值。由于数组容量翻倍（2的次幂），只需要看原哈希值新增的那一位是 0 还是 1。是 0 就留在原索引位置，是 1 就移动到 `原索引 + 原数组容量` 的位置。
        
3. **ConcurrentHashMap (CHM)：协同并发扩容 (重点)**
    
    - JDK 1.8 的 CHM 在扩容时，不再是单线程干活，而是支持**多线程协助扩容 (`transfer` 机制)**。
        
    - 当一个线程发现当前 Map 正在扩容（遇到特殊的 `ForwardingNode` 节点），它不会阻塞等待，而是**主动加入**扩容大军。
        
    - CHM 将原数组按步长（如 16 个桶为一批）进行任务划分，多个线程各自领取一部分桶进行数据迁移，极大提升了扩容效率，避免了长时间阻塞。
        

### 三、 ConcurrentHashMap (CHM) 并发机制演进

面试必考 JDK 1.7 与 1.8 中 CHM 如何保证线程安全的底层差异。

- **JDK 1.7：分段锁 (Segment)**
    
    - 采用 `Segment` 数组结构，每个 `Segment` 继承自 `ReentrantLock`。默认将哈希表分为 16 段，每次写操作只锁住当前哈希所在的那个段，并发度最高为 16。
        
- **JDK 1.8：CAS + synchronized**
    
    - 废弃了臃肿的 `Segment`，直接采用 Node 数组。
        
    - **锁粒度细化：** 只锁定当前链表或红黑树的**头节点**。并发度等于当前数组的长度，极大提升了并发量。
        
    - **写入策略：** 如果发生哈希碰撞，发现当前桶是空的，通过底层硬件级别的 **CAS 操作**无锁插入；如果不为空，才使用 `synchronized` 锁住头节点进行尾插或树操作。
        

### 四、 CopyOnWriteArrayList (COW)

- **底层机制 (写时复制)：** 内部维护一个 `volatile` 修饰的数组。在执行 `add()` 或 `remove()` 等写操作时，不直接修改原数组，而是先通过 `ReentrantLock` 加锁，然后复制出一个新数组（长度 +1 或 -1），在新数组上完成修改，最后将内部的 volatile 引用指向新数组，然后释放锁。
    
- **读写分离：** 读操作完全无锁，直接读取原数组，性能极高。
    
- **核心痛点与适用场景：**
    
    1. **内存占用高：** 每次写操作都会在内存中复制一份完整的数组。
        
    2. **弱一致性（最终一致性）：** 读线程可能读到的是旧数组的数据，无法保证强一致性。
        
    
    - _适用场景：_ **读多写少**的并发场景，如系统的黑白名单加载、网关路由规则缓存等。
        

### 五、 数据结构横向对比：红黑树 vs B/B+树 vs 跳表

面试官通常不会让你手写这三种结构，而是考查你对它们**应用场景和物理特性的理解**。

|**数据结构**|**核心特性**|**时间复杂度**|**经典应用场景**|**为什么在这个场景用它？**|
|---|---|---|---|---|
|**红黑树 (RB-Tree)**|弱平衡二叉查找树。任何不平衡最多只需三次旋转即可解决。|$O(\log n)$|Java `HashMap`、`TreeMap`|相比 AVL 树，牺牲了极其严格的平衡性，换取了**更低的插入/删除旋转开销**，适合内存中高频读写的场景。|
|**跳表 (Skip List)**|在底层单链表上添加多级索引，基于概率维持层级结构。|$O(\log n)$|Redis `ZSET`、Java `ConcurrentSkipListMap`|**高并发环境下的利器。** 红黑树在并发插入时调整树结构需要大范围加锁；而跳表只需用 CAS 修改局部链表指针，能极其简单地实现**无锁并发**。|
|**B/B+ 树**|多路平衡查找树，树干极度矮胖。非叶子节点只存索引，叶子节点存数据且相连。|磁盘 I/O 决定|MySQL InnoDB 索引|数据库数据存在磁盘上。B+ 树的高扇出率保证了千万级数据树高仅为 3 层（最多 3 次磁盘 I/O），且极其适合范围查询。|
