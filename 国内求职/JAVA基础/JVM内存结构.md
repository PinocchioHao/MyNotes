
## 类加载机制与双亲委派

### **类加载的生命周期：** 

- **编译：** 你在 IDEA 里写了一个 `User.java` 文件，点击运行。JDK 的 `javac` 编译器首先把它编译成二进制的字节码文件 `User.class`。
    
- **加载 (Load)：** JVM 的 **类加载器 (ClassLoader)** 开始工作，把硬盘上的 `User.class` 读入到内存（方法区/元空间）中，并在堆里生成一个代表这个类的 `java.lang.Class` 对象。
    
- **验证 (Verify)：** JVM 检查这个 `.class` 文件的字节流是否符合规范，防止恶意代码把 JVM 搞崩。
    
- **准备 (Prepare)：** 仅仅为类中的**静态变量**分配内存，并赋“初始零值”。比如你写了 `public static int age = 18;`，在这一步 `age` 的值是 `0`。
    
- **解析 (Resolve)：** 将常量池内的符号引用替换为直接引用（底层内存地址的绑定）。
    
- **初始化 (Init)：** 执行类的 `<clinit>` 方法，真正的赋值动作开始了。这时候刚才的 `age` 才会被正式赋值为 `18`。执行静态代码块。
    
- **使用与卸载：** 程序开始 `new User()` 并在 JVM 执行引擎中运行。运行结束后，类对象被垃圾回收卸载。
    
### **双亲委派模型：**
    
- **BootstrapClassLoader (启动类加载器)：** 由 C++ 编写，它加载的是 Java 绝对的核心底座。**`rt.jar` (Runtime 的缩写)** 就在这里面，包含了我们天天用的 `java.lang.String`、`java.util.List`、`java.io` 等最核心的类。
    
- **ExtensionClassLoader (扩展类加载器)：** **（纠错）它不加载你通过 Maven 引入的包！** 它加载的是 `jre/lib/ext` 目录下的包。这里面通常是 Java 官方提供的一些密码学、国际化等非核心但有用的官方扩展包。
    
- **AppClassLoader (应用程序类加载器)：** 这才是加载“你自己写的类”和“通过 Maven/Gradle 引入的第三方包（MySQL 驱动、Spring 包等）”的类加载器。它的扫描路径是当前的 ClassPath。

        
- **工作流：** 一个类加载器收到加载请求，它自己不先加载，而是把请求**向上委托**给父加载器。只有当父加载器找不到时，子加载器才会尝试自己加载。。。层级委派模型。。。好处：1. 安全性，优先给启动类加载器加载，防止Java核心类被破坏，防止自己写的同名类覆盖核心类。 2. 避免重复加载导致程序混乱，父加载器加载过了，子加载就没必要加载了。。。

还可以通过classloader类来实现自定义加载器来满足特定场景的需求。。。


### 面试话术：
> “Java 程序的运行，本质上是将我们写的 `.java` 文件编译成 `.class` 字节码后，由 JVM 的类加载器加载到内存中执行的过程。这个加载过程包含了加载、验证、准备、解析和初始化等严谨的生命周期。
> 
> 在真正执行加载时，JVM 默认采用的是**双亲委派模型**。主要由三个核心加载器协同工作： 最顶层是 C++ 编写的 `BootstrapClassLoader`，负责加载 `rt.jar` 等 Java 核心基础类；往下是 `ExtensionClassLoader` 负责加载官方扩展包；最底层是我们日常接触最多的 `AppClassLoader`，负责加载我们在 ClassPath 下写的业务代码和引入的第三方依赖。
> 
> **双亲委派的工作流是‘向上委托，向下查找’。** 当 AppClassLoader 收到加载类的请求时，它不会自己先加载，而是把请求一层层向上抛，一直抛到最顶层的 Bootstrap，如果父加载器在自己的管辖范围内找不到这个类，子加载器才会尝试自己去加载。
> 
> 这个设计非常巧妙，主要带来了两个极大的好处：
> 
> 1. **避免重复加载：** 确保了一个类在整个 JVM 内存中只有一份 `Class` 对象，提高了运行效率，防止程序混乱。
>     
> 2. **核心安全性（沙箱机制）：** 比如我自己写了一个恶意代码命名为 `java.lang.String`，因为双亲委派的存在，请求会被抛到最顶层，Bootstrap 会发现核心包里已经有 `String` 类了并直接加载官方的，我写的假冒伪劣类永远没有机会被运行，从而保护了 Java 核心 API 不被篡改。
>     
> 
> **不过在实际的复杂框架开发中，有时候我们必须去打破双亲委派。**
> 
> 最经典的例子就是 **JDBC**。JDBC 的核心接口 `java.sql.Driver` 是定义在 `rt.jar` 里的，由顶层的 Bootstrap 加载。但是它具体的实现类（比如 MySQL 驱动）是由第三方厂商提供，放在 ClassPath 下的。这就导致了一个问题：Bootstrap 作为父加载器，看不到子加载器 AppClassLoader 管辖范围内的 MySQL 驱动代码。
> 
> 为了解决这种‘父加载器需要调用子加载器代码’的倒流问题，Java 引入了 **SPI 机制和线程上下文类加载器 (Thread Context ClassLoader)**。核心类库通过获取当前线程绑定的 AppClassLoader，去主动加载第三方驱动，这就成功打破了双亲委派向上委托的铁律。
> 
> 此外，像 Tomcat 这种 Web 容器，为了保证部署在同一个服务器上的不同项目之间的类能够相互隔离（比如项目 A 依赖 Spring 4，项目 B 依赖 Spring 5），它也会通过自定义 ClassLoader 来打破双亲委派，优先加载 Web 应用自己目录下的类库。”

### JVM内存结构
#### **线程私有**，它们的生命周期和线程相关
包括：程序计数器PC，虚拟机栈，本地方法栈
程序计数器：记录的是当前指令执行到的行数。
虚拟机栈：记录的是方法执行的相关信息，每个方法在执行的时候会创建一个栈帧，记录的是方法层层调用的一个结构，栈帧中存放了局部变量、操作数、动态链接、方法出口等一些方法相关的信息。
本地方法栈：跟虚拟机栈类似，主要用于记录本地方法，包括C++等语言写的一些原生底层方法的调用信息。



#### **线程共享**，它们的生命周期与JVM垃圾回收机制相关
包括：方法区，堆内存
方法区（元空间）：存放一些线程共享的类的一些结构信息。在本地内存里面。 

堆内存：存放对象实例、数组、**字符串常量池**、**静态变量（这俩没有单独的区域，底层还是作为对象被分到新生代和老年代，大概率之后在老年代）**。具体的内存结构要看垃圾回收器。
传统CMS又分为了约1/3的新生代和2/3的老年代，新生代主要存放不断被创建和销毁的不稳定的对象，而老年代主要存放稳定的对象。新生代中又分为80%的Eden区，10%的SurvivorFrom区，10%的SurvivorTo区。当Eden区满的时候，会清除Eden区和SurvivorFrom区的空间，把这上面存活的对象复制到SurvivorTo区，然后这块SurvivorTo区变成SurvivorFrom区，进行下一轮GC，这个过程被称为Young GC。

在 JDK 9 中，默认的垃圾收集器变成了 G1，所以堆内部不再是物理隔离的新生代/老年代，而是变成了大小相等的 Region 集合，逻辑上动态地整合了新生代（E区、S区）和老年代（O区、H区）。

#### **直接内存**
不受JVM管控，性能高。（主要给开发者用，比如操作NIO，就会在堆外分配一块内存用于高速 I/O）


**为什么要废弃永久代，换成元空间？** 核心原因是：类的元数据大小**很难预估**。在旧版本中，给永久代设置小了，项目一旦引入大量动态生成的类（比如用 Spring AOP、CGLib 代理产生大量动态类），极其容易报 `PermGen OOM`；设置大了又浪费内存。移到元空间后，直接使用受系统可用内存限制的本地内存，大大降低了这类 OOM 发生的概率。


### 垃圾回收
#### 如何确定对象是否是垃圾
引用计数法：对象被引用则计数+1，若对象计数为0则表示不被引用，则该对象可被标记为垃圾。python中使用，但是会存在循环依赖问题。
可达性分析法：给定一个GC Root（可以是虚拟机栈或者本地方法栈中引用的对象，以及方法区中静态变量、常量引用的对象），基于这个GC Root看有无对象引用它，若有则记录成一个链式结构。若对象找不到一个GC Root与它相连，则记为不可达，当对象被判定为不可达两次以上之后，被标记为垃圾（JVM会在第一次不可达时判断是否执行finalize()方法，如果不执行或者执行后依旧不可达，则在第二次的时候将其标记为垃圾）。


#### 垃圾回收算法
标记清除法
先标记出垃圾，然后清空垃圾所在的内存区域。实现简单，速度快，但是容易造成内存碎片化。碎片太多对大对象不友好。

标记整理法
标记出垃圾，然后将存活对象向内存一端移动，移动完成后清除存活对象以外区域。解决了内存碎片化问题，但是开销比较大，速度慢。一般用于老年代。

复制法
内存按比例划分为不同区域，当指定区域容量满后，就将存活对象全部复制到另一区域，清空原来区域。内存利用率不高，容易造成内存闲置。新生代在用复制法。


### GC
- **Minor GC = Young GC（新生代 GC）：** 只清理新生代。
- **Major GC = Old GC（老年代 GC）：** 只清理老年代（严格意义上只有 CMS 收集器有单独清理老年代的行为）。
- **Full GC：** 清理整个堆内存（新生代 + 老年代 + 元空间）。很多人经常把 Major GC 和 Full GC 混为一谈，只要明确表达出“Full GC 是全堆扫描”即可。

- **什么时候发生 Young GC？**
    - 当新生代的 **Eden 区被新对象塞满**时，就会触发。
    
- **什么时候发生 Full GC？**
    - **老年代空间不足：** Young GC 存活下来的对象要晋升到老年代，发现老年代装不下了。
    - **空间分配担保失败：** 每次 Young GC 前，JVM 算了一下，发现老年代剩余的连续空间，可能不够装下这次存活下来的对象。
    - **元空间（Metaspace）满了。**
    - 代码里手贱写了 `System.gc()`。


### JVM 调优的目的就是为了减少甚至消灭Full GC
Full GC 的 STW（Stop-The-World），对性能影响巨大。Young GC 和 Mixed GC 也会发生 STW，但是影响甚微。

- **停顿时间呈指数级差异：**
    - Young GC 只扫描新生代，存活对象极少，STW 通常在 **几毫秒到几十毫秒**。用户根本感知不到。
    - G1 的 Mixed GC 是可控的，STW 也能控制在你设定的 **200毫秒** 以内。
    - **Full GC 是全局扫描并整理！** 如果你线上有一个 8GB 甚至 16GB 的堆，发生一次 Full GC，STW 可能会长达 **几秒甚至十几秒**！
        
- **STW 的致命后果：**
    - 在 STW 期间，JVM 里的所有业务线程全部暂停。
    - 对于用户态：APP 会卡死、网页会转圈请求超时。
    - 对于微服务架构：注册中心（如 Nacos、Eureka）会因为几秒钟收不到该节点的心跳，**误以为这个节点宕机了**，直接把它从服务列表里踢出去。等 Full GC 结束，节点恢复，又会重新注册。这会导致线上服务出现**诡异的阵发性熔断和报错**。

所有的调优手段核心都围绕两点：
1. 尽量把对象在新生代的 Young GC 阶段就干掉，不要让它们提前晋升到老年代。 
2. **合理控制并发标记的时机**。比如在 G1 中，我们会合理设置堆占比阈值，让 Mixed GC 早点介入，防止堆内存被完全塞满从而退化为耗时数秒的 Full GC。

通过调优也能发现代码存在的问题和隐患。

###  对象的流转与分配担保

对象一般在堆中创建，流转规则如下：

1. **优先在 Eden 区分配：** 绝大多数新对象在新生代的 Eden 区诞生。当 Eden 区满时，触发 **Minor GC**。
    
2. **大对象直接进入老年代：** 避免在 Eden 和 Survivor 之间发生大量内存复制（可通过参数 `-XX:PretenureSizeThreshold` 设置）。
    
3. **长期存活的对象进入老年代：** 对象在 Survivor 区每熬过一次 Minor GC，年龄+1。默认长到 **15岁**（CMS默认是6岁）就会晋升老年代。
    
4. **动态对象年龄判定：** 如果 Survivor 区中**相同年龄所有对象大小的总和 > Survivor 空间的一半**，年龄大于等于该岁的对象直接进入老年代。
    

#### 什么是“空间分配担保”？  
就是minor GC时，新生代存活对象可能会有一些转移到老年代，针对他们需要做校验再转移。
每次发生 Minor GC 之前，JVM 会先检查**老年代最大可用的连续空间**是否大于**新生代所有对象总空间**。

- 如果大于，说明这次 Minor GC 是绝对安全的。
    
- 如果小于，JVM 会查看历史数据，看之前每次晋升到老年代的对象**平均大小**是多少。
    
    - 如果老年代剩余空间 **大于** 历史平均大小，那就“冒险”尝试一次 Minor GC。如果冒险失败（存活对象太多，老年代还是装不下），就会引发一次 **Full GC**。
        
    - 如果老年代剩余空间 **小于** 历史平均大小，那连冒险都不做了，直接触发 **Full GC**。



“当新生代发生 Minor GC 时，如果 Survivor To 区因为空间不足无法容纳所有存活对象，**不会直接抛出 OOM**。

JVM 会启动**空间分配担保机制**，将无法放入 Survivor To 区的对象直接晋升到老年代。

只有当老年代的可用空间也无法容纳这些溢出的对象时，JVM 才会触发一次 **Full GC** 来清理老年代空间。如果 Full GC 之后老年代依然空间不足，这时候才会最终抛出 **OOM 异常**。OOM 永远是 JVM 尝试了所有清理手段后的最后无奈之举。”



### GC失败的影响
#### 1. Minor GC 失败 (晋升失败)

Minor GC（新生代回收）的“失败”，通常不叫崩溃，而是被称为 **“晋升失败 (Promotion Failure)”** 或 **“空间分配担保失败”**。

- **发生场景：** Eden 区满了触发 Minor GC。存活下来的对象太多，Survivor 区装不下，JVM 试图把这些对象直接放进老年代。但是，**老年代剩下的连续空间也不够装下这些对象了**。
    
- **造成影响（降级与卡顿）：** Minor GC 会立刻中止当前的轻量级回收，**强制升级触发一次 Full GC（或 Major GC）**，试图去清理老年代腾出空间。 _影响：_ 原本只需要几毫秒的停顿，瞬间变成了长达几百毫秒甚至几秒的卡顿。如果系统频繁发生 Minor GC 失败，你会看到应用的响应时间出现极不规律的毛刺。
    

#### 2. Full GC 失败 (彻底崩溃)

Full GC 是 JVM 清理内存的最后一张底牌。它的“失败”，意味着整个堆（新生代+老年代）都被彻底扫描和清理了一遍后，**依然腾不出足够的空间**来存放新的对象。

- **发生场景：** 发生了严重的内存泄漏（如没关闭的连接、无限增长的静态 List），或者瞬间并发极高（如千万级报表导出），导致存活对象把老年代死死占满。
    
- **造成影响（灾难性）：**
    
    1. **抛出 OOM 异常：** JVM 彻底绝望，直接抛出 `java.lang.OutOfMemoryError: Java heap space`。
        
    2. **CPU 被榨干 (GC 死亡螺旋)：** 在抛出 OOM 之前，JVM 会陷入疯狂。它会 100% 占用 CPU 去做无用功（疯狂触发 Full GC 但只回收了不到 2% 的内存），这会导致伴随抛出另一种致命异常：`java.lang.OutOfMemoryError: GC overhead limit exceeded`。
        
    3. **微服务节点假死与雪崩：** 因为 Full GC 会引发极长的 STW（Stop-The-World）。在这漫长的几秒到几十秒内，你的 Spring Boot 节点无法向注册中心（如 Nacos、Eureka）发送心跳。注册中心会认为该节点已宕机，将其强制踢出集群；等 GC 结束后节点又活过来重新注册。这种“阵发性假死”会引发严重的路由异常和调用链超时雪崩。

#### 面试话术
> “Minor GC 和 Full GC 都有可能失败，但后果截然不同。
> 
> Minor GC 的失败通常表现为‘空间分配担保失败’或‘晋升失败’。比如老年代空间不足以容纳从新生代晋升的对象时，它会降级并强制触发 Full GC，这会导致原本几毫秒的停顿突增到几百毫秒，造成接口响应时间的毛刺。
> 
> 而 Full GC 的失败则是灾难性的。当全堆扫描后依然无法释放足够内存时，不仅会直接抛出 OOM 导致应用崩溃，在崩溃前夕，系统通常还会陷入‘GC 死亡螺旋’——CPU 占用率飙升到 100%（触发 GC overhead limit exceeded）。更严重的是，在微服务架构下，Full GC 导致的超长 STW 会让节点错过注册中心的心跳，引发节点被误踢和微服务雪崩。
> 
> 此外，像 CMS 或 G1 这种并发收集器，如果垃圾产生速度快于回收速度，还会发生 Concurrent Mode Failure（并发模式失败）或退化担保失败，导致收集器退化为单线程全局扫描，引发极其严重的线上卡顿假死。”





## 垃圾收集器对比

JDK9之后默认G1，但是默认的不一定就是最优的，需要根据情况设置

虽然现代的 G1 和 ZGC 大放异彩，但它们为了实现“低延迟（低停顿时间）”，在底层牺牲了一定的“吞吐量”（需要消耗更多的 CPU 资源来维护内存状态和并发标记）。如果你的业务是**离线大数据跑批、夜间定时结算报表、科学计算**这类对“系统卡顿”完全不敏感，但要求“整体运算时间最短、最大限度利用 CPU 算力”的纯后台任务，换回 Parallel 收集器依然是性能最强悍的配置。

STW - Stop The World，指的是清除垃圾的时候工作线程也会暂停，造成的短暂卡顿。如果工作线程不停的话容易造成漏标和误标的情况。


### G1收集器
堆内存被划分为2000+大小相等的region，region分以下类型：
- **E (Eden Region)：** 存放刚创建的新对象。
- **S (Survivor Region)：** 存放经过 Minor GC 后存活下来的对象。
- **O (Old Region)：** 存放长期存活的老对象。
- **H (Humongous Region)：** **这是 G1 独有的新概念（大对象区）。** 当一个对象的大小超过了 Region 容量的一半，G1 就认为它是大对象，会直接寻找一个或多个连续的 H 区来存放它，而不是让它进入普通的 Eden 或 Old 区。
逻辑上仍然有新生代和老年代，新生代其实就是**当前所有贴着 E 和 S 标签的 Region 的逻辑集合**，老年代就是**所有贴着 O 和 H 标签的 Region 的逻辑集合**。它们在物理空间上可能是完全散落、交替分布的。

Region 的角色不是终身制的。 比如，一个 Eden Region 被垃圾回收清空后，它就变成了一个空白的“Free Region”。在接下来的运行中，JVM 可以根据需要，把它重新分配为 Old Region 或者是新的 Eden Region。这意味着，**新生代和老年代在整个堆中所占的比例是动态变化的**，G1 会根据预测的停顿时间自动调整它们的数量。

G1的垃圾回收机制
- **Young GC（新生代收集）：**
    - **触发条件：** G1 会动态计算当前需要多少个 Region 作为 Eden 区。当这些 **Eden Region 被塞满**时触发。
        
- **Mixed GC（混合收集 —— G1 的核心灵魂！）：**
    - **注意，这是传统 JVM 没有的概念。** 它清理 **所有的新生代 Region + 部分垃圾最多的老年代 Region**。
    - **触发条件：** 当整个堆的内存占用率达到一个阈值（默认 45%，参数为 `-XX:InitiatingHeapOccupancyPercent`）时，就会开始触发并发标记周期，等并发标记完成后，G1 会根据用户设定的期望停顿时间，在接下来的几次 GC 中分批次执行（默认最多8次） **Mixed GC**，挑出那些“投入产出比”最高的老年代 Region 和新生代一起回收。并且G1还会通过Adaptive IHOP机制自适应调整堆占比阈值。
        
- **Full GC（G1 的退化保底，大灾难）：**
    - **触发条件：** 当你的应用造垃圾的速度太快，导致 Mixed GC 清理不过来，**没有空的 Region 来存放存活对象了**（拷贝失败/晋升失败），G1 就会绝望地停止所有工作，退化成单线程或多线程的全局扫描，这就是 G1 里的 Full GC。

G1切分成 Region 的根本目的，是为了实现**可预测的停顿时间（Pause Time）**。 如果堆是一整块，Full GC 时就必须扫描整个老年代，耗时极长且不可控。划分成 Region 后，G1 会在后台计算每个 Region 里“垃圾”的多少以及回收需要耗费的时间。当触发 GC 时，G1 会根据你设定的最大允许停顿时间（比如 200ms），**优先挑出那些垃圾最多、回收收益最大的 Region 进行回收**，而不是一次性回收整个堆。

### 不同的垃圾回收器对应不同的堆内存布局

- **传统物理隔离的分代模型（连续内存空间）** 如果你通过 JVM 参数配置了 `-XX:+UseSerialGC`（串行 GC）或者 `-XX:+UseParallelGC`（并行 GC），即使你用的是 JDK 9、JDK 17 甚至 JDK 21，堆内存依然会被划分为物理上界限分明的 **Eden 区、两个 Survivor 区和老年代**。
    
    > **注意：** 曾经著名的 CMS 回收器（`-XX:+UseConcMarkSweepGC`）也是传统分代模型，但它在 JDK 9 被标记为废弃，并在 JDK 14 中被彻底移除了，所以高版本 JDK 无法再切换回 CMS。
    
- **基于 Region 的内存结构（物理不连续，逻辑分代或不分代）** 如果你使用默认的 **G1 (`-XX:+UseG1GC`)**，堆内存会被划分为多个大小相等的 Region。G1 仍然保留了新生代和老年代的**概念**（逻辑分代），但它们在物理上不再是隔离的一整块连续内存，而是由一系列分散的 Region 动态组合而成的。 如果你使用更新的 **ZGC (`-XX:+UseZGC`)** 或 **Shenandoah**，它们同样也是基于 Region（或 Page/ZPage）的内存布局。


### 一、 单核时代的极简主义：Serial 家族
- **包含组合：** Serial (新生代/复制算法) + Serial Old (老年代/标记-整理)
- **核心机制：** 单线程串行执行，垃圾回收时必须“Stop The World”（STW，暂停所有业务线程）。
- **利与弊：**

    - **优：** 极度轻量级，没有多线程切换的上下文开销。在单核环境下，它的收集效率是最高的。
    - **劣：** 无法利用多核 CPU 算力，内存越大，STW 卡顿时间越长。
        
- **开发应用场景：** **严格受限的云原生环境**。例如部署在 Kubernetes 中被限制为 `1核 1G` 的轻量级微服务或容器。在算力受限时，简单粗暴就是最好的选择。

### 二、 算力压榨的吞吐量王者：Parallel 家族
- **包含组合：** Parallel Scavenge (新生代/多线程复制) + Parallel Old (老年代/多线程标记-整理)
- **核心机制：** 多线程并行回收。它的唯一 KPI 是**高吞吐量**（让 CPU 尽可能多地把时间花在运行业务代码上，而不是回收垃圾）。**JDK 8 默认。**
    
      
    
- **利与弊：**
    - **优：** 极限利用多核 CPU 资源，整体任务执行时间最短。
    - **劣：** 单次 GC 的停顿时间（STW）不可控。它可能会为了攒足垃圾一次性高效清理，而导致系统短暂卡顿。

- **开发应用场景：** **后台纯计算型任务**。例如夜间的财务报表结算服务、大数据的离线跑批任务、科学计算模块。这些场景不需要人去点击和等待，对“稍微卡一下”完全不敏感，只追求总体任务最快跑完。
    

### 三、 互联网低延迟的先驱：CMS (配合 ParNew)

- **核心机制：** 并发回收（垃圾回收线程与业务线程交替执行）。将老年代回收拆分为四步，核心理念是**降低单次停顿时间（低延迟）**。
    
- **利与弊：**
    - **优：** 第一次打破了长时间的 STW 卡顿，极大提升了系统的响应速度。
    - **劣：** 使用“标记-清除”算法，会产生大量**内存碎片**；产生“浮动垃圾”；并发执行时会抢占部分业务 CPU 资源。
- **开发应用场景：** **已经被淘汰。** 在 JDK 9 被标记为废弃，JDK 14 彻底移除。面试中提到它，主要是为了作为引出 G1 优势的“垫脚石”和对比参照物。
    
### 四、 大内存时代的六边形战士：G1 (Garbage-First)

- **核心机制：** 打破物理隔离，将堆内存划分为数百个大小相等的 **Region**。依然保留新生代/老年代的逻辑概念，但它们变成了动态的 Region 集合。通过评估每个 Region 的垃圾价值，优先回收收益最大的区域。**JDK 9+ 默认。**
    
- **利与弊：**
    - **优：** 使用局部“复制/整理”算法，**完美解决了 CMS 的内存碎片问题**；提供了**可预测的停顿时间**模型（你可以配置期望每次只卡顿 200ms，G1 会尽量满足你）。

    - **劣：** 为了维护各个 Region 之间的跨区引用（Remembered Set），需要消耗额外的内存（约 10%-20%）和 CPU 算力。

- **开发应用场景：** **现代主流后端服务**。只要你的微服务堆内存较大（例如 4GB 到 32GB 之间），且属于面向用户的 API 接口、Web 网站、网关层（对响应延迟极其敏感），G1 都是绝对的主力。
    

### 总结对比速查表

（新生代都是复制法）

| **垃圾回收器体系**      | **核心目标**    | **核心算法（老年代为主）** | **内存结构**      | **最佳开发场景**       | **现状**         |
| ---------------- | ----------- | --------------- | ------------- | ---------------- | -------------- |
| **Serial**       | 极简、省资源      | 标记-整理           | 物理隔离分代        | 单核微服务/轻量级容器      | 可用，特定场景强       |
| **Parallel**     | **最高吞吐量**   | 标记-整理           | 物理隔离分代        | 后台跑批/数据处理        | 可用，JDK 8 默认    |
| **CMS** & ParNew | **最低延迟**    | 标记-清除           | 物理隔离分代        | 历史老旧交易系统         | **已淘汰**        |
| **G1**           | 均衡：延迟可控且无碎片 | 标记-整理/复制        | 逻辑分代 (Region) | 现代高并发 Web/API 服务 | 绝对主力，JDK 9+ 默认 |

## JVM调优与标准排查流程

### CPU占用高、OOM
**开场白（化解没有经验的尴尬，展现规范性）：**

> “其实在我们的票据核心系统里，因为业务请求链路相对可控，且上线前有压测，线上极少出现真实的 OOM。但我们在演练和日常排查中，团队有一套标准的 SOP 流程。”

**话术 A：排查 CPU 100%（展现 Linux 肌肉记忆）**

思路：
`[找到高占用进程] -> [定位高占用线程] -> [16进制转换] -> [定位具体代码行]`

> “如果是报警提示 CPU 飙升，我一般会按四步走，直接抓到具体的代码行号： 第一步，先用 `top` 找出 CPU 占用最高的 Java 进程 PID。 第二步，用 `top -Hp <PID>` 进去看这个进程里的线程，找到占用最高的那个线程 TID。 第三步，这也是排查最关键的一步，必须用 `printf "%x\n"` 把这个十进制的线程号**转成十六进制**。 第四步，用 `jstack <PID> | grep -A 20 <十六进制TID>`，直接把这段堆栈打出来。
> 
> 根据打出来的日志，通常分两种情况：如果定位到的是我们自己的业务类，那基本就是写了死循环或者复杂的正则回溯；但**在实际场景中，非常大概率我看到的是 `VM Thread`（垃圾回收线程）**。这就意味着 CPU 飙升其实是内存不够导致的频繁 Full GC，这时候我就会立刻切换到 OOM 的排查思路上。”

**神器替代方案：** 如果线上安装了 **Arthas**，直接输入 `thread -n 3`，就能一步列出 CPU 占用最高的前 3 个线程及其堆栈。

**话术 B：排查 OOM（主要是对堆快照进行分析）**

2. **在线观察（不中断服务）：**  
    - 使用 `jstat -gcutil <PID> 1000` 实时观察各区域（Eden、Survivor、Old、Metaspace）的内存使用率和 GC 次数。如果老年代（O区）使用率居高不下且在 Minor GC 后无法释放，说明存在内存泄漏。

> “排查 OOM，核心原则是**先保现场，后做分析**。
> 
> 在发生 OOM 瞬间，最可靠的是依赖启动参数配置的 `-XX:+HeapDumpOnOutOfMemoryError` 自动导出的 `.hprof` 堆快照文件。当然，如果是刚才那种 CPU 飙升、系统假死但还没崩的情况，我会先用 `jstat` 观察一下 Full GC 的频率，确认是内存问题后，手动用 `jmap -dump` 把快照拉下来。
> 
> 拿到 Dump 文件后，我会把它拖到本地用 MAT (Memory Analyzer) 分析。我通常会看三个点：
> 
> 1. 先看 **Histogram（直方图）**，按类名排个序，看是不是有某个对象实例数异常飙升，比如几百万个 String 或者 User 对象。-- 找**数量异常**
>     
> 2. 再看 **Dominator Tree（支配树）**，看哪块内存占据了绝对比例。 -- 找**体积异常**
>     
> 3. 找到大对象后，最关键的是右键执行 **Path to GC Roots**。
>     
> 
> 顺着GC Roots引用链往上追溯，够看到**是哪个具体的类和变量名死死抓住了这些大对象**，基本就能定性是**溢出**还是**泄漏**了。如果是被 `ThreadLocal` 或者没关闭的数据库连接池死死拽着，那就是内存泄漏，要去改代码；如果是千万级报表导出未分页导致瞬间塞满，那就是内存溢出，可以考虑**从业务架构上重构**：将同步导出改为异步任务，后台使用 EasyExcel 一条条流式写入生成文件，完成后上传，最后发通知让用户去下载中心提取，彻底斩断 OOM 的风险。”


相关命令使用链：
- **`top` (系统级监控)：** 收到 CPU 报警时的第一抓手。用 `top` 找异常进程，用 `top -Hp <PID>` 找异常线程。
    
- **`jstat` (GC 状态监控)：** 当系统响应极慢但尚未崩溃时使用。通过 `jstat -gcutil <PID> 1000` 每秒刷新，重点观察 `FGC`（Full GC 次数）和 `FGCT`（耗时）。如果数据疯狂上涨，说明系统正在经历 GC 风暴。
    
- **`jstack` (线程堆栈分析)：** 配合 `top` 定位到的十六进制线程 TID，打印此时 Java 进程的线程快照，用于精准定位死循环、死锁或疯狂运转的 GC 线程。
    
- **`jmap` (内存快照导出)：** 在系统假死、频繁 Full GC 但还没彻底 OOM 时，通过 `jmap -dump:format=b,file=heap.hprof <PID>` 手动把当前内存状态导出来。
    
- **启动参数 (自动现场保留)：** 生产环境必须配置 `-XX:+HeapDumpOnOutOfMemoryError`，确保系统真正 OOM 崩溃时，能自动留下一份 `.hprof` 现场文件。



### 场景 3：接口响应变慢，日志显示频繁发生 Full GC，如何优化？

这个场景考查的是对内存模型、垃圾回收机制以及 JVM 参数的综合理解。

#### 标准回答步骤：

1. **分析原因：** 频繁 Full GC 通常有三个原因：

    - **大对象直接进入老年代：** 代码里一次性从数据库查了太多的数据（比如 `select *` 没加分页）。
    - **老年代空间不足：** `-Xmx`（最大堆）设置得太小，或者堆内存动态扩容引发波动。
    - **内存泄漏：** 某些静态集合或长生命周期对象持续持有短期对象的引用，无法回收。
        
2. **优化手段：**
    - **业务代码层面（优先）：** 优化 SQL 加上分页，避免一次性加载大对象；检查本地缓存是否有过期淘汰策略。

    - **JVM 参数调优：**
        - **固定堆大小：** 将初始堆 `-Xms` 和最大堆 `-Xmx` 设置为相同的值（如 `-Xms4g -Xmx4g`），避免 JVM 频繁调整堆大小带来的开销。
        - **调整垃圾回收器：** 如果是 JDK 8，且老年代回收停顿太长，可以尝试切换为 G1（`-XX:+UseG1GC`），并设置期望的最大停顿时间 `-XX:MaxGCPauseMillis=200`。


## 二、 生产环境必备的常用 JVM 参数速查

面试时如果能顺口报出这几个标准参数，会显得非常专业：

|**参数**|**作用/最佳实践**|
|---|---|
|`-Xms4g` / `-Xmx4g`|设置堆内存初始值与最大值，**强烈建议设为相同**（防止内存抖动）|
|`-Xmn1g` 或 `-XX:NewRatio=2`|设置新生代大小（或老年代与新生代的比例）|
|`-XX:MetaspaceSize=256m` / `-XX:MaxMetaspaceSize=256m`|显式限制元空间大小，防止元空间无节制占用物理内存|
|`-XX:+HeapDumpOnOutOfMemoryError`|OOM 时自动导出 Heap Dump 文件（生产必配）|
|`-XX:HeapDumpPath=/path/dump.hprof`|指定 Dump 文件的保存路径（生产必配）|
|`-XX:+UseG1GC`|手动开启 G1 垃圾收集器|

### 主流第三方排查工具

- **MAT (Memory Analyzer Tool)：** 分析 jmap 导出的 dump 文件，找内存泄漏（OOM）原因的核心工具。
    
- **Arthas（阿尔萨斯）：** **目前国内面试必问/加分项**。阿里开源的 Java 线上诊断神器，无需重启即可动态追踪方法耗时、查看方法入参出参、反编译类文件等。

### “你在项目中做过哪些 JVM 调优？”

> 说实话，在我们的金融票据系统中，因为对业务链路和并发有着极其严格的控制，加上线上环境配置比较充裕，所以真正在生产环境中并没有发生过 OOM 崩溃。
> 
> 但是我了解过遇到 CPU 飙升或者疑似内存溢出的报警的处理方案。比如，在不中断服务的情况下，先用 `jstat -gcutil` 盯一下老年代和 Full GC 的频率有无异常。如果是内存瓶颈，在拿到 Dump 文件后，我会重点用 MAT 去看直方图和支配树，排查GC Roots引用链。
> 
> 我个人的调优理念是：**绝不盲目先动 JVM 参数**。所有的内存问题，本质上要优先去排查业务代码。顺着 MAT 里的 GC Roots 引用链，如果是 ThreadLocal 或连接池没释放，那就去修泄漏的 Bug；如果是某个大报表导出导致内存瞬间被打满，那我会向团队建议从架构上改成流式导出或异步处理。只有当代码层面的优化做到极致，我才会去考虑调整 `-Xms`、`-Xmx` 或者切换像 G1 这样的垃圾回收器。
