## Java四种引用类型
#### **1. 四种引用的实战意义：**

- **强引用 (Strong Reference)：** 最普遍的 `Object obj = new Object()`。只要强引用在，OOM 死机了也不回收。
    
- **软引用 (Soft Reference)：** 内存充足时不回收，**濒临 OOM 之前才会回收**。实战场景：本地内存缓存（如缓存图片、字典数据），能在一定程度上防止 OOM。
    
- **弱引用 (Weak Reference)：** **只要发生 GC，不管内存够不够，立刻回收**。实战场景：`ThreadLocal` 的 Key、`WeakHashMap`，用于防止内存泄漏。
    
- **虚引用 (Phantom Reference)：** 无法通过它拿到对象实例。唯一作用：在这个对象被 GC 回收时，收到一个系统通知。实战场景：监控堆外内存 (DirectByteBuffer) 的回收。
    

#### **2. ThreadLocal 为什么会内存泄漏？

> “`ThreadLocal` 的底层是一个 `ThreadLocalMap`。这个 Map 的 Entry 设计非常特殊，它的 **Key 是 WeakReference 弱引用（指向 ThreadLocal 对象本身），但 Value 是强引用（指向真实的业务数据）**。
> 
> 发生 GC 时，如果没有外部强引用指向这个 ThreadLocal，它的 Key 就会被回收变成 null。但是！Value 依然被强引用连着：`Thread -> ThreadLocalMap -> Entry -> Value`。
> 
> 尤其是在业务中我们通常配合**线程池**使用，核心线程是不会销毁的，这意味着这条强引用链永远存在。Key 是 null 了，但 Value 永远驻留在内存里，造成了**内存泄漏**。
> 
> **解决办法：** 阿里规约强制要求，每次用完 `ThreadLocal`，在 `finally` 代码块里必须手动调用 `.remove()` 方法，把整个 Entry 清理掉。”

#### **3. ThreadLocal 为什么要用弱引用？**

假设你在业务方法里写了 `ThreadLocal<User> local = new ThreadLocal<>()`。

- **如果 Key 是强引用：** 当业务方法执行完，你对 `local` 变量的引用断开了。但底层 `Thread` 里的 `ThreadLocalMap` 依然**强引用**着这个 `local` 对象，并且关联着 `Value`。只要线程不死（比如线程池），`local` 对象和 `Value` **永远**都不会被回收，这是 100% 的双重严重泄漏。
    
- **如果 Key 是弱引用 (当前 JDK 设计)：** 当业务方法执行完，`local` 变量失去强引用。下次 GC 时，**`local` 对象本身一定会被回收**。此时，Map 里的 Entry 会出现一个特殊状态：**`Key == null`**，但 `Value` 还在。
    

**奇妙的“兜底清除”机制来了：** JDK 在设计 `ThreadLocalMap` 的 `set()`、`get()`、`remove()` 方法时，加入了一个探测机制。当其它代码再调用这个线程的这些方法时，只要顺道碰上了 `Key == null` 的 Entry，JDK 就会**顺手把对应的 Value 也清空掉**。

**结论：** 弱引用 + 顺手清理机制，极大地降低了内存泄漏的概率。如果不靠规范，这已经是 JDK 能做的最大努力了。 **那为什么阿里规约还要强制 `remove()`？** 因为在**线程池**场景下，如果你用完后不再调用这个线程的 `set/get` 方法，那个顺手清理的逻辑就不会被触发，Value 依然会泄漏。所以强制 `remove()` 是终极保险。




## 内存泄漏 & 内存溢出 (OOM)

- **内存泄漏 (Memory Leak)：** 这是一个**原因（慢性疾病）**。意思是垃圾没法回收，越堆越多。**内存泄漏最终一定会导致内存溢出 OOM。**
- **内存溢出 (OOM - OutOfMemoryError)：** 这是一个**最终死机结果**。意思是 JVM 向操作系统申请不到内存了，直接崩溃。但导致 OOM 的原因，不只有内存泄漏，还有**纯粹的内存溢出（急性撑爆）**。

### OOM 原因
#### 第一类：纯粹的内存溢出 (急性OOM)

对象都是业务正在使用的，GC 无法回收，且短时间内需求量极其巨大，直接撑爆堆内存。

1. **大对象瞬间加载：**
    
    - _场景：_ `SELECT * FROM table` 没有加分页，或者一次性导出百万级 Excel 报表。几百兆的数据瞬间涌入新生代，导致内存溢出。
        
2. **无限增长的无界队列：**
    
    - _场景：_ 错误使用了 `Executors.newFixedThreadPool()` 或 `newCachedThreadPool()`。它们底层默认使用的是 `LinkedBlockingQueue(Integer.MAX_VALUE)`。当突发高并发时，任务处理不过来，几百万个任务堆积在队列里排队，直接导致 OOM。
        
3. **分配的内存本身太小：**
    
    - _场景：_ 启动参数 `-Xmx` 设置过小，不满足业务系统的正常运转底线。
        

#### 第二类：内存泄漏 (慢性OOM：底层资源未释放堆积)

对象已经不再被业务使用了，但由于代码编写错误，还被某些强引用（GC Root）牵连着，导致 GC 无法回收它们。日积月累，吃光内存。

1. **长生命周期的静态集合类 (最常见)：**
    
    - _场景：_ 使用了 `static HashMap` 或 `List` 做本地缓存，只管往里 `put` 数据，但忘了写清除淘汰逻辑，导致集合越来越大。
        
2. **ThreadLocal 忘记 `remove()`：**
    
    - _场景：_ 在微服务网关或拦截器中，用 `ThreadLocal` 存储当前用户的登录信息。由于底层服务器使用了线程池，线程复用不死，如果没有在 `finally` 块中调用 `.remove()`，会导致用户数据残留在内存中，积少成多引发泄漏。
        
3. **各种物理连接未关闭：**
    
    - _场景：_ 数据库连接 (`Connection`)、网络 Socket、IO 流对象等。它们不仅占用 JVM 内存，还占用操作系统的物理资源。不使用时如果没有 `close()`，即使没有任何引用了，底层资源也不会被立刻回收。
        
4. **非静态内部类 (隐蔽杀手)：**
    
    - _场景：_ **非静态内部类在实例化时，会隐式地持有一个外部类的 this 引用。** 如果把这个内部类对象交给了其他长生命周期的组件管理，就会导致外部类哪怕没用了，也永远被牵连着无法被 GC 回收。而静态内部类没有这个隐式引用，内存上是干净的。


### 接口 vs 抽象类
**1. 语法维度的终极区别（注意 Java 8 的变化）：** 以前说接口不能有实现方法，现在不行了。**Java 8 之后，接口可以有 `default` 默认方法和静态方法**。 那两者的核心区别是什么？

- **状态的保持：** 抽象类可以有普通成员变量（状态）；接口只能有 `public static final` 常量（无状态）。
    
- **继承机制：** Java 单继承，所以一个类只能继承一个抽象类，但可以实现多个接口。
    

**2. 架构设计维度的区别（亮剑）：**

- **抽象类表示 "Is-a" (是什么)：** 它是对**同类事物**的向上抽取。
    
    - _结合设计模式：_ **模板方法模式 (Template Method)**。抽象类里写好一套业务骨架（比如支付流程：校验->扣款->发通知），公共逻辑自己实现，把易变的逻辑留成 `abstract` 方法让子类去填空。
        
- **接口表示 "Can-do" (能干什么)：** 它是对**行为/契约**的抽象，跨越了类的界限。
    
    - _结合设计模式：_ **策略模式 (Strategy)**。定义一个 `PaymentStrategy` 接口（含 `pay` 方法），微信支付、支付宝支付分别实现它。然后在运行时通过多态动态切换具体实现。


### 池化技术 & 连接池
#### 池化技术 (Pooling) 的本质与调优

面试官常问：“为什么要用连接池？参数你是怎么设置的？”

- **为什么要池化？** 数据库连接是极其昂贵的物理资源。创建一个连接需要经历底层的 TCP 三次握手、数据库权限校验、分配内存等繁琐步骤。在高并发下，如果每个请求都去新建和销毁连接，数据库瞬间就会被连接耗尽打死。**连接池的本质就是资源复用**，项目启动时提前建好一批连接，业务用完不销毁，而是归还给池子。
    
- **高频踩坑参数 (必须掌握)：**
    
    - **`minIdle` (最小空闲连接数)：** 池子里常驻的保底连接数。
        
    - **`maxActive` (最大连接数)：** 决定了业务高峰期最多能向数据库发多少个并发请求。
        
    - **`maxWait` (获取连接的等待超时时间)：** **这是线上排错的重灾区！** 如果请求突增，池子里的连接被拿光了，新请求等多久报错？如果不设置或设置过长，会导致 Tomcat 的业务线程全部卡死在等数据库连接上，引发应用级雪崩。
        
    - **探活机制 (`testOnBorrow` / `testWhileIdle`)：** 数据库服务端（如 MySQL）默认如果在 8 小时内没有操作，会自动掐断连接。如果池子里的连接“假死”了，业务一用就报错。配置探活机制能在拿连接前执行一句 `SELECT 1`，确保连接是可用的。
        

#### 架构选型：为什么业界垄断式使用 Druid？

在商业汇票这类对数据一致性和系统稳定性要求极高的核心金融系统中，Druid 几乎是唯一的标配选型。面试官很喜欢问：“大家都是连接池（比如 HikariCP 速度还比 Druid 快），为什么公司基本都选 Druid？”

你可以直接抛出 Druid 的两个**杀手锏特性**：

1. **极其强大的可视化监控 (StatFilter)：** Druid 不仅是个连接池，更是个数据库层面的 APM（应用性能监控）。它能监控所有的 SQL 执行耗时、并发数、甚至能精确定位到哪条 SQL 属于慢查询，哪个 Controller 触发了这几条 SQL。这对于线上排查数据库性能瓶颈是降维打击。
    
2. **SQL 防火墙拦截防御 (WallFilter)：** 它内置了强大的 SQL 解析引擎，能在底层直接拦截掉各种恶意的 SQL 注入攻击，或者禁止执行未经索引的全表扫描 `DELETE/UPDATE` 语句，为金融级系统提供了极高的安全兜底。
    
**面试实战话术整合：** “在我们的项目中，业务代码层面通过 MyBatis 进行数据交互，完全屏蔽了底层 JDBC 的繁琐操作。我们在架构层面主要关注数据源的管理，统一采用了阿里的 Druid 连接池。相比于追求极致单体性能的 HikariCP，我们在核心业务中更看重 Druid 提供的 StatFilter 慢 SQL 监控和 WallFilter 防火墙能力。同时，我们会根据不同微服务的业务量，严格调优 `maxActive` 和 `maxWait` 等参数，并开启空闲连接探活，防止数据库出现连接风暴或僵死连接。”
