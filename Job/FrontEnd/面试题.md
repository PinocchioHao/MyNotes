## 1️⃣ Cookie

- **存储位置**：浏览器（客户端）。
    
- **特点**：浏览器每次请求时，会自动带上对应域名下的 cookie。
    
- **用途**：
    
    - 保存一些简单信息（用户偏好、登录状态标识）。
        
    - 也常被用来存储 **Session ID**（不是直接存储密码）。
        
- **问题**：
    
    - 容量小（几 KB）。
        
    - 明文存储在浏览器，容易被窃取（XSS、CSRF）。
        

---

## 2️⃣ Session

- **存储位置**：服务器端（比如内存、Redis、数据库）。
    
- **工作原理**：
    
    1. 用户第一次登录成功 → 服务器生成一个 **Session ID**，保存用户信息。
        
    2. 把这个 Session ID 放在 Cookie 里返回给浏览器。
        
    3. 之后用户请求时，浏览器带着 Session ID，服务器去查对应的会话数据。
        
- **问题**：
    
    - 要在服务器端存储数据 → 成本较高。
        
    - 多服务器集群时，需要做 Session 共享（一般用 Redis 解决）。
        

---

## 3️⃣ Token

- **存储位置**：一般存在浏览器的 localStorage 或 cookie。
    
- **特点**：
    
    - 一串加密/签名的字符串，里面可能包含用户信息。
        
    - 不依赖服务器存储（无状态认证）。
        
- **优点**：
    
    - 适合分布式/微服务（因为不需要共享 Session 数据）。
        
    - 可以跨平台（移动端、Web 端统一用 Token）。
        

---

## 4️⃣ JWT（JSON Web Token）

- **Token 的一种具体实现方式**。
    
- **结构**：`Header.Payload.Signature`
    
    - Header → 声明算法、类型
        
    - Payload → 用户数据（一般不放敏感信息，因为是明文 base64）
        
    - Signature → 签名，保证数据没被篡改
        
- **验证流程**：
    
    - 服务器用密钥验证签名是否正确。
        
    - 正确 → 信任这个 Token；否则拒绝。
        
- **优点**：
    
    - 自包含（包含用户信息 + 签名验证）。
        
    - 无状态，不需要服务器端保存会话。
        
- **问题**：
    
    - 一旦泄漏，别人就能冒充你（直到过期）。
        
    - 不能轻易撤销（不像 Session 可以直接删掉）。

### ✅ **推荐做法（现代主流）**

- **Access Token（JWT）**：短时有效（几分钟），存储在 **内存或 HttpOnly Cookie**。
    
- **Refresh Token**：存储在 **HttpOnly + Secure Cookie**。
    
- 登录时前端只用 Access Token，请求过期时用 Refresh Token 向服务器换新的 Access Token。
